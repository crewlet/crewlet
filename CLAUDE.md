# Crewlet — Project Conventions

Crewlet is a Go engine for orchestrating hierarchically organized AI agent companies. This file is what every session and every agent loads, so it holds what any change here needs and no more: area rules live in `.claude/rules/` and load when you read or edit a file they cover, and procedures live in `.claude/skills/` and load when used. [Where the Rest Lives](#where-the-rest-lives) names them all, and `internal/docsgate` holds this file to its budget.

## Where to Look
- The docs are the source of truth for how the system should work. `docs/index.md` lists every page and is the docs site's navigation; before changing a subsystem, read its concept page under `docs/concepts/` (`overview.md` is the vision, design principles and architecture; `docs/getting-started/quickstart.md` the first run).
- **`internal/README.md` maps every package**, one line each: what it is for. A package's decisions live in its package doc (`go doc ./internal/<pkg>`), the authority: read it before you change the package, and record a decision there, never in the map. Until a package's row is folded into its doc (#1474), read the row too: it may still hold decisions the doc lacks. A row may not grow (`internal/commentgate`), and a new package gets a one-line row.
- `adr/` holds decision records, for a decision that binds more than one package (one inside a package stays in its doc). Each names an Authority it may not restate and an Enforced-by (a test, a compile error or `nothing`); `internal/adr` checks both ways.

## This Is a Public Open-Source Repository
Crewlet is MIT-licensed, developed in the open at `github.com/crewlet/crewlet`, ships signed binaries and a container image from a `v*` tag (plus `ghcr.io/crewlet/crewlet:main`, rebuilt on every push to `main`, which is not a release), and its `docs/` tree is served at docs.crewlet.ai. Everything committed is published permanently — git history keeps what a later commit deletes — so write every change as something a stranger will read, run, and depend on.
- **Never commit a secret, and never fix one by deleting it.** No real API keys, tokens, PATs, webhook secrets, private hostnames, internal URLs, or customer/employee names — in code, tests, docs, examples, fixtures, or commit messages. Examples use `${VAR}` references and placeholders (`example.com`, `U0FOUNDER`, `sk-ant-...`). A credential that lands in a commit is compromised the moment it is pushed: it must be **rotated**, and removing it in a later commit is not a fix.
- **Commit subjects are semantic** — `type(scope): summary`, imperative, lowercase, no trailing period, ≤72 chars. Type is one of `feat` / `fix` / `docs` / `refactor` / `perf` / `test` / `ci` / `build` / `chore` / `revert`. Scope is the component: the package directory under `internal/`, `dashboard` for `dashboard/` and `static/dashboard/`, `cli` for `cmd/crewlet/`, and outside `internal/` the area (`docs`, `deps`, `examples`, `schema`, `scripts`, or the workflow name for `ci`). An incidental fix or tuning the change needed goes in its own commit with its own scope; an unrelated one goes in an issue. A pull request lands as a squash or a merge commit, so its title takes the same form. Nothing enforces this; the full rules are in `CONTRIBUTING.md`.
- **Every commit is signed off** — `git commit -s`, certifying the `DCO` file at the root. Enforced: `scripts/check-signoff.sh` (with its own suite, `scripts/check-signoff_test.sh`) runs in `make check` and in ci.yml's `sign-off` job over a pull request's own commits. Presence is checked, never a match against the author, and merge commits are exempt. Nothing checks the commit the merge button writes; the repository's merge settings keep the trailers. A missing trailer is repaired by rewriting the commit (`git commit --amend -s --no-edit`, or `git rebase --signoff origin/main`).
- **The pull request title is the release note.** There is no `CHANGELOG.md`: each Release body is generated from the titles of the pull requests merged since the previous tag (grouped by `.github/release.yml`), so a user-visible change's title must read as a release note for someone running Crewlet.
- **The root-level files are canonical for process**, and neither this file nor `.claude/` may contradict them: `CONTRIBUTING.md`, `RELEASING.md`, `SECURITY.md`, `CODE_OF_CONDUCT.md`, `DCO` (verbatim upstream text, never edited), `LICENSE`. A rule changed here is changed there in the same commit.
- **Follow the repository's own templates** — `.github/pull_request_template.md` for pull requests, `.github/ISSUE_TEMPLATE/` for issues.
- **Third-party code must be MIT-compatible and attributed.** Source files carry no license headers — do not start adding them.
- **Security issues never go in a public issue or a public PR description** — see `SECURITY.md`.

## No Band-Aids — Always Do the Proper Fix
Never apply band-aid fixes, workarounds, or partial solutions: diagnose the actual problem and fix it at the source, with the correct, complete fix — even if it is large, touches many files, or requires significant refactoring. A quick hack that "works for now" creates tech debt that compounds. **When suggesting a fix, its cost is never a factor**: lead with the proper fix whatever its size — a 2000-line refactor across 50 files or a subsystem rewrite — and never hide it behind a cheaper alternative or present a "quick" option as the default. Never pre-filter suggestions on effort, time, or scope. Size, time and lines of code are not factors — the scope of the fix matches the scope of the problem, and a one-line hack that papers over an issue is strictly worse than a thousand-line change that solves it.
- **No workarounds** — no special cases, flags, or conditional logic around a broken abstraction: fix the abstraction. A compatibility shim — an alias, a both-spellings fallback, an adapter — is the same move under a respectable name, and for a surface no release ever shipped there is nothing on the other side of it to be compatible with (see "Breaking Changes Are Free Until a Tag Ships Them" below).
- **No "temporary" solutions** — every change is one you are willing to maintain indefinitely. Refactor rather than bolt new functionality onto a broken foundation.
- **Update everything** — a proper fix includes all tests, docs, and dependent code.

When in doubt, ask: "Is this the fix I would make if I had unlimited time and unlimited diff size?" If not, find the fix that is.

## Fix the Bugs That Affect Your Work — Open an Issue for Unrelated Ones
While working you WILL notice bugs, and what happens to one turns on a single question: **does it affect what you are implementing?** It does when your change depends on it (calls, reads or builds on the broken behaviour), when it is in the code or text you are changing, when your change would make it worse or newly reachable, when it is another copy of the defect you are fixing, or when it keeps your change from passing a test or gate — that it was broken before you arrived does not make it unrelated. Then it is part of the task: fix it in this change, properly (root cause, tests, docs). If it is **totally unrelated** — none of that holds, noticed while reading, debugging or reviewing something else — leave its code alone and open a GitHub issue for it, so it is on record and gets a change of its own: an unrelated fix folded into a change is a second change nobody reviewed as one, reverted with the first. The `file-issue` skill has how (search first, the bug-report template, the `Priority` and `Effort` fields). Doing neither is never an option.
- **"Totally unrelated" is the bar, not the default** — if you cannot show that none of those holds, fix it. An issue is never a way to skip a fix your change needs.
- **A security bug never goes public** — anything you believe is exploitable, whether or not it affects your work, goes through `SECURITY.md`'s private reporting and into no issue, commit message or pull request description. If you cannot file that report yourself, tell the user in the session and let them decide how its fix lands.
- **Surface what you fixed and what you filed** — call out every incidental fix in your summary and commit message, in a commit of its own where that keeps history clean, and link every issue you opened or added to in your summary and the pull request description. If you could not open one, say so and give the user its title and body.
- **If a fix your change needs can't fit in it** — it needs its own coordinated effort or a risky redesign — do not drop it, and do not file it as though it were unrelated: fix what you safely can and raise the rest with the user (as "No silent narrowing of scope" below).

When in doubt, ask: "Did I notice anything broken that I'm about to leave broken?" If yes: fixed here if it affects this change, an issue if it is totally unrelated — never neither.

## Tuning Knobs Are Findings Too — Don't Defer Them Either
A value that is not a crash but is plainly wrong is a finding like a bug: a magic number, an arbitrary timeout, retry count, backoff, batch size, poll interval, cache TTL, concurrency cap, page or buffer size, rate limit, log level, flag default, temperature or model choice, a baked-in value that should be config, or config that should be a constant. "Just a tuning knob" is the moment the work gets dropped, and a wrong knob is a slow-motion bug waiting for production load — a 1-second timeout that flaps, a retry count that hammers a dying dependency, a temperature that makes a judge non-deterministic. The right value is often a judgment call, and a judgment call is something you make, not something you skip.
- **It goes where a bug would** — a knob your change depends on, touches or makes worse is tuned in this change, to the same bar as a real fix; one in code your change does not touch gets an issue naming the value you would set and why.
- **Tune to the justified value now** — the value you can defend from the code, the data, and the surrounding behaviour. No placeholder, vague comment, or "configurable later" hook. **Expose or collapse, deliberately**: a value callers genuinely need to vary becomes real config; a knob with no honest reason to differ becomes a plain constant.
- **Tie the value to something real** — record why this value where the next reader will see it (the config doc, a comment at the definition, the commit message), anchored to the dependency's p99, the page-size limit, the SLA, the memory budget.
- **Surface what you tuned** — every knob you changed, exposed, or collapsed, with the old and new value and the reason, in your summary and commit message; link the issue for every knob you filed.
- **If the right value needs production data, a benchmark you can't run, or a product decision** — make your best-justified call, mark it clearly, and raise it with the user with a concrete recommendation and the tradeoff. An issue for a knob you did not tune carries the same.

When in doubt, ask: "Am I calling this 'just a knob' so I don't have to decide its value?" If yes, decide it — or escalate it with a concrete recommendation — but never walk past it.

## No Deferred Work — Always Deliver the Clean Implementation
Never defer work: no TODOs, "follow-up" tickets, stub functions, or "we'll fix this later" comments. When you start a task you finish it — completely and cleanly. A long or sprawling task is a reason to commit to the full implementation, not to ship part of it; delivering a large task as a planned series of pull requests (below) is how it gets finished, not a way to defer part of it.
- **Decide and deliver** — make the call and implement it end-to-end; no half-built parallel paths, no decision left for "later".
- **No TODOs, no stubs, no placeholders** — no `TODO`, `FIXME`, `XXX`, `raise NotImplementedError`, or empty bodies pretending to be done. If it's in the diff, it's finished, and that holds for every pull request in a series, not just the last one.
- **No "follow-up" tickets for the current scope, and no "phase 1 / phase 2" hand-waving** — what is part of the task ships in this change, or in a later pull request of a series the tracking issue already lists. An issue is for what lies outside the task, never for an unplanned part of it; a series is planned up front and runs until its last piece lands.
- **No silent narrowing of scope** — deliver the full scope, or raise it with the user before cutting.
- **Tests, docs, migrations all included** — a feature without tests or docs is not delivered.

When in doubt, ask: "If I stopped right now, would a reader of this diff consider the task done?" If not, keep going.

## Split a Large Change into a Series of Mergeable Pull Requests
Before writing code, judge from the planned diff whether it should be split: it is large enough that one pull request would be hard to review or would sit open long enough to drift from `main`, AND it has seams where `main` can take part of it alone (a refactor the feature needs, a new package before the code that wires it in, a migration before its readers, one subsystem before the next). If both hold, run it as a series with the `pr-series` skill; if either does not, it stays one pull request — never split for the sake of splitting. Tell the user which you chose and why. A piece does not have to deliver working functionality by itself, but `main` must be able to take it as it is: clean, finished code that passes every gate, breaks no existing behaviour and leaves nothing half-wired. Never open a pull request against another pull request's branch: open it against `main`, saying `Builds on #N`.

## Breaking Changes Are Free Until a Tag Ships Them
A `v*` tag is the only compatibility boundary: a surface no tag has shipped has nobody behind it. **Change it outright** — rename the field, reshape the struct, drop the flag, move the route — rather than carry a compatibility path for a version that never existed.
- **Establish what has shipped; never remember it** — `git tag --merged` and `git log <newest tag>..HEAD -- <path>`. Today the only release, `v0.1.0`, sits on the initial commit, which holds no `.go` file, so nothing in this tree has shipped. Re-run the check rather than trusting this line.
- **No compatibility path for an unreleased surface** — no alias, both-spellings reader, fallback, adapter, `V2` type or vestigial flag — **and no breaking-change ceremony**: no `!` and no `BREAKING CHANGE:` footer for a break nobody can be running.
- **A free break is still a complete break** — the rename lands everywhere in the same change (`docs/`, `examples/`, `skills/`, the dashboard, tests, package docs) and `schema/` is regenerated. Grep the old name to zero.
- **No compatibility with an older UNRELEASED build** — nothing it wrote is read, migrated, swept or tolerated, and code that exists only for one is deleted. Two constraints hold anyway:
  - **An applied migration is history, not source** — `schema_migrations` keys on the filename, so reshape with a new numbered migration under `internal/store/schema/`.
  - **This build must be a good OLDER peer to the next one** — a rolling upgrade mixes builds, so the forward mechanisms stay; `.claude/rules/compatibility.md` lists them and loads with the code that holds them.
- **Once a tag ships it, the bar changes** — the break carries `!` and a `BREAKING CHANGE:` footer naming what an operator must change, the pull request title says so, and while the major is 0 the minor number moves for it. `CONTRIBUTING.md` and `RELEASING.md` carry the whole rule; change the three together.

## Code Conventions
- **Interfaces are defined by the consumer**, in the package that calls them, and kept to what that caller needs. A provider exports a concrete type. There is no `interfaces.go`
- **`context.Context` first, always**, threaded rather than stored in a struct. A rollback or a teardown takes `context.WithoutCancel`: the failure it is undoing is often the cancellation itself, and a cleanup that inherits a dead context does nothing at all
- **Accept interfaces, return structs**
- **Zero values must be meaningful, or the type must refuse them** — a config field whose zero value is a valid setting needs a pointer or an explicit `Unset` sentinel, not a comment
- **Errors wrap with `%w`** and say what to do about it: an error a person reads names the field, the file or the variable to change. Sentinels are `errors.Is`-comparable; typed errors carry the identifier the caller needs
- **A field holding words somebody else wrote is declared on the field**, as a credential's `secret:"true"` is: a read type tags it `untrusted:"fence"` (words at length — a body, a comment, a message, an excerpt) or `untrusted:"name"` (a title, a name, a label), the tag `provenance.FieldTag` names. The agent runtime's read tools refuse to answer a declared field they did not fence or name the writers of, `provenance.TestEveryDeclaredFieldHoldsText` holds every tag in the tree to those two kinds and to a type that holds text, and `agent/builtin`'s sweep (`TestEveryToolThatHandsOverSomebodysWordsIsFenced`) derives from the declarations which tools hand such words to a model — so a new read type that carries somebody's words declares them, or a tool answering it is never held to the fence (ADR-0040)
- **Every piece of state answers "who has to agree on it?"** before it is written anywhere. *This node alone*: the node's own database file. *Every data node, identically, derived from an ordered log*: the replicated estate, which ONLY a state log's applier writes. *The whole company, now*: the coordination store. *Whichever node holds this seat, current value only*: a compacted changelog (ADR-0014). *A replicated row names it and one store the fleet shares keeps its bytes*: the object store (ADR-0026) — and a table that names an object is declared in `internal/objstore/references`, or the collector deletes its files. "It has always been in the store" is not an answer. The stream is the write-ahead log and the SQL estate is derived, never the reverse (ADR-0002, 0003, 0004); `internal/store`'s estate gates refuse a table that skips the question
- **A three-valued answer is `(value, error)`**, never a bool: "held", "definitively not held" and "the store could not be reached" are three facts (see `internal/coord`)
- **IDs are `uuid.UUID`**, timestamps `time.Time` in UTC, durations `time.Duration`; a config field holding seconds is named `…Seconds` and converted once, at the edge
- **Enums are a named string type** with typed constants and a `Valid()` method, so an unknown value off the wire is a value rather than a panic
- **Concurrency**: a goroutine's lifetime belongs to whoever started it, and every one has a way to stop. Channels for handoff, a mutex for state; `sync.OnceValue` over a `sync.Once` plus a variable. Everything runs under `-race`
- **Comments explain WHY, briefly**: the decision, and why the obvious alternative is wrong, in the fewest lines that keep a reader from undoing it — every reader of the code pays for every line beside it, every time. A comment block outside a package doc stays within 12 lines. The argument behind it is written once, in the package doc, where `go doc` will find it (or in an ADR when it binds more than one package), and the comment points there; history stays in the commit, the pull request and the issue, and a rule is stated where it is decided, not again where it applies. `internal/commentgate` holds the bound, with an inventory of older code that only shrinks

## Tech Stack
- **Go 1.27+**, pure Go: the module pins its own toolchain (`GOTOOLCHAIN=auto` fetches it), and `CGO_ENABLED=0` builds every release target. **The standard library first** (`net/http`, `log/slog`, `context`, `encoding/json`): a dependency has to earn its place against what `std` already does.
- **Turso** (`turso.tech/database/tursogo`) is the embedded store and the ONLY driver, and **NATS JetStream** the event stream and the ONLY broker — there is no second driver, no Pulsar backend, and no setting to select one. Their constraints are in `.claude/rules/build-and-release.md` and `.claude/rules/broker.md`.
- **Harnesses are the only LLM backend** — every model call runs a vendor's own harness as a subprocess (Claude Code, Codex, OpenCode). There is no HTTP client to a model vendor and none is to be added (`docs/concepts/llm-backends.md`, `.claude/rules/harnesses.md`).
- `github.com/modelcontextprotocol/go-sdk` for MCP client and server; **OpenTelemetry** (`go.opentelemetry.io/otel` and the OTLP trace exporters) for tracing, configured from the standard `OTEL_*` environment rather than Tier A, the provider always installed and only the exporter conditional, because a trace id is an event-store column before it is an exporter's concern; `github.com/openai/openai-go` as the embeddings client (`providers.embeddings`) and only that; **official vendor SDKs** for integrations where one exists, a thin typed client where one does not (Mattermost, GitLab, Confluence); `github.com/aws/aws-sdk-go-v2` for the object store's `s3` backend and the AWS integration's IAM and STS calls and only those (request signing, the regional endpoint rules, the credential chain and its standard retryer; its HTTP goes through `httpx`, and Roles Anywhere's CreateSession and AWS's MCP Server are signed by `internal/sigv4`, since the SDK covers neither — the default object backend, `nats`, needs nothing beyond the broker); **YAML** via `gopkg.in/yaml.v3` for config parsing.
- **Gitlet runs real upstream git** (≥ 2.55 on a Gitlet node, ≥ 2.40 for a client; ADR-0087), and the suite runs the git `scripts/git-pin.env` pins, never the machine's (`.claude/rules/gitlet.md`).
- **`testing`** — the standard library's, with no assertion framework. Table tests where the cases vary, named tests where the reasoning does.

## Package Layout
- `cmd/crewlet/` — the one binary. Every command the switch dispatches must appear in `usage()`: nothing connects them, a test asserts it (`.claude/rules/cli.md`).
- `internal/` — everything else, mapped package by package in `internal/README.md`. Nothing here is importable from outside the module: the engine has no stable Go API, only a CLI, a config format and a wire protocol.
- `dashboard/` — the dashboard's SOURCE (React 19 + TypeScript, built by Vite); `make dashboard` builds it into `static/dashboard/`, which is committed, embedded and NEVER hand-edited (`.claude/rules/dashboard.md`).
- `examples/` — the Nimbus example company, a working two-tier config. `docs/` — product documentation, published to docs.crewlet.ai. `skills/` — FOUNDER-facing authoring skills for an AI assistant (not `.claude/skills/`).
- `schema/` — GENERATED JSON Schema for both config tiers (`crewlet schema <tier>`; a test regenerates and compares). Never hand-edit: change the Go models.
- `scripts/` — the two vendor dev-loop bootstraps, the DCO gate, and the git and Chromium pins the engine and the suite run (`.claude/rules/dependencies.md`).

## Checks and Tests
- **Before committing, ALWAYS run `make check`** and fix what it reports: it is every gate CI runs on a pull request (the list is in `.claude/rules/testing.md`; it needs GnuPG, `zip` and `unzip`, `node`, and a prebuilt `golangci-lint` built with a Go no older than `go.mod`'s). Repair formatting with `make fmt` (`gofmt -s -w`, which clears both gofmt standards) or `golangci-lint fmt` handed the captured list (which also fixes the import grouping) — never plain `gofmt -w`, which cannot fix what the linter reports — and list unformatted files with `gofmt -l` over `go run ./internal/sourcetree/gofiles` — never `gofmt -l .`, which enters every nested checkout under `.claude/worktrees/`.
- **Run `make test` and `make test-solo`**, never a bare `go test ./...`, which runs the cluster-forming packages beside everything else and bypasses `internal/skipgate`. One package with `go test ./internal/foo/` is a fine fast loop. Every package runs under the race detector with `-count=1`. The packages that stand up a multi-member broker run alone in `make test-solo`, so a run of `make test` by itself has NOT exercised the fleet.
- **A skip is not a pass** — both test targets fail the run on a skip not declared in `internal/skipgate/allowed.go`. `internal/store`'s capability cases skip DELIBERATELY, and that is the mechanism rather than a gap: a feature Turso announces but does not reach Go yet turns into a passing test the day it lands.
- **The Makefile is the command CI runs.** The two test jobs call `make test` and `make test-solo` themselves, so editing `GOTEST`, `GOTESTBUILD` or `GOTESTRUN` changes CI; every other job inlines its own command, mirroring its target by hand, and nothing checks that they agree. Change a target and its `ci.yml` step in the same commit, and give a new target its `## ` help line.
- **Every subsystem needs tests, and a test names the invariant it protects**, not the function it calls. Tests never call real LLM APIs (use the fakes in `internal/providers`), and a fixed wait decides nothing: a claim rests on a signal, never on wall-clock time having passed (`internal/fixedwait`). **A test that cannot fail is worse than no test** — break what you wrote on purpose and confirm the suite goes red.

## Documentation
Every change to code, config, or behaviour includes its documentation; docs are part of the deliverable, and stale docs are worse than none. A change to a public API, config format, CLI command, data model or behaviour updates the relevant pages in `docs/`; a new feature gets a page or a section; a renamed or removed name is fixed everywhere it appears (grep for it). An architecture change updates `docs/concepts/`, and a quickstart-affecting change `docs/getting-started/quickstart.md`. If in doubt, update them: a one-line config rename still needs its docs. How the pages are held together is in `.claude/rules/docs.md`.

## crewlet-operator, Releases and Dependencies
- **`crewlet/crewlet-operator`** (public, MIT) runs Crewlet companies from Kubernetes custom resources and consumes this engine's contract; its suites run this repository's `main` as `ghcr.io/crewlet/crewlet:main` publishes it, never a pin, so an engine change it has not followed turns its next run red. A change to anything it renders, calls, copies, runs or links needs its companion change there, delivered with this one. The summary and the pull request description link the companion change, or say in one line why there is none (`crewlet-operator: none — internal to the turn loop`); most changes need none and must not get one. `.claude/rules/operator.md` has the surfaces and the rules, and loads with the files that hold them.
- **The tag is the version** — nothing in the tree records one: goreleaser stamps it into `internal/version.value` at link time, and a literal version constant is never added back. Semver: the minor number moves for features, the patch number for fixes. `RELEASING.md` is the runbook; `.claude/rules/build-and-release.md` holds the rest.
- **Pick the newest release, then pin it exactly** — established from the registry rather than memory, written as a literal (`4.2.4`), never `latest` or `@main`, which nothing moves. A version held back on purpose carries its reason at the pin. The shipped examples float instead (`@latest` at most), except a server a bundled tool skill triggers on by tool name; a tool server a docs page, a skill or the curated MCP catalogue launches is held to the exact release `internal/config/toolservers_test.go` and its catalogue entry record; and a new dependency surface ships with its `updates:` entry in `.github/dependabot.yml`. Dependabot, its workflows and the git and Chromium pins are in `.claude/rules/dependencies.md`.
