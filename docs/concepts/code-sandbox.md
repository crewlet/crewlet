# Code Sandbox

> **v1 status.** Both backends run — `e2b` (a remote VM per run, on the vendor
> cloud or a self-hosted cluster) and `local` (the engine host, as a process
> tree or in a container) — and the engine-fronted OTLP receiver is wired.
> `providers.sandbox` is a **catalogue** of cells, required once a company has
> an agent seat and a `providers.llm` entry: every agent seat's executor runs in
> one of them, placed by the `run_in` of the `providers.llm` entry the launch
> picks, else `providers.sandbox.default_run_in`.

Every agent seat's **executor** is its coding CLI's own agentic run — Claude Code or OpenCode — in a **box**: a remote VM, a container, or a directory on the engine host, each with a shell, a filesystem and a git checkout ([ADR-0066](../../adr/0066-every-executor-is-its-coding-clis-own-run.md)). This page is about where that run happens and what becomes of it. The [turn engine](turn-engine.md) launches it with the turn's ask as its brief and the seat's system prompt as its standing instructions, and the turn **parks**. The run does the seat's work — code and everything else — with its own shell and editor, calls the seat's tools over the [tool bridge](#the-tool-bridge--a-seats-own-tools-from-inside-a-box), and ends by calling `submit_work` there. Its collection, minutes or hours later and possibly on another node, re-enters the **same turn**, where the engine's delivery check and the reviewer judge what it did; a reviewer's `self_iterate` launches it again. The engine's own tool loop runs only the phases around it, on the engine host: the reviewer, delegated workers, the onboarding pass and the side passes (see [Where the CLI runs](llm-backends.md#where-the-cli-runs)).

This is how a Crewlet agent answers a message, works a ticket, implements a feature, makes tests pass or reproduces a bug: one run, with a shell and a checkout. **The run is fully permissioned in every cell** — Claude Code under `--permission-mode bypassPermissions`; OpenCode with a `permissions` rule list that allows every action (`{"action": "*", "resource": "*", "effect": "allow"}`) and denies only `question`, since `ask_and_wait` asks the seat's people instead — because a headless run has nobody to answer a permission prompt, and a gate left to ask would stall it or refuse the step. The **cell** decides what that run can reach: `container` and `e2b` keep it off the engine host, and `direct` runs it on the engine host as the engine's own user (see [Where a run happens](#where-a-run-happens)).

The moving parts live in `internal/sandbox/`: the provider, the manager, the coding-agent runners under `codingagent/`, the waiters, the coordinator, the pending store, `launch.go` (the plumbing between an executor's launch in `internal/engine/agentrun.go` and its detached run), `boxhost.go` (which keeps a `direct` or `container` box with the node that launched it, [ADR-0065](../../adr/0065-a-local-box-is-driven-by-the-node-that-launched-it.md)) and `answerseal.go` (which seals a person's answer onto the run's row).

## How a coding task runs

Every turn's executor is a run like this one. Its box is placed by the `run_in` of the `providers.llm` entry the launch picks, else `providers.sandbox.default_run_in`, and reads the seat's `role.sandbox` `setup`, `env` and `mcp` (see [Where a run happens](#where-a-run-happens)).

```mermaid
sequenceDiagram
    participant T as Turn (runner)
    participant E as Engine
    participant W as Waiter
    participant B as Box
    T->>T: open the Execute phase: the seat's surface and prompt, agent_phase_started
    T->>E: launch the executor, from the turn's pinned epoch
    E->>E: the turn's fence, the budget floor, the chain member and its cell
    E->>E: open the run's row as launching: the seat is held from here
    E->>E: open the bridge session under the job's id
    E->>B: continue the turn's box or provision one, apply setup, start the CLI (detached)
    E->>E: publish executor_launched
    T->>E: the turn parks: its state is written, the row becomes running
    Note over E: the seat is busy: its inbox is held, so nothing is fetched
    B->>B: clone, code, test, push, open the PR or MR
    B->>E: the seat's tools over the bridge, ending with submit_work
    E->>W: the submission nudges an immediate poll
    loop every 15 s, the fallback
        W->>B: keepalive and completion check
    end
    W-->>E: the job finished: executor_finished
    E->>B: claim the row, collect the result, pause the box
    E->>E: charge the run's spend, publish its executor_collected record
    E->>T: resume the same turn with the run's calls and its submit_work
    T->>T: the engine's delivery check, then the reviewer
    alt the work is accepted
        T->>E: the turn settles
        E->>B: reclaim the box
    else self_iterate
        T->>E: launch again, continuing in the paused box
    end
```

The details, each load-bearing:

- **Launch → park.** Every launch takes the same steps, in order (`internal/engine/agentrun.go`): the turn's own fence, so a seat this node no longer holds, or one a person stopped, launches nothing; a sandbox runtime on the node, the turn's catalogue and a bridge its box can reach; the [budget floor](#budgets); and the member of the seat's executor chain the run goes to — the first whose CLI has a runner and is not sitting out a spent plan ([The executor's run in a box](llm-backends.md#the-executors-run-in-a-box)) — with its cell. Every fact comes from the turn's pinned epoch, so a revision applied mid-turn is the next turn's. The coordinator then opens the run's row as `launching`, the job's bridge session is opened under the job's own id, the box is continued or provisioned and set up, and the CLI starts as a background command. The row is a durable record in the [coordination store](coordination.md): the task the turn was working on, both conversation values — the conversation identity a later answer is matched on and the resume reports back to, and the inbox partition the triggering delivery arrived in — the trace context, the `providers.llm` entry the launch picked and its model, the node that launched it, whether the turn owes anybody an answer, and — where a colleague's [A2A ask](event-system.md#ephemeral-a2a-channels-internala2a) woke the turn — that ask's channel, question, chain and trace, which the frame that ends the turn replies to — or, for a run lost under its turn, the run's ending, which tells the asker so. The executor phase returns parked and the turn's segment ends. The seat is **busy from the write that opens the row** — before the box is provisioned, and so before the turn can end and the seat's consumer move on to its next message. The launch also publishes `executor_launched` to the seat's control topic, and processing it recounts the seat from the pending store's own list of the seat's active runs, which is what carries a busy seat across a restart or a handoff; but nothing waits for it. A launch that fails after opening the row (no box, a job that will not start, a parked state the turn cannot write) gives the seat back as it ends the row, and a launch refused before it closes its phase as failed — or as stopped, where a person stopped the seat — so no screen shows a phase that never ends. Nothing is parked in memory; everything the collection needs is in the row.

  **The record lands in two writes, and the state says which one it is at.** The turn's parked state (`internal/agent/execstate`: the round, the closed rounds, the surface and the skills it had loaded, the task, what it was asked and by whom, the items it wrote, the spend no segment has paid yet, the turn's deadline and the context it froze at its start — no conversation, since there is no engine loop to re-enter) is written by the turn as its frame unwinds, *after* the launch returns. So the launch opens the row as `launching` and the unwinding turn writes its state, flipping the row to `running` in the same compare-and-swap. In between, the job is already executing and the row has nothing to resume — so **nothing polls or claims a `launching` run**: a completion claimed in that window would find no turn to resume and would have to fail a run that finished. The window is milliseconds on an idle host and hundreds of milliseconds on a loaded one, and a trivial run is exactly the one that fits inside it.
- **A seat whose run is working takes no other work, and that is every turn.** While one of a seat's runs is running (or the seat owes an answer's resume, or a reply a run let go of), the seat **receives nothing at all**: not new work, not a colleague's message. And **no person's answer to a different run of the same seat is resumed meanwhile**, whether that answer is a chat reply or one given [by naming the run](#answering-a-parked-run). That is the rule, not a cost of the mechanism: an agent in the middle of its work is busy with it, and it takes up the next thing when this one is done, as a person would; resuming a second run beside the first would put two of the seat's turns in flight at once, each acting for the seat without seeing the other. So **each seat runs at most one executor run at a time**. A chat reply waits on the broker with the rest of the mail and is offered when the busy run **settles or parks on its own question**, which for a long job can be hours; an answer given by naming the run travels on the seat's control topic instead, is recorded on its run at once, and its resume waits for the busy run and then runs ahead of the held mail. Nothing is lost while either waits (the reply keeps its place and the question its anchor), and a parked run whose box outlives `pause_ttl_seconds` in the meantime re-seeds from its branch when the answer arrives.
- **Busy while it runs.** While a run HOLDS the seat, the seat's inbox is **held** (the `sandbox` hold): the coordinator takes it as the launch opens the run's row — and when a node that takes the seat over recovers a run still going, before the mailbox opens — and lifts it when the last such run settles or parks on a question. Held, nothing is fetched: the mail waits on the broker in order, nothing is held against a broker ack window during an hours-long run, no new turn starts and nothing runs at all until the run is done. A person's chat reply to *another* of the seat's runs waits with the rest of its mail and is offered when the run settles or parks; an answer by turn to one travels on the seat's control topic, is recorded at once, and its resume waits for the run and then runs ahead of the held mail. A colleague's [A2A ask](event-system.md#ephemeral-a2a-channels-internala2a) waits with the held mail as a chat reply does, and its channel is not closed under it: the idle sweep spares a channel whose seat's inbox is held, as it spares one whose ask a run's record carries. A run parked waiting on a human answer holds nothing — the seat works as usual, and its deliveries are offered to that question before they become turns (see [Mid-run clarification](#mid-run-clarification-ask_and_wait)).

  A delivery that reaches a held seat anyway (it raced the hold, or the queue refused to take it) asks for the hold again and is deferred, keeping its place at the head of the inbox — never requeued behind the seat's newer mail.
- **Completion → resume.** The resume starts a turn, so it asks the node's admission first, as every turn does ([ADR-0063](https://github.com/crewlet/crewlet/blob/main/adr/0063-every-turn-on-a-node-passes-the-nodes-admission.md)): the seat owned fresh, a slot under `node.max_concurrent`, and no drain. It asks **before the claim**, so a node that refuses leaves the run exactly as it was, and the completion is handed back by the condition the refusal names: a draining node defers it, which quiesces the seat's control topic for the rest of the drain and leaves the completion at its head for the seat's next holder, while a condition that clears by waiting (the seat's ownership not yet proven again after a store blip) acknowledges it, spending none of its deliveries, because the waiter that drives the run's box announces a finished run again on every poll until a node claims it. The node also keeps the refused completion and re-fires it **the moment the condition clears**, on the same signal that wakes an answer waiting on that condition, so the resume waits for the condition and not for the poll; a clearing nothing signals is caught by that waiter's next poll, at most **15 seconds** later. Whichever arrives first claims the run, once. Both waiters keep running through a drain, so that waiter's keepalive keeps the box meanwhile: the fleet's for an `e2b` box, and for a `direct` or `container` box its host's own, which announces the run to the seat's next holder, who reads the box back through that host ([two waiters](#durability-completion-and-observability), [ADR-0065](https://github.com/crewlet/crewlet/blob/main/adr/0065-a-local-box-is-driven-by-the-node-that-launched-it.md)). The admission is held until the resume and its settle return. The completion event is claimed **at-most-once** (an atomic status flip on the row) and **only for the job it reports**: every launch gets a new id on the row and the completion carries it, so a duplicate that arrives after its job parked on a question, or after a relaunch started the next job, claims nothing. The result is collected, tokens are post-accounted once per run (see [Budgets](#budgets)), each launch is published once as a record of its own (see [each launch is published as its own record](#a-run-is-bounded-by-its-rounds-each-launch-is-published-as-its-own-record)), and the turn is rebuilt from its parked state: the surface and skill-guard state as the run left them (as the launch recorded them, with every tool the run activated and every skill it loaded over the bridge replayed onto them, so the collected phase's record lists the tools the run held as `tools_available`, apart from those it could still have discovered, `tool_catalogue`), the call log seeded with every call the turn and the run made, each read by its canonical arguments — the run's bridged calls in the order the bridge admitted them — and the run's `submit_work`, replayed from the bridged calls on its row, taken as the round's work. A run that never submitted is rescued as `incomplete`, never read off the prose it ended with. The engine's delivery check and the reviewer then judge it in the same turn (`Runner.Resume`). The same `turn_id` continues, so the whole sequence renders as one turn on the dashboard, and so does the round count: the collection is the round the run was launched in, so a launch and its collection share one `turn_engine.max_iterations`. A failed resume dispatch hands the claim back, to the status it was taken from, so the redelivered completion can retry, and the parked turn is never lost. That includes a resume a drain interrupts: the hand-back does not inherit the drain's cancellation, so the seat's next owner resumes the turn rather than reaping it as abandoned. The one exception is a resumed turn that broke after it had already written outside the engine (pushed a branch, commented on an issue): a retry would repeat those writes, so the run is settled instead, its box reclaimed and its record deleted, and the seat is freed. Otherwise it hands back only the claim it took: when the resumed turn has already relaunched its executor and the relaunch started another job, or the seat's next owner has reaped the run as abandoned, the row is left as it stands, because the relaunch replaced the job a retry would collect and the reap has already ended the run. **The seat stays held through the resumed turn**: a run claimed for its resume is `resumed`, which holds the seat, and it is counted so until the resumed turn returns, when the seat is recounted from the store. It used to be uncounted just before the resumer ran, which lifted the seat's inbox hold for the whole resumed turn and let the seat's next mail start a second turn, and a second job, beside it. And a seat runs one turn at a time on its node whichever road the turn comes by (`node.ErrSeatBusy`): a resume that finds the seat mid-turn waits for it, holding nothing, and one that is admitted holds the seat's inbox until it returns, so the mailbox fetches nothing meanwhile and spends none of its mail's deliveries.
- **What the resumed half writes under.** The resumed turn's tracker, knowledge-base and chat writes derive their operation ids from the same unit of work as the first half's, minted at the instant that work began, so a first-half write the second half repeats — the retry an `unknown` asks for — lands once. The exception is a resume that runs **more than twenty-nine days after its work began**: the [operation ledger](../guides/replication.md#what-a-retry-is-judged-by-the-instant-its-operation-was-minted) keeps each row thirty days, and an operation minted before what a node's ledger swept, whose row is gone, is answered `unknown` and never published — so minted at that start, every write the resumed half made would be lost on every data node. Such a half is **rebased**: it mints its ids at the attempt instead and records that instant in the fleet's coordination store under the unit of work, logged as `turn_rebased`; the price is that a first-half write it repeats is written a second time — except a work-item comment, a created item and a created view, whose ids are the keys of their rows and are derived as the work began, so the first half's is found and answered from its row rather than made again. **Every attempt is judged against its own clock.** A resume that fails is retried — by the completion coming round again, or by the person's next answer, which can be weeks later — and each retry is judged afresh, never held to a decision an attempt took while the start still looked recent. A later attempt **inherits** a recorded instant while it is within the same twenty-nine days of it, so a failed resume retried on this node, on the seat's next owner or after a restart derives the ids the attempt before it derived, and so does the resume of the turn's next launch — a reviewer's send-back, or a run carried on with a person's answer — whatever the earlier attempt or the earlier half wrote is not written twice. The line is drawn a day short of the thirty so that no sweep passes the instant while one attempt is still working. A turn with no unit of work (a scheduled fire) seeds its ids from its run and mints them at the run's start, and is rebased by the same rule, under its run. The same rule covers a trigger dispatched long after it arrived — see [Turn Engine](turn-engine.md#a-turns-two-identities).
- **Reuse across launches.** On collect the box is **paused** (snapshotted), not destroyed. A relaunch in the same turn — a reviewer's `self_iterate`, or a person's answer carrying a parked run on — **continues in it**, checkout and disk state kept and provisioning not applied again, when the job that used it is over, the member the launch picks runs the same coding CLI in the same cell, and the box is one this node can reach: any `e2b` box, or a local one on this node's own host (`PriorBox.ContinuesIn`). A run carried on with an answer also continues its CLI's own session there; a send-back starts a fresh CLI run in the kept checkout, told what the rounds before it did. Otherwise the box is **reclaimed through its own cell** before the fresh one exists (`sandbox_prior_reclaimed`), so a fallback onto a member in another cell moves the run without leaving its last box behind; a box that cannot be reattached is reclaimed and replaced (`sandbox_reuse_failed`), the work re-seeding from the pushed branch; and a local box on another node's host — the seat moved since the last launch — is left to that host, whose waiter reclaims it (`sandbox_prior_left_to_host`, see [A local box is the node's that launched it](#durability-completion-and-observability)). Whichever ending the turn reaches reclaims the box its row names. The two jobs are told apart by the launch id, not the row's status: a new job that finishes, or parks on a question of its own, before the resumed turn has returned keeps its box and its tail.
- **Publishing a build from the box.** `create_artifact` and `publish_artifact` name a box as a source — `source: {sandbox: "dist"}` for a directory as an artifact's whole file set, `from_sandbox` for one file, each relative to the workspace — and the engine serves one only to **the run working in it**: the run's own call, made over its bridge while its record reads `running`, so the run publishes its build when it says the build is ready. A [worker](turn-engine.md#workers) the run delegates to never makes that call: both tools write to a surface people read, and a worker is granted no such tool. It attaches that box as a reader — never resumed, and a remote box's kill timer left where the waiter keeps it — lists the directory through the box itself with links never followed, holds every listed path to the workspace and the published-path grammar, and streams each file through the [artifact upload pipeline](../guides/tools-and-mcp.md#artifacts), which reserved its bytes first and reads them back verified before the version is decided. The box is never handed an upload URL or a credential. A seat's call that finds no such run — none launched yet, parked on a question (its job paused, which a read would wake), collected, another seat's, or torn down — is refused `not_running`, and nothing is published; so is one served on a node other than the one that launched a `direct` or `container` box, which only that node reaches ([ADR-0065](../../adr/0065-a-local-box-is-driven-by-the-node-that-launched-it.md)). A caller that is not an agent seat — a person, or their own assistant, calling through the operator catalogue — has no such run and is refused `forbidden`; a seat's call on a node that runs no sandbox is refused `unavailable`. A collected run's resumed segment calls no artifact tool — its reviewer holds one submission tool — so a running record is the only one a box source is read for. A `from_sandbox` path that names no file (one that's missing, a directory or a link), and a `sandbox` source that names no directory (one that's missing, a file or a link), are refused `invalid`, for the seat to name another. A workspace that's gone from the box is refused `not_running`, for the seat to build again, and a directory the box couldn't walk whole (a directory under it the box's user can't open, a read error) is refused `conflict` rather than published as the part it could read: the listing reads `find`'s own exit, and passes the directory to it as `./dir`, so a name that reads like one of its options is still a directory. A box its provider can't read right now is told by the [same classes](#when-a-run-does-not-start) a launch is, with a wait offered only where one helps, and so is a listing or a file check the box itself ended: one it timed out or killed, or whose container runtime failed on its own side, is the box not answering, and one whose box can't run its shell, `find` or `head` is its image, a `configuration`.
- **A settled run has no record.** When a run ends, whether its turn finished, a person stopped it, or it failed, its box is reclaimed first and then its record is **deleted** from the coordination store. The record's bucket has no age (a parked run can wait days, and an age would reap the only thing that knows a billed box exists), and the completion poll and every seat recovery read all of it, so a finished run kept there would be read on every one of those passes for the life of the deployment. What a run ended as is recorded elsewhere: the resumed turn's own phase events, an `executor_failed` event naming why it was lost, or an `executor_stopped` event naming who stopped it. The box goes first on purpose: a record that outlives its box is reaped by the seat's next recovery, while a box that outlived its record would be named by nothing.
- **An ending is decided before it is done, and announced exactly once.** Ending a run is several effects in several systems — a person's reply handed back to the seat's inbox, the box reclaimed, the loss announced, the record deleted — and a node can stop between any two. So the ending is first **decided on the run's record** (`ending`), in one compare-and-set under the ending's terms: what it announces, under an identity of its own, and whether a person's reply goes back. From then on the record takes **no other write** — no claim, no take of an answer, no hand-back of a claim, no relaunch, no new answer, no park — so nothing can move the run off the ending, and whoever reads the record next (this node's retry, or the seat's next holder) finishes **that** ending from wherever it stopped, never one of its own. The loss is announced (`executor_failed`) **before** the record is deleted, under an id derived from the run and its ending and the instant it was decided, so a repeat after a crash is the same event to the event store — whose key is that (time, id) pair — and to the fleet's reads, which merge rows on it. The announcement used to be made only after the delete: a delete that landed and reported a failure, or a node that stopped between the two, left the loss announced by nobody, and the seat's next holder, finding the claim the delete had not taken, announced it as `abandoned_tail` whatever it had been ended for. A broker that refuses the announcement keeps the ending, and the seat's mail waits behind it until it is made. **The box goes after the decision, never before it.** An ending is made by a node that read the run and decided it is over, and that read can be stale: a node that lost the seat while settling a claim it had taken used to kill the box first, off its own read, and only then had its ending refused under the seat's next holder's lease — after that holder had given the claim back to its answer, so the run it then resumed had lost its checkout while its record still named the box. The reclaim now rides the decided ending, so the store checks the ending's lease against the run as it stands before anything is killed, and an ending refused there leaves the box to the run's holder; whoever finishes the ending — this node or the seat's next holder — reclaims the box the record names before deleting it. A node that loses the run that way says nothing about it either: what became of the run, and of a reply on it, is announced by whoever holds it now.
- **A person's stop is an ending too, and never a loss.** A [pause with `stop_running`](agent-runtime.md#pausing-a-seat) ends the seat's runs that are launching or running, at once, on the node that holds the seat — when the pause lands, when the node next reads every pause, or when it acquires the stopped seat. The stop is decided on the run's record like any ending, with **who stopped it** recorded in the same write, and only while the run is still that job in one of those two statuses: a run whose completion was claimed first is a resumed turn, which the turn's own fence stops at its next round, and whose call that was out as the stop landed, if it comes back refused for a limit or the seat's budget, is settled as stopped there and then rather than waiting for the limit's instant or the window's turn, and parks nothing; so is a run back in `running` whose job a collection already read — its resume held by the seat's budget, held by its node for a model's limit, or handed back for a retry — which the store refuses a stop of, because its job is over and its spend is the resume's to charge, once, and whose wait the stop ends instead (its hold lifted, a completion its node kept re-fired, and a stopped seat's completion admitted past its budget and its models' limit, which its stopped turn never reaches), so that turn is closed now rather than when its condition would have cleared; and a run parked on a person's question does no work and stays parked behind the pause. Finishing it closes the run's tool-bridge session first — nothing it does after that acts as the seat — then reads what the run had spent off its box, charges it to the token counters and publishes it as the launch's own `executor_collected` record (noted as stopped, not failed), all recorded on the row so a repeat after a crash neither charges nor publishes twice; then the box is reclaimed and the stop is announced as `executor_stopped`, under an id derived from the run and its ending exactly as a loss is. The turn that was parked on the run is closed as stopped — `agent_turn_stopped` and a completion carrying `stopped` — under identities derived from the same ending, so the seat's next holder finishing a stop this node could not finish closes the turn once. A run stopped while its turn was still launching it is closed by that turn as it unwinds: its park is refused, and it ends as stopped — from the stop's own decision, which the node keeps for that turn, so a seat resumed before the turn unwinds does not turn the stop into a park with nowhere to go. The completion poll leaves a run whose ending is decided alone, so it never keeps alive a box the ending is reclaiming.
- **Review sees the whole turn.** Every call the run made over the bridge is recorded on its row in the order it was admitted, and joins the turn's record after the closed rounds' calls when the turn resumes, so the delivery check and the reviewer's evidence see what the run did as the seat. The CLI's own editing, commands, tests and commits happen inside the box and are in **no** log, and every review is told so: the reviewer judges that work on the executor's report and on the branches and pull requests listed under `## What the agent delivered`, and a missing shell or test call is never fabrication.

There is deliberately no synchronous "block the turn until the run finishes" shape: a turn that held its concurrency slot and its broker message for a real run's length would trip the inbox ack window and the shutdown drain. A short run in the detached model simply completes fast.

## Configuring it

One block is required and one is optional. **`providers.sandbox`** is the catalogue every agent seat's executor runs in, and a company needs it as soon as it has an agent seat and a `providers.llm` entry: without it the company is refused at `providers.sandbox`, once, naming the first such seat and how many more, and suggesting `local: {}` with `default_run_in: direct` (the engine host) or `e2b:` (a remote box). A company with no agent seat, or an org chart written before its credentials (no `providers.llm` entry yet), needs none — it holds every seat's work until a revision adds a model, and the catalogue with it. A seat's own **`role.sandbox`** is optional, and only adds what that seat's box reads.

### Engine provider — `providers.sandbox`

A sibling of `providers.llm`, live-reloadable, with secrets kept as `${VAR}` references and resolved at construction time:

```yaml
providers:
  sandbox:
    # THE CATALOGUE: which boxes exist. Configure either, or both.
    e2b:
      api_key: "${E2B_API_KEY}"   # required whenever e2b: is present — the API
                                  #   authenticates every call
      domain: ""                  # set → self-hosted / local cluster; empty → the cloud
      template: ""                # empty → the prebuilt template for the coding agent;
                                  #   ALSO how a remote box is sized (below)
    local:
      state_dir: ""               # empty → $CREWLET_SANDBOX_LOCAL_HOME,
                                  #   else ~/.crewlet/sandboxes
      image: ""                   # required only where a run is placed in a container
      runtime: ""                 # auto | docker | podman; empty → auto
      network: ""                 # the container network; "none" cuts the box off
      run_args: []                # how a container box is SIZED
      runtime_env: {}             # extra environment for the docker/podman CLI
                                  #   itself, never the box (below)

    default_run_in: e2b           # direct | container | e2b — where a run on a
                                  #   providers.llm entry naming no run_in happens
    default_timeout_seconds: 900  # box TTL / keepalive window — NOT a run cap (below)
    default_pause_ttl_seconds: 1800     # omit for this default; 0 = never pause. how long a blocked run's paused box is
                                        #   held before the reaper takes it
    default_max_turns: 96         # agentic-round cap for one executor run; unset = 96, 0 = uncapped
    commit_attribution: true      # credit Crewlet as co-author on a run's own commits;
                                  #   unset = true, false = credit nothing (below)
    setup: []                     # engine-wide provisioning steps (see Setup steps)
```

- **The block is a catalogue, not a mode.** It says which boxes *exist*; the `run_in` of each `providers.llm` entry, else `default_run_in`, says where a run launched on that entry goes. This is the shape's whole reason: a company has exactly one `providers.sandbox`, so a company-wide `type:` would choose the engine host for the run that needs the operator's own subscription login *and* for the run whose work must never touch that host. Those are different decisions about different work, and an operator who wants both writes two entries and points each seat at the one that is right for it. **The block may be left out** only by a company with no agent seat, or with no `providers.llm` entry yet: an absent block says "no boxes", and a company whose agent seats have a model and no box to run in is refused.
- **An empty block is refused.** `providers.sandbox: {}` configures nothing: every agent seat's executor runs in one of its cells, and it has none to run in. Give it `e2b:`, `local:`, or `fake: true`.
- **`default_run_in` is required unless the catalogue names exactly one cell — or nothing would read it.** `local:` alone is **two** cells (it serves both `direct` and `container`), and there is deliberately no implicit answer: `direct` runs the coding agent as the engine's own user, and `e2b` mints billable VMs, so neither may be chosen for an operator who did not say which they meant. Only an `e2b:`-only catalogue (and `fake: true`) resolve on their own. What makes the default *required* is something that would fall to it: an entry some agent seat's executor can launch on — a `claude-code` or `opencode` member of its executor chain — that names no `run_in`. A company whose every such entry names its own cell needs no default at all — that is the shape the catalogue exists for — and validation refuses the silent entry **where it is written**, offering `default_run_in` as the other remedy.

The one thing an ambiguous catalogue may not do is reach **nothing at all**: a default or an entry's `run_in` has to name some cell. A backend is built only for a cell something reaches, so a catalogue nothing names builds none — a block that reads as configuration and configures nothing, which is the reason an empty block is refused too. Every catalogue that resolves a default reaches it, precisely so a seat added later has somewhere to go.
- **`api_key`, `domain` and `template` live under `e2b:`**, where they can only mean what they say — a `domain:` at the top of the block used to read as a cluster address beside `type: local` and configure nothing. The key is **required** whenever `e2b:` is present, including against a self-hosted cluster: `domain` changes *which* API is talked to, never whether it authenticates.
- **`local.image`, `runtime`, `network`, `run_args` and `runtime_env` are container-only**, and are checked against the cells your executors actually reach: an image is **required** when some run is placed in a container and **refused** when none is, because there it looks like configuration and configures nothing. Required unconditionally it would refuse a perfectly good direct-only company; unchecked, the seat's first run fails at container create, minutes into a turn.

- **`default_timeout_seconds` is not a run-time limit.** It is the box's TTL / keepalive window: the completion poll refreshes a running box's TTL to this value on every tick, so the clock never kills a live job. It is effectively the *orphan-reclaim grace* — how long a box outlives an engine that stopped heart-beating (a crash) before E2B reaps it — and the time after which a node that launched local boxes and stayed away is [taken for gone](#durability-completion-and-observability). A run is never stopped on its box's TTL. The one clock that ends a run is its **turn's** wall-clock cap, where the trigger carries one (a scheduled fire's `timeout_seconds`): it is written on the run's row as its deadline, the completion poll ends a run still working past it (`sandbox_run_past_deadline`), and the collection reads what the run did up to then, marked as cut off.
- **`default_pause_ttl_seconds`** bounds how long a run blocked on a human answer keeps its *paused* box. E2B holds a paused sandbox indefinitely — there is no provider-side TTL — and bills for the snapshot, so expiring it is the engine's job: past this age the completion poll [reaps it](#mid-run-clarification-ask_and_wait) and the run re-seeds from the pushed branch when the answer arrives. 30 minutes trades a bounded snapshot bill against exact resume for the replies that come back quickly; raise it if your teams answer in hours. `0` means never pause — the box is torn down the moment the run blocks, for zero snapshot cost — and *omitting* the key is how you take the 1800s default. The two are different settings and the field distinguishes them, which it did not before: read as a plain number, an explicit `0` was indistinguishable from an absent field and was quietly mapped onto the default, so a company that asked for zero snapshot cost was billed for every paused box for half an hour. Negative values are rejected here: an unbounded pause is the leak the knob exists to prevent. A *role* inherits this default by leaving `role.sandbox.pause_ttl_seconds` out entirely, and a negative role value is rejected for the same reason. Correctness never depends on the box: the durable state is the pushed branch plus the persisted row.
- **`default_max_turns` is the only round bound on every agent seat's turn.** An executor run is deliberately never stopped on its box's clock (see `default_timeout_seconds` above), and the completion poll refreshes a running box's TTL on every tick precisely so that it cannot be — so, outside a scheduled turn's own cap, nothing else stops an agent that is thrashing rather than working. This caps its agentic *rounds* instead, which is a measure of work done rather than time spent, and it covers both runners: Claude Code's `--max-turns`, and OpenCode's agent `steps`. **Unset, it is 96**: an executor run in the engine's own loop would stop at 48 rounds once its extension judge had granted all it could, for engine-tool work alone, and a run also does the shell, edit and test steps code work adds, each a round of its own — so twice that, room for a real task's reading, editing and checking, and still a wall a thrashing run hits within one turn. `0` is uncapped, which is how a company opts out of the bound; a negative value is refused. There is no companion budget cap — the fleet's own [token meter](agent-learning.md) already post-charges a collected run against the seat's budget, and a second ceiling denominated in the operator's dollars would just disagree with it. A role overrides this with `role.sandbox.max_turns`.
- **`commit_attribution` credits Crewlet on the commits a run makes as itself**, unless set to `false`: `Co-authored-by: Crewlet <noreply@crewlet.ai>` and `Crewlet-Run: <turn id>`, added by git rather than by the model. A person's commit the run amends, cherry-picks or rebases is never credited. See [Commit attribution](#commit-attribution).
- **Sizing is `template`, not a limits knob.** There is deliberately no `default_limits`. A box's vCPU and RAM are properties of its **template**, fixed when the template is built; the sandbox-*create* API accepts no resource arguments at all, and disk is not exposed in either place. An engine-side limits field could only ever be parsed and dropped — an operator setting `memory_mb: 16384` would silently get whatever the template had. To give agents bigger boxes, build a template with the resources you want and name it in `template:`; a `container` box is sized with `local.image` and `local.run_args` instead. There is no per-run or per-seat template field: sizing is a property of the backend, configured once, and the `Spec` field that used to sit in front of `e2b.template` was set by nobody while looking exactly like a wired knob.
- **Hot-reload, in every direction, with no restart.** The runtime under the catalogue — the coordinator that holds which seats are mid-run, and the completion poll — is a fact about the *process*, so it is brought up **once**, by the first company that reaches a sandbox cell: at boot, or at whichever apply brings one (the apply's `sandbox_runtime` stage — see [Configuration](configuration.md#the-engine-half)). That covers a node started with no company, the quickstart's own route, and a company that adds `providers.sandbox` later. The same apply prepares the seats the node **already** holds, which were taken before there was anything to prepare: each attaches its completion topic and recovers the runs recorded on it, exactly as a seat taken afterwards does on its way in, and a seat whose preparation fails is handed back so its next acquisition runs the whole of it. From then on a revision only **swaps the manager** under the runtime (`Coordinator.SetManager`), and three rules keep the runs already in flight whole across the swap:
  - **The poll follows the swap.** It asks the coordinator for its current manager on every tick, so a job launched after a reload is polled through the backend that made it, rather than through the catalogue the node first ran.
  - **A dropped cell stays reachable for what is already on it.** A run's placement is on its row, so a revision that removes a cell (`local:` taken out, say, while a `container` job is still running) carries that cell's backend as *retired*: a running job is still polled, collected and reclaimed, and a parked one still reaped, through the backend that made it — while no new box is ever provisioned there. An entry still naming the removed cell, or falling to it as the default, is refused at validation.
  - **Removing the block keeps the last manager.** A company validates with no `providers.sandbox` only when it has no agent seat or no `providers.llm` entry, and every launch reads the catalogue of its turn's pinned epoch, so such a company launches nothing; the runtime and its last manager stay for the runs still in flight, which still have to be finished through it.

  A catalogue that cannot be **built** is refused before anything on the node changes — on a node that runs no sandbox yet as on one that does — so a company whose agent seats' executors would launch into a box nobody can mint is never published.

### A seat's own box settings — `role.sandbox`

Every agent seat's executor is its coding CLI's own run in a box, so this block gates nothing and places nothing: the box is placed by the `run_in` of the `providers.llm` entry the launch picks, else `providers.sandbox.default_run_in`, and the runner is that entry's own CLI. What the block holds is what the seat's box reads beyond the engine-wide settings — `setup`, `env`, `optional_keys`, `mcp`, `pause_ttl_seconds` and `max_turns` — and absent, the seat's box gets the engine-wide settings alone. Any other key is refused as unknown.

```yaml
roles:
  - name: Senior Engineer
    handle: senior-engineer
    mcp_env:
      github: { Authorization: "Bearer ${GITHUB_APP_TOKEN_SENIOR_ENGINEER}" }
    sandbox:
      # pause_ttl_seconds:              # leave out → provider default; 0 → never hold a paused box
      # max_turns:                      # leave out → provider default (96); 0 → uncapped
      env:                              # env injected into this seat's runs, ${VAR}-expanded
        GITHUB_TOKEN: "${GITHUB_APP_TOKEN_SENIOR_ENGINEER}"   # this seat's own app (git-auth recipe + gh)
        NPM_TOKEN: "${NPM_TOKEN_SENIOR}"
        DATABASE_URL: "postgres://${TEST_DB_HOST}/app"
      optional_keys: [DATABASE_URL]     # expected to resolve to nothing at times: left out quietly,
                                        #   where any other unresolved key is left out and logged
                                        #   (sandbox_env_unresolved) as a gap in the run's environment
      mcp:
        servers: [github, atlassian]    # which of the role's MCP servers the coding agent gets
      setup:                            # per-role provisioning steps, applied after the
        - name: node                    #   engine-wide providers.sandbox.setup
          # No `corepack enable`: it writes pnpm's shim beside the Node binary,
          # and a setup command runs as the box's own account — `user` on E2B,
          # the engine's on the host for `direct` — which cannot write there
          # when Node was installed as root. `corepack pnpm …` needs no shim.
          commands: ["command -v corepack >/dev/null || { echo 'no corepack on PATH' >&2; exit 1; }"]
          brief: "Node and corepack are installed; run the repo's pinned package manager through corepack (`corepack pnpm install`), never a bare `pnpm`."
```

`role.sandbox.env` is where **external-service tokens are declared** — the engine names no tool-specific variable of its own (see [Credentials and the run environment](#credentials-and-the-run-environment)). By convention a seat points `GITHUB_TOKEN` / `GITLAB_TOKEN` at the *same* `${VAR}` as its `mcp_env` code-host credential, so PRs/MRs land under the agent's own identity — see [GitHub](../integrations/github.md) and [GitLab](../integrations/gitlab.md).

## Where a run happens

A `providers.llm` entry's `run_in` (else `providers.sandbox.default_run_in`) names one **cell** of the catalogue, and every executor run launched on that entry happens there. The three cells and the two backends behind them:

| `run_in` | Backend | Runs as | Isolates state | Isolates the **host** | Needs |
|---|---|---|---|---|---|
| `direct` | `local:` | the engine user, on the host | yes | **no** | the coding CLI installed on that host |
| `container` | `local:` | a PID in a Docker/Podman container | yes | yes | `local.image` with the coding CLI ([bring your own](#bring-your-own-image)) |
| `e2b` | `e2b:` | a fresh remote VM per run | yes | yes | `e2b.api_key` |

Every **executor run** is placed by the `run_in` of the entry the launch picks rather than by the seat, because where that runtime runs is a property of the runtime: the CLI's subscription login is on the engine host, so a local cell reaches it directly while a remote one needs the headless token instead. An entry that names none takes `providers.sandbox.default_run_in`, resolved at **launch** rather than at config time, so changing the catalogue reaches every entry that wrote nothing without rewriting it. The entry's cell is **reached**: the backend behind it is built for it, and `run_in: container` there needs `local.image`. A seat's own `role.sandbox` therefore places nothing: what the executor's box reads off it — its `setup`, `env` and `mcp`, and its `pause_ttl_seconds` and `max_turns` — are the seat's settings for the box its entry places. Validation refuses the impossible and nothing else: a `run_in` whose backend is not configured, a company default naming an unconfigured backend, an entry some seat's executor reaches that names no cell against a catalogue with no default, and agent seats with models in a company with no catalogue at all — each of which otherwise reads as working configuration and fails inside a turn. A `run_in` on an entry whose CLI cannot run an executor (anything but `claude-code` and `opencode`) is refused too, because no launch would ever read it.

### Choosing a cell

The run is the same fully permissioned CLI in every cell; what differs is what it can reach.

- **`direct`** runs it as a process tree on the engine host, as the engine's own user, in a directory of its own. It is the shortest path — no image, no remote account, the subscription login `crewlet llm login` already made on that host — and the right one for a dedicated host you are willing to hand to an autonomous agent, for the entry that needs the host itself, or for a first run on your own machine while its seats take work from you alone: the run can read what the engine's user can read and reach what that user's credentials reach. On any node that binds `api.port`, a `direct` box reaches its [tool bridge](#the-tool-bridge--a-seats-own-tools-from-inside-a-box) on that node's own loopback listener with nothing to set, which is why the [quickstart](../getting-started/quickstart.md), a first run, starts every seat this way; before a seat takes work from anyone else, move the runs into `container`.
- **`container`** runs it in a Docker or Podman container on the engine host, with only the box's own directory mounted, so the run reaches the host only through what the container is given. It needs `local.image` with the coding CLI installed ([Bring your own image](#bring-your-own-image)) and `CREWLET_MCP_BRIDGE_URL`, which a single host sets to its own loopback: a loopback address is handed to the box under the runtime's name for the engine host, and on Linux `api.host` must not be loopback, since the container's calls arrive from its bridge network ([Local sandboxes](#local-sandboxes)). Pick it for any other local instance, a workstation included, a shared host, or wherever the work should not reach the engine host's files.
- **`e2b`** runs it on a fresh remote VM per run, off the engine host altogether, and needs `e2b.api_key` (a self-hosted cluster takes `e2b.domain` too) and `CREWLET_MCP_BRIDGE_URL`, set to an address the VM reaches, a reverse proxy or tunnel to the node included ([The tool bridge](#the-tool-bridge--a-seats-own-tools-from-inside-a-box)). A login never leaves the engine host for it, so the entry signs in with a headless token or a key in the run's environment ([Credentials and the run environment](#credentials-and-the-run-environment)).

A company can use all three: the cell is the entry's, so two entries on the same CLI and model with different `run_in` let each seat take the one that is right for its work, and a fallback member of a seat's executor chain is placed by its own `run_in`.

**A run remembers its cell.** The placement is written onto the run's durable row *before the box exists*, and reconnect, teardown and the pause reaper all read it from there. It is not re-derived: the turn that collects a run may be a different process on a different node, days later, with the company configuration applied again in between — and reconnecting to a remote box through the local backend does not error usefully, it reports a box that has vanished, so a job that is still running would be abandoned as gone. An entry that names no cell is given the company's default at launch, so every row names one.

### Whether a cell is ready

Each node probes the cells `providers.sandbox` declares and publishes the answer on its heartbeat, so the Models page can say, per node, which cells can start a box now and disable the rest with the reason:

| Cell | Ready when |
|---|---|
| `direct` | the engine host runs the local backend (Linux or macOS) and the box root under `local.state_dir` is writable |
| `container` | `local.image` is set, the runtime (`docker` or `podman`, per `local.runtime`) is on the engine's `PATH`, and its daemon answers `version --format '{{.Server.Version}}'` within 5 s |
| `e2b` | `e2b.api_key` resolves on this node, and one authenticated read of the API (`GET /v2/sandboxes?limit=1`) answers within 5 s |

A cell the company does not declare reads `unconfigured`, never not ready. A cell that is not ready carries its fix, for example "Install Docker or Podman on this node and restart the engine: PATH is read at start". The probe runs at boot, at every apply and every five minutes; it never makes a box. The `direct` cell is not probed for host confinement: an executor's direct box is not confined, so a host without bubblewrap or Landlock still runs it.

### Sandbox backends

The provider layer is pluggable behind the `sandbox.Provider` interface (`internal/sandbox/protocol.go`). Two backends run code, and one stands in for them:

- **E2B cloud** (`e2b:`, no `domain`). Sign up at [e2b.dev](https://e2b.dev), export `E2B_API_KEY` from the dashboard. The engine talks to the documented REST API directly — there is no Go SDK to install, and no optional dependency for any of this — and uses E2B's prebuilt [`claude`](https://e2b.dev/docs/agents/claude-code) / [`opencode`](https://e2b.dev/docs/agents/opencode) templates (the coding-agent CLI preinstalled), picked automatically per coding agent when `template` is empty.
- **Self-hosted / local E2B** (`e2b:` + `domain`). E2B's infrastructure is open source ([e2b-dev/infra](https://github.com/e2b-dev/infra)); set `domain` to your cluster's domain and the **same code path** talks to it — one field is the whole cloud↔self-hosted switch, because the control-plane address and every box's own hostname are both derived from it. The cluster still issues its own key.
- **[Local](#local-sandboxes)** (`local:`). The engine host itself — `run_in: direct` (a process tree) or `run_in: container` (Docker/Podman). No remote account and no API key, and the coding agent can use the **subscription login** `crewlet llm login` already established. See below.
- **`fake: true`** — deterministic in-process stubs (`internal/sandbox/fake.go`): an in-memory filesystem, scripted coding-agent results, no network. The unit-test substrate, and a way to demonstrate the flow: it does **not** run real code, and every run it plays finishes at once with a report saying the double played it, so the turn collects a run that submitted nothing and is judged on that. It answers **every** cell, and is refused beside a real backend — the double *replaces* the backends rather than joining them, so a real block underneath it would read as configuration and configure nothing.
- **No sandbox at all** — omit `providers.sandbox`, which only a company with no agent seat, or with no `providers.llm` entry yet, may do. Any other company is refused at `providers.sandbox`, naming its first agent seat.

The closed set `run_in` is checked against is exactly the set the engine can construct — a test walks it, because a value the config accepts and the engine cannot build fails at the first run and nowhere earlier. The engine builds a backend only for the cells your company actually **reaches**, read from the same computation validation uses: built eagerly instead, it constructed a container backend for a company whose seats all run `direct` and failed the apply demanding an image the validator had just refused as a field nothing would read.

> **Two planes, and they behave differently on purpose.** The control plane (`api.<domain>`) mints, kills, pauses and re-times boxes under a bounded timeout, because minting a VM is a real allocation with a real cost when it is abandoned. The in-box plane — running commands, reading and writing files — is reached on each box's own hostname and carries **no overall deadline at all**: a coding agent's foreground command legitimately runs for many minutes, so what bounds it is the gap *between* output frames rather than the length of the call (ten minutes of silence). A file transfer is bounded the same way and more tightly: envd answers from a file that already exists, so a read or write that moves no byte for sixty seconds — the control plane's own request budget — is abandoned and says so, rather than holding that box's poll for as long as the process lives. (The poll of a box is bounded as a whole as well, and no box's poll waits on another's — see [the completion poll](#durability-completion-and-observability).)

> **Boxes are created with [secured access](https://e2b.dev/docs/sandbox/secured-access).** A secured box's in-box agent runs a command or serves a file only for a request carrying that box's own access token, and the engine sends it (`X-Access-Token`) on every command and file call. E2B hands the token back on the create, on a reconnect and on a read of the box alike, so the engine never stores it. Every box the engine creates is secured. A template whose in-box agent predates secured access (envd below 0.2.0) is refused at the create, with E2B's own message to rebuild it.

### Local sandboxes

The `local:` backend runs the coding agent on the machine running `crewlet run`. It exists for the case the [LLM backends](llm-backends.md) create: you already logged a coding CLI in on that host, and you want every executor run to use that same login — no E2B account, no API key, no token to mint.

```yaml
providers:
  sandbox:
    local:
      state_dir: ""               # empty → $CREWLET_SANDBOX_LOCAL_HOME,
                                  #   else ~/.crewlet/sandboxes
    default_run_in: direct        # direct | container — no implied answer
```

**`state_dir` is the box root** of both local cells, and of Ask Crewlet's [deep work](../guides/assistant.md#where-a-run-happens) when it runs on the engine host: a seat's box is made under its `boxes/`, and a deep-work run's confined box under its `assistant/boxes/`, which a seat's backend never lists, reattaches or reaps. Give it a volume sized for boxes and never the one holding the store and the stream ([Where a box writes](../guides/deployment.md#where-a-box-writes)).

Both shipped examples pair a `local:` catalogue with `run_in: direct` and run every seat's executor as its entry's [own run in a box](llm-backends.md#the-executors-run-in-a-box) on the engine host — each is a first run on your own machine while its seats take work from you alone, and names the `container` block to move to before a seat takes work from anyone else — and the difference between them is worth reading side by side. [`examples/nimbus.company.yaml`](../../examples/nimbus.company.yaml) runs on an `opencode` entry and has a code host to push to, so its runs open merge requests. [`examples/nimbus-claude-cli.company.yaml`](../../examples/nimbus-claude-cli.company.yaml) runs on the Claude Code entry's plan login and has **no code host at all**.

That second shape is worth saying out loud, because a sandbox and a code host are often assumed to come together. A sandbox with nowhere to push is still a place to run code: a spike, a benchmark, a reproduction, an SDK example that has actually executed. Add a code host later and the same runs start opening merge requests; nothing about the sandbox block changes.

**`local:` alone still needs a `default_run_in`** (or a `run_in` on every entry a seat's executor launches on), because it serves two cells and choosing `direct` is choosing to run an autonomous coding agent as the engine user. The block carries no mode of its own: `direct` and `container` are a choice about **one entry's runs** — point the seats that should use the host's login at an entry with `run_in: direct`, and the others at one with `run_in: container` — and a block-level mode could only ever answer for every run at once.

| | `run_in: direct` | `run_in: container` |
|---|---|---|
| Runs as | the engine user, on the host | PID inside a Docker/Podman container |
| Isolates state (per box) | yes | yes |
| Isolates the **host** | **no** | yes |
| Needs an image | no | yes (`image:`, no default) |
| A setup file outside the box's home | refused: it would be the host's | refused: only the home is mounted |
| Setup commands run | on the host, as the engine user | in the container: as the engine's uid on a rootful runtime, as container root on a rootless one |
| Sizing | the host | `run_args: ["--cpus", "2", "--memory", "4g"]` |
| When memory runs out (Linux) | the kernel kills the box before the engine | the same, through the runtime's `--oom-score-adj`; past its own `--memory`, only inside the container |

**Both modes isolate state.** Each box gets its own directory under `boxes/` with two sides: `home/`, which is the agent's — `HOME`, the XDG variables and `TMPDIR` are pointed inside it, its working directory is an empty per-box workspace there (a `direct` command starts in the home and its own shell enters the directory it was asked to run in, so every confinement starts it there and the engine never walks into it), and in `container` mode it is the one directory mounted into the container — and `records/`, which is the engine's: the logins the box was seeded with and a digest of each (so a reconnected teardown knows what to write back, where, and against what), the keepalive stamp, a `direct` job's process group, the engine process that last saw the box's job running (see [A job lost with its host](#durability-completion-and-observability)), and the env file. The two used to be one directory, which let a containerised job rewrite what the engine knew about its own box — name any file the engine's user could write as the "shared login" to copy a box file over at teardown, or make the env file a link the next exec followed out of the box. A box's environment is **allowlisted** (PATH, locale, TLS trust, proxy — never the engine's own keyring, its Tier A token values, its `SLACK_BOT_TOKEN` or its collector credential in `OTEL_EXPORTER_OTLP_HEADERS`). The allowlist is the same one every child the engine starts is handed — a [stdio MCP server](../guides/tools-and-mcp.md#what-a-stdio-servers-environment-is) and a coding CLI get it too. In `container` mode the run environment is handed to the runtime through an `--env-file` in the box's records rather than as `-e KEY=value`, because a process's argv is world-readable on the host (`/proc/<pid>/cmdline`, every `ps`) and that environment carries the seat's LLM key and whatever token `role.sandbox.env` declares; the runtime's client reads it on the host, so the container has no need of it. A `direct` job runs as the engine's own user with no mount, so it can reach its box's records too — which is what `direct` is documented to be below.

**The container runtime's own CLI gets an explicit environment too.** Every `docker`/`podman` invocation — `run`, `exec`, `pause`, `rm`, `ps`, `info` — is started with exactly the environment a [stdio MCP server whose `command` is `docker` or `podman`](../guides/tools-and-mcp.md#what-a-stdio-servers-environment-is) gets, which that table lists name by name: the host allowlist, the engine user's home, temporary and XDG directories (where the runtime keeps its config, and `XDG_RUNTIME_DIR`, where a rootless daemon's socket lives), and the runtime's own configuration — the `DOCKER_*` family, Podman's, and the few settings they read by name. Nothing else of the engine's reaches it, or any plugin and credential helper it runs.

**Whatever else the runtime needs, declare in `local.runtime_env`.** What a runtime's helpers read is open-ended, so the fixed list cannot carry it: the credential helper that pulls your image from a private registry needs its cloud's role, profile or key file (`docker-credential-ecr-login`, `docker-credential-gcr`), and a runtime plugin may read settings of its own. Name them there, exactly as you would an MCP server's `env:` — a `${VAR}` resolves from the [secret store](secret-store.md) first and the engine's own environment behind it, when the backend is built on an apply — and a declared name wins over the fixed list's value for it:

```yaml
providers:
  sandbox:
    local:
      image: ghcr.io/acme/crewlet-coding:1
      runtime_env:
        AWS_ROLE_ARN: "${REGISTRY_PULL_ROLE}"         # docker-credential-ecr-login
        AWS_WEB_IDENTITY_TOKEN_FILE: /var/run/secrets/eks.amazonaws.com/serviceaccount/token
        GOOGLE_APPLICATION_CREDENTIALS: "${GCR_KEY_FILE}"   # docker-credential-gcr
```

It is the **runtime's** environment and never the box's: nothing in it reaches the coding agent except through an argument you add to `run_args`. That is the one consequence for `local.run_args` worth knowing — a bare `-e NAME` copies `NAME` from the runtime CLI's environment, so it copies only a name the fixed list carries or `runtime_env` declares, and anything else arrives in the box unset. `crewlet validate` warns about each such `-e NAME` where it is written. Put what a box needs in `role.sandbox.env` (or a setup step's `env`), which reaches the box directly and is what that is for.

**Boxes are removed at teardown, and a crash-orphaned one is reaped on the next create, but only when it is genuinely orphaned.** Two independent questions are asked. *Is anything running in it?* A live process group that is still the box's own job (`direct`) or an existing container, read from the operating system rather than inferred. *Has anything touched it?* The completion poll refreshes a keepalive stamp on every tick, which is what `Sandbox.SetTimeout` means on this backend, exactly as it refreshes an E2B box's TTL. A box is reaped only when both say no: nothing running, and nothing has touched it for a whole `default_timeout_seconds`. A run blocked on a human answer is covered by the first (its process group is stopped, not gone) and bounded by `pause_ttl_seconds`, which is the knob that owns that wait. A reaped box still gives back any login the run refreshed before it was abandoned.

**A pid is not an identity.** A `direct` box records its job's process group as the leader's pid *together with the leader's start time*, read from the kernel's own process record (`/proc/<pid>/stat` with the boot id on Linux, `sysctl kern.proc.pid` on macOS) while the engine still holds the unreaped process. Every later act on that record, from a different process or hours on, first asks whether the group is still that one: the kernel hands a pid out again once its process is gone, and a bare pid read back from disk may by then lead somebody else's processes. A recorded group that is gone or now belongs to a later process keeps no box alive and receives no signal, so a teardown, a kill or a clarification pause can never reach a stranger's tree. When the kernel's record cannot be read, the reaper keeps the directory and a signal is withheld and logged (`local_sandbox_signal_withheld`), because neither can tell a live job from a recycled pid.

**Only `container` isolates the host.** In `direct` the coding agent runs fully permissioned as the engine user, so it can read what that user can read and reach what its credentials reach. That is the normal bargain of a local cell, and it is the right one on a dedicated host you are willing to hand to an autonomous agent and for a first run on your own machine while its seats take work from you alone, but it is not a boundary around the host, and Crewlet does not present it as one. **For any other local instance, a workstation included, and before a seat takes work from anyone else, run code work in `container`**, with [an image of your own](#bring-your-own-image), and keep `direct` for the entry that has a reason to need the host itself. Give a `providers.llm` entry `run_in: container` (or `e2b`), and every executor run launched on it runs there, or point the whole company at it with `default_run_in`:

```yaml
providers:
  sandbox:
    local:
      image: registry.example.com/coding:1   # must have the coding CLI installed:
                                             #   see "Bring your own image" below
      runtime: auto                          # auto | docker | podman
      network: ""                            # "none" cuts the box off entirely —
                                             #   including from its own LLM
      run_args: ["--cpus", "2", "--memory", "4g"]
    default_run_in: container
```

A `local.network` you set has to reach the engine host too: `none` cuts the box off from its [tool bridge](#the-tool-bridge--a-seats-own-tools-from-inside-a-box) as well, and with it from every tool of its seat.

The box directory is bind-mounted at `/home/user` — the same home E2B uses — so in-box paths, setup steps and briefs are identical across the two backends. The container is started with `--init` so a finished detached job is reaped rather than left as a zombie (which the completion probe would read as *still running*).

**The container runs as the engine's own user, and the mount is proved before the box is used.** A bind mount is one directory shared by two processes, so both of them have to be able to manage what the other writes. Under a **rootful** Docker or Podman the container's root is the host's root, and every directory the box creates in the mount comes out root-owned — the engine, which is not root, can then neither write a run's files into it nor reclaim the box's disk at teardown, so box directories accumulate on the host with no error anywhere. Crewlet therefore passes `--user <uid>:<gid>` on a rootful runtime and **not** on a rootless one, where the user namespace already maps container root onto the invoking user and `--user` would map it into the subuid range instead. The runtime is asked which it is (`docker info` / `podman info`); an unanswerable probe is treated as rootful, because that mistake fails loudly at creation while the other is silent.

If your image genuinely needs its own user — one that installs packages at run time, say — put `--user 0:0` in `run_args`. Operator flags are spliced last and both runtimes take the final occurrence of a repeated flag, so yours wins. Be aware you are taking back the problem above.

Every container box is then proved once, at creation, before anything runs in it: the engine writes a token the box reads back, and the box creates a directory the engine writes into and removes. That catches the ownership case and one other that is otherwise invisible — a `runtime` pointed at a daemon on **another host** (`DOCKER_HOST`, a forwarded socket) bind-mounts *that* machine's filesystem, so the agent finds no brief, no credentials and no tools. A box that fails the proof is torn down and the error names the cause; use the `e2b` provider for a genuinely remote runtime.

**A box reaches the engine host by the runtime's name for it.** The engine hands a box addresses written in its own network: the [tool bridge](#the-tool-bridge--a-seats-own-tools-from-inside-a-box) (`CREWLET_MCP_BRIDGE_URL`), the telemetry receiver (`CREWLET_SANDBOX_OTEL_RECEIVER_URL`), the URL of every HTTP [MCP server](#mcp-inside-the-sandbox) the seat scopes into the box, and the run's [notes route](#notes-to-a-running-run) on the bridge, which OpenCode's plugin polls. A single-host install sets those to loopback (`http://127.0.0.1:8000`), and inside a container loopback is the container itself. So where a URL the engine hands a `container` box names the engine host's loopback (`127.0.0.1`, any `127.x` address, `::1` or `localhost`), the box is given the same URL with the host replaced by the runtime's own name for the engine host: `host.docker.internal` under Docker, which the engine defines for every box it starts (`--add-host host.docker.internal:host-gateway`, which Docker Engine on Linux needs and Docker Desktop answers the same way), and `host.containers.internal` under Podman, which defines it itself. Any other host is handed on as written, since it already names a machine both sides can see, and so is every value you declare for the box yourself (`role.sandbox.env`, a setup step's `env`), which is in the box's network to begin with: a box reaching a service on the host names `host.docker.internal` there. `direct` shares the host's network and is handed every address as written — and for the bridge it needs none on a node that serves the API, dialling that node's own listener on loopback, which the node derives from the socket it binds — so one company runs `direct` entries and `container` entries side by side with one loopback `CREWLET_MCP_BRIDGE_URL`, which only the containers read. Docker Desktop, and Podman's machine on macOS and Windows, deliver that name over the host's loopback, where a loopback bind hears it and the [tool bridge](#the-tool-bridge--a-seats-own-tools-from-inside-a-box) serves it: a seat's run under any name, and an Ask Crewlet deep-work run held to the host's loopback under a loopback host name or one of these two runtime names alone. Docker Engine and Podman on Linux deliver it from the container's bridge network rather than the host's loopback, so the engine's API must listen there too: `api.host` empty (every interface) or the bridge's address, never `127.0.0.1`. `crewlet validate`, given both files, and every apply on a Linux node with both the `ingress` and the `seats` role — the one that serves the bridge and the receiver and starts the boxes that dial them on this host; a node without `seats` starts no box here, so whatever dials its routes comes from another machine — warn (`config_advisory` at `api.host`, or `api.public.host` when the public listener serves the bridge) when a company that reaches the `container` cell meets a loopback bind.

**Setup commands get a provisioning budget, not a control one.** Each command may run for `timeout_seconds` (default 600). Real provisioning — a dependency install, a cold image pull, a large clone — takes minutes, and without its own budget these inherited the backend's control-plane timeout and were killed, failing the whole acquisition. Raise it for a step you know is slow; lower it for one that should be instant, so a hung command surfaces as a named setup failure rather than eating the turn. A failure names the step and what in it failed — the file it could not write, or the command's position and either the status it exited with or that it reported none — and never the command text: the engine resolves nothing in a command, which the box's shell expands from the run environment, but a recipe may still spell a credential out literally, and the failure is logged and handed back to the agent.

**Setup steps and the local cells.** Neither local cell writes a setup step's *file* outside the box's home. `direct` has no filesystem virtualisation, so a file anywhere else would be the engine host's own — its real `/usr/local/bin` — and is refused with an error naming the mode; and its home is a directory minted for each box, so no absolute path a document can write is inside it. `container` writes a file on the host side of its one mount, the home at `/home/user`, and refuses any other path. A relative path is under the home in either cell, and so is a path starting `~/`, which names the home in every cell as it does on `e2b`; a path that climbs out of the home with `..`, names the home itself, or names another account's home (`~name/…`) is refused. So name a file a step needs in the box relative to its home — `.npmrc`, `.local/bin/tool`, or `~/.npmrc` — which is the one form every cell writes in the same place. File paths in a setup step are **not** shell-expanded, so `$HOME` does not work there; a step that needs a file's absolute path has a `commands` entry, which does run in a shell, expand `"$HOME"` — the [git-auth recipe](#the-git-auth-recipe) writes its helper that way, because git is given the helper's absolute path.

**A step whose file a local box would refuse is refused when the document is written** — by `crewlet validate` and every write path — rather than at the seat's first box, where it used to surface as a setup failure on every box that seat opened. The check is the boxes' own rule, the same function both local cells call before they touch a path, applied to every box a seat actually runs in: each box its executor runs in, placed by the `run_in` of each entry its launch can pick (or `default_run_in`). A box in `e2b` is judged too, by the shapes its in-box agent refuses for certain — another account's home (`~name/…`), and the home itself or a directory above it (see `files` under [setup steps](#setup-steps--provisioning-the-box)) — so an engine-wide step writing `/usr/local/bin` is still accepted in a company whose seats all run in `e2b`. The refusal sits at the file in the step that writes it, names the step, the path and the first seat whose box it fails (and how many more), and is an admission rule: a stored revision that keeps such a step still applies, reported as a warning, so a rolling upgrade never takes a node off the fleet's revision over it. What it cannot see is a link an existing directory on the engine host holds; the box refuses that one itself, when it writes.

**A setup command is not confined the way a file is.** It runs in the box's shell, and under `direct` that shell is the engine host, as the engine's user: a step that installs a system package installs it on the host, or fails for want of the rights to. Under `container` it runs inside the container — as the engine's own uid on a rootful runtime, which an image's system directories usually refuse too, and as container root on a rootless one. Have such a step check for the tool it needs and name what to install where, and provision a box's system toolchain deliberately: on the host for `direct`, in the image for `container`.

**Credentials.** The local backend seeds the credential files of the [`providers.llm` entry](llm-backends.md) the launch picked — the first member of the seat's executor chain whose CLI has a runner and is not sitting out — or, for OpenCode, the login document its export printed, which the run imports and exports again ([OpenCode](#opencode)) — into the box before the run, and writes one the run **refreshed** back afterwards — OAuth access tokens expire in hours and most vendors rotate the refresh token with them, so discarding the rewritten file would log the fleet out at the next expiry. The box is offered every file of the login and seeded with what the login holds when it is seeded, **read whole** under the shared credential directory's lock — [one login](llm-backends.md#a-login-of-several-files-is-written-whole), never one sign-in's token beside another's `config.toml` — and given every file of it or none: a login it cannot be given whole (a credential path that would leave the box's home) is not seeded at all, with a `local_sandbox_credential_seed_failed` warning, so the CLI inside answers its own "not authenticated" rather than failing on half a login. The write-back is a **compare-and-swap against what the box was seeded with**, recorded (as a SHA-256 of the bytes the box was given, and every file of the login it was not given) in the box's records at creation: the files the run refreshed are written back only where the box's copy differs from its seed **and** the shared login, as a whole — every file, and every absence — still holds that seed, and then as **one write** of the whole login, so a teardown killed part way never leaves half of it. An idle box therefore writes nothing (an OpenCode box's export reproduces its import byte for byte, so it would otherwise have put its stale seed back over a login the host had refreshed meanwhile), and a box whose run refreshed while the shared login also moved — another seat's refresh, a new `crewlet llm login` — keeps the shared one, which is the newer of the two, and logs `local_sandbox_credential_superseded` with `shared=changed`, naming the file and its path, never a value. The comparison and the write are one step under the shared credential directory's lock (`<state_dir>/<agent>/credentials.lock`, beside it), which the [CLI backend's](llm-backends.md) seats and `crewlet llm` commands take for their own writes; a teardown waits at most 10 s for a writer holding it. A credential the shared directory did not hold when the box was seeded is never created from a box, and nor is one the operator has since removed with `crewlet llm logout` — a refresh the run made of that one is dropped, and logged as `local_sandbox_credential_superseded` with `shared=removed`. A file the login gained while the box ran — the host signed in again — is a newer login too, and the box's refresh is dropped with `shared=changed`.

**Pause / resume works.** A run blocked on a human answer is genuinely suspended: `direct` SIGSTOPs the job's process group, `container` issues `docker pause`. Both hold memory, which is exactly why the same `default_pause_ttl_seconds` reaper bounds them as it bounds a billed E2B snapshot.

**A box goes before its engine when memory runs out.** On Linux every process a local box runs stands ahead of the engine for the kernel's OOM killer: raised, before it runs anything, to the engine's own `oom_score_adj` plus 1000, held to the kernel's ceiling of 1000. A `direct` box's first process raises itself and then becomes the command, ahead of any confinement, so every setup command, exec and the detached job start there, along with everything they start; a `container` box is started with the runtime's `--oom-score-adj`, which Docker and Podman give every `exec` into the container too. The kernel scores a process by the memory it holds, in thousandths of the memory that ran out, plus that adjustment, so a box a whole thousand ahead is taken before the engine whatever the two hold. A coding CLI and its builds are the node's most expendable work: the run the kernel kills is collected as the failed run it is, its partial output and exit status with it, where the engine killed would take every seat on the node down at once. The lead is counted from the engine's own value, because that value is its deployment's decision. A Kubernetes Guaranteed pod runs at -997 so its node's kernel takes it last, and its boxes at 3 go before its engine without going before every other pod's work. An engine already above 0 leaves its boxes at the ceiling. An operator's own `--oom-score-adj` in `run_args` wins for a `container` box. It is an order for the kernel and not a boundary, since a box may lower its own value again, and on macOS, which gives an unprivileged process no such priority, a box and the engine compete on size alone. What an OOM kill takes beside the box is up to whatever supervises the engine, and a systemd unit's and a Kubernetes container's defaults both take the engine with it: see [When the host runs out of memory](../guides/deployment.md#when-the-host-runs-out-of-memory).

**What local mode does not give you:** template-based sizing (use `run_args`, or the host), provider-enforced network egress policy (use `network:` plus your own firewall), and a fresh machine per run — a `direct` box shares the host's installed toolchain, which is usually the point.

### Bring your own image

The engine ships no image for `local.image`: the one to use is one built for your repositories, kept as current as they are. Whatever you build, the engine runs it as

```text
docker run -d --init -v <box home>:/home/user -w /home/user/workspace -e HOME=/home/user \
  --user <engine uid>:<gid> --add-host host.docker.internal:host-gateway <run_args> IMAGE sleep infinity
```

(`--user` only on a rootful runtime, `--add-host` only under Docker), and runs every job and setup command in it with `docker exec`, its run environment in an `--env-file`. So the image needs:

- **the coding CLI on the login `PATH`**: the CLI is started under `sh -lc`, and a Debian or Ubuntu image's `/etc/profile` resets `PATH` to the standard directories, so a CLI in `/usr/local/bin` is found and one only on an `ENV PATH` entry is not;
- **`git`**, and **`gh`** where seats open GitHub pull requests;
- **a POSIX `sh`** and no `ENTRYPOINT`, since the engine supplies the command;
- **a writable `$HOME`** and nothing it relies on under `/home/user`, which the box's own home is mounted over;
- **no assumption about the user**: it must work as a uid it has no account for (the engine's own, on Docker Desktop for a Mac user `501:20`).

A box reaches the engine host by the runtime's name for it, as [above](#local-sandboxes), and on Linux `api.host` must not be loopback.

**Recipe 1: a stock image and a setup step.** No image to build: a step installs Claude Code and `gh` into the box's home, each at a pinned version, `gh` checked against the checksums file GitHub publishes with the release.

```yaml
providers:
  sandbox:
    local:
      image: node:22-bookworm       # has git, curl and sha256sum
    default_run_in: container
    setup:
      - name: coding-tools
        files:
          .profile: |              # the login shell the CLI starts in reads it
            export PATH="$HOME/.npm-global/bin:$HOME/.local/bin:$PATH"
        commands:
          - |
            err=$(mktemp)
            npm install --global --prefix "$HOME/.npm-global" --no-audit --no-fund \
              @anthropic-ai/claude-code@2.1.310 2>"$err" && exit 0
            s=$?; cat "$err" >&2
            grep -Eq 'code E(408|429|5[0-9][0-9])$' "$err" && exit 75
            exit "$s"
          - |
            set -eu
            v=2.103.3; a=$(dpkg --print-architecture); t="gh_${v}_linux_${a}.tar.gz"
            cd "$(mktemp -d)"
            fetch() {
              code=$(curl -fsSL --retry 5 --retry-delay 2 --retry-all-errors -o "$2" -w '%{http_code}' "$1") && return
              s=$?
              case $code in 408|429|5??) exit 75 ;; esac
              exit "$s"
            }
            fetch "https://github.com/cli/cli/releases/download/v${v}/${t}" "$t"
            fetch "https://github.com/cli/cli/releases/download/v${v}/gh_${v}_checksums.txt" sums.txt
            grep " ${t}\$" sums.txt | sha256sum -c -
            tar -xzf "$t"
            mkdir -p "$HOME/.local/bin" && mv "gh_${v}_linux_${a}/bin/gh" "$HOME/.local/bin/gh"
        timeout_seconds: 600
```

Setup steps run after the box is created and before the CLI starts, as the box's own uid, which is why both install under `$HOME` rather than the image's system directories. The trade-off against recipe 2: **every new box downloads and installs both again** (a reused box keeps them), which costs time on each run and needs egress to the npm registry and GitHub.

**Each download says what its failure means.** npm retries a failed fetch twice by itself, and `curl` here retries every failure five times, two seconds apart (`--retry-all-errors`, since `--retry` alone gives up at once on a reset or a refused connection), so a blip of a few seconds never fails the step. A registry or a download server still failing on its side after that, answering a 408, a 429 or a 5xx, ends the command with 75: a download that failed for now, which a wait clears (`setup_unavailable`). Every other failure keeps its own status, a setup an administrator has to fix (`configuration`): a pin that names no release (npm's `E404` or `ETARGET`, a 404 from GitHub), a 401 or a 403, a checksum that doesn't match, and a connection refused or reset, a name that doesn't resolve or a timeout, which from inside the box look the same as egress that is blocked (see [Setup steps](#setup-steps--provisioning-the-box)).

**Recipe 2: your own image from Claude Code's dev container.** Build Anthropic's [reference dev container](https://code.claude.com/docs/en/devcontainer) (`.devcontainer/` in `anthropics/claude-code`) with the CLI pinned, `--build-arg CLAUDE_CODE_VERSION=<version>`, then put `claude` where a login shell finds it, since that image adds its npm prefix to `PATH` with `ENV` alone:

```dockerfile
FROM claude-devcontainer:<version>
USER root
RUN ln -s /usr/local/share/npm-global/bin/claude /usr/local/bin/claude
USER node
```

Add your repositories' toolchains to the same Dockerfile and name the result in `local.image`. Its egress firewall (`init-firewall.sh`) is not started by a plain `docker run`; restrict a box's network with `local.network` and your own firewall instead.

A seat on a [plan's login](llm-backends.md#authentication) needs nothing more in either recipe: a local box is seeded with the login and writes a refreshed one back.

## Coding agents

Two runners ship behind the `sandbox.Runner` interface, one for each CLI that can run an executor: `claude-code` and `opencode` (`config.CodingAgents`, held to the runners that exist by a test). A run's runner is the CLI of the `providers.llm` entry its launch picked, with no setting beside it, and a launch passes over a member of the seat's executor chain on any other CLI. Both runners are handed the same two texts — the **brief**, the prompt the CLI runs, and the run's **standing instructions**, which go on the CLI's channel for adding to its own system prompt ([What a coding agent is told](#what-a-coding-agent-is-told)) — and return the same structured result. The entry names its model in its own CLI's grammar and signs in the way that CLI does, so a run goes only to that CLI's runner (see [One entry, one runner](#claude-code) below).

### What a coding agent is told

A run is handed two texts, kept apart from the launch all the way to the CLI:

- **The brief** — what this run is asked to do, and the whole of the prompt the CLI runs: the turn's own ask, with the ledger of its earlier rounds where a reviewer sent it back — the user message a phase on this host sends. A run carried on after a person's answer in the box it parked in is prompted with the answer, in its own CLI session; one that cannot reuse that box is re-seeded in a fresh one and told the question, the answer and the branch to check out beside its brief (see [Answering a parked run](#answering-a-parked-run)).
- **The standing instructions** — how to work, for the whole run, in this order: the seat's executor system prompt (its identity, policies, roster and memory, exactly as a phase on this host sends them as its system message, opened by one constant note saying that these, and not the coding tool's own prompt, are the role — Claude Code's prompt opens with "You are Claude Code", and no flag removes it), then `## Your environment` (the box, each [setup step's](#setup-steps--provisioning-the-box) `brief`, and the MCP servers connected), then `## When you need a person's answer` ([how to ask a person](#mid-run-clarification-ask_and_wait), on every launch), then the [report to write before stopping](#a-run-is-bounded-by-its-rounds-each-launch-is-published-as-its-own-record), addressed at the box's own path, and last — for a run whose CLI takes a person's notes between its steps — what such a note is: how it opens, and the heading its CLI puts it under (for Claude Code a system message, or on some models a system reminder at the end of the last tool result; for OpenCode a message from the user), and that text a tool produced — a file's contents, a command's output, a fetched page — is never a note, whatever it says ([Notes to a running run](#notes-to-a-running-run)).

The standing instructions are **appended to the CLI's own system prompt** — never put in its place, and never in the prompt it runs. The vendor's prompt is the harness an executor exists to use: how to drive its shell and editor and work through a task, which a replacement would strip. And instructions placed in front of the task reach the model as part of the user's request, where a seat's identity and policies, sent that way, are something the model is asked rather than who it is. Each runner uses its own CLI's channel:

- **Claude Code** — `--append-system-prompt-file`, which puts the file's text after Claude Code's default system prompt and leaves that prompt whole (measured on 2.1.310, off the request the CLI sent).
- **OpenCode** — an absolute `instructions` entry in the [configuration the run writes](#opencode) (`<home>/.crewlet/opencode.json`), which OpenCode adds after its default agent's prompt as `Instructions from: <path>` and the file's text (measured on 2.0.32 and 2.1.4, the same way). An entry rather than a global `AGENTS.md` in OpenCode's configuration directory, because the entries of every configuration OpenCode reads are added together — an image's own global configuration keeps its instructions, where a written `AGENTS.md` would replace one an operator baked into the box — and because the run's configuration is rewritten on every run, so a reused box never carries a previous run's entry. Absolute, because a relative entry is matched by walking up from the checkout.

Both read the text from **a file** in the box's work directory (`<home>/.crewlet`), never from argv. OpenCode's `instructions` entry names `system.md`. A Claude Code run is started with one of two: its launch writes `system.md`, the instructions as they stand, and for a run wired to its turn's notes — every seat's executor run — `system-notes.md` beside it, the same text with what a note is after it; the run's script names `system-notes.md` on a release that reads notes and `system.md` on an older one ([Claude Code's hooks](#claude-codes-hooks)), and a run not wired to notes, Ask Crewlet's deep work, is started with `system.md`. The text carries a seat's org chart, policies and memory, and a command line is readable by every process that can list it — on a `direct` box, every account on the engine host — and bounded by `ARG_MAX`. Each file is written afresh for every run, at the mode a box writes every file with (`0600` on a local box) even where a previous run on a reused box left one wider, and outside the checkout, so a `git clean` cannot remove it and a commit cannot carry it into a repository. A run with no standing instructions writes no `system.md` and passes no flag for it; a runner always has at least the report instruction.

Neither text is recorded anywhere a later process reads: the box is started with them once, and the run's record holds the task and the turn's parked state, which a resumed turn reads instead.

### Claude Code

Runs headless — `claude -p --output-format stream-json --verbose --permission-mode bypassPermissions --settings <home>/.crewlet/claude-settings.json --append-system-prompt-file <home>/.crewlet/system-notes.md` (the run's [hooks](#claude-codes-hooks) and its [standing instructions](#what-a-coding-agent-is-told) told of notes, which every seat's executor run is started with on Claude Code 2.1.163 or later; on an older release, and for a run not wired to notes, `--append-system-prompt-file <home>/.crewlet/system.md` and no `--settings`), with `--model` from the entry, `--max-turns` from the run's turn cap, `--mcp-config <file> --strict-mcp-config` for its servers and the bridge, and `--resume <session>` where a person's answer carries a parked run on, the brief on its standard input — so it prints every message as it happens, one JSON object a line, into its own **event stream** (`stream.jsonl` in the box's work directory). That stream is what a person watching the run sees and what its transcript is built from; `--output-format json` printed one object when the run ended and nothing before it, and in print mode the CLI writes nothing to stderr either, so a run on it showed nothing while it worked and left no transcript after. (`--verbose` is not optional: print mode refuses stream-json without it.) The stream's **last line is the result message**, which the wrapper copies to `result.json` after the CLI exits — never through a pipe beside it, whose exit status would be the copy's rather than the CLI's — and that line maps directly onto the result (final text, session id, token usage, cost; an error subtype such as `error_max_turns` and its `errors` are the failure). A stream that ends on anything else is a run that stopped before it said how it ended, and reads as one rather than as a silent success. A run whose wrapper never made the copy — its process group killed, by an OOM or a host restart, so the poll ended it on the wrapper's liveness — is read from the stream's own last line, which is what the copy would have held: the result, where the CLI printed one before the wrapper died, and otherwise what it was saying when it stopped. It used to read as a run that "produced no output" beside a transcript of everything it did. A result file the box refuses (one that is [not a regular file](#a-run-is-bounded-by-its-rounds-each-launch-is-published-as-its-own-record), say) is read from that line the same way, and the refusal is still said; a CLI that exited before printing anything at all — not installed, a bad flag — leaves both empty, and reads as what it is.

**The brief is read on stdin**, from `brief.md` in the box's work directory, never from argv — `-p` with no prompt reads its prompt there, verbatim (measured on 2.1.263 and 2.1.310). A brief carries every note the turn has read, so it grows; one argument is capped at 128 KiB; and a command line is readable by every account on a `direct` box's host, the reason the standing instructions are a file too. **The wrapper unsets `CLAUDE_CODE_SIMPLE` and `CLAUDE_CODE_SAFE_MODE`** before the CLI starts: bare mode drops every hook (with `CLAUDE.md`, subagents and a plan's login) and safe mode drops hooks and the `--mcp-config` bridge, and either can arrive from the seat's `role.sandbox.env`, the image or a profile the login shell sources — only the wrapper, running after all three, reaches every one, so they are removed for every Claude Code run rather than refused in configuration. **A run a hook stopped is a failure.** Claude Code reports a loop that a hook of the repository's or the image's own settings stopped — one that exited 2 or returned a block — as a success subtype with an empty result and `terminal_reason: hook_stopped` (measured on 2.1.263 and 2.1.310); the runner reads it as a failed run saying so, never as a run that succeeded and said nothing.

The run's input is its **whole** prompt: the vendor's `input_tokens` counts only the uncached remainder, so the engine adds `cache_read_input_tokens` and `cache_creation_input_tokens` to it and carries both as the cache's share, the same way the engine counts a call on a Claude Code entry on its own host. Read alone, the uncached figure put a fraction of every launch's prompt on the budget counter.

The run's model and its sign-in come from the `providers.llm` entry the launch picks — the first member of the seat's executor chain (its `llm`, else the company's fallback entry) whose CLI has a runner and is not [sitting out](llm-backends.md) — which for this runner is a Claude Code entry (`agent: claude-code`, or no `agent` at all). Its model goes to `--model` exactly as the entry's calls on the engine host pass it, an alias (`sonnet`) or an id, and the entry's `env` goes into the run environment, so an entry that reaches its model through a gateway (`ANTHROPIC_BASE_URL`, and the `ANTHROPIC_AUTH_TOKEN` it takes) or a cloud provider (`CLAUDE_CODE_USE_BEDROCK` and its region) runs its executor the same way ([Credentials and the run environment](#credentials-and-the-run-environment)). A seat may sign Claude Code in itself in `role.sandbox.env` — `CLAUDE_CODE_OAUTH_TOKEN` (a Pro/Max plan), `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, or a `CLAUDE_CODE_USE_BEDROCK` / `CLAUDE_CODE_USE_VERTEX` / `CLAUDE_CODE_USE_FOUNDRY` toggle — and a variable it names there wins over the entry's under the same name.

**One entry, one runner.** An entry's model is written in the grammar of the CLI it drives and its sign-in is that CLI's, so a run on one is that CLI's own run: a `claude-code` entry runs under Claude Code, an `opencode` entry under OpenCode. There is no runner setting beside the entry to disagree with it — the runner *is* the entry's CLI. The model is handed to the run exactly as the entry's calls on the engine host hand it to the CLI. A CLI with no runner at all (`codex`, `gemini-cli`, `kimi-code`, `hermes`, `pi`, …) cannot be an executor: a launch passes over it in the seat's chain, a seat whose chain has no member that can run is [refused on the write](#failure-modes), and a `run_in` on such an entry is refused as a placement nothing would read. It still serves the seat's reviewer, workers and side passes (`llm_review`, `llm_subagent`, `llm_auxiliary`, `llm_judge`). When the run launches, the entry's environment is exported into the box: its whole `env` — a gateway's address and the token it takes, a cloud provider's switch and its region, a proxy, and, for `opencode`, which reads its model provider's key from its own environment, [that key](llm-backends.md#6-a-provider-key-in-env-opencode-hermes-pi) — and what signs that CLI in: the headless subscription token (`CLAUDE_CODE_OAUTH_TOKEN`, minted by `crewlet llm login <key> -capture-token`, so Claude Code there bills your Pro/Max plan — no API key anywhere), the key of an `auth.mode: api-key` entry, the variables `inherit-env` forwards. This works on **every** backend including remote E2B, because each is a variable, and a credential among them one scoped, revocable variable. The login itself — Claude Code's credential files, OpenCode's exported login — deliberately never leaves the engine host for a remote box: it carries a refresh token whose rotation is shared fleet state. So a `claude-code` entry with no headless token and no API key (nor a gateway's token or a cloud provider's switch in its `env`), or an `opencode` entry signed in only by `crewlet llm login`, needs a [local cell](#local-sandboxes) — `run_in: direct` or `run_in: container` — which is seeded with the login and writes a refreshed one back.

### OpenCode

Drives **OpenCode 2** — the `@opencode/cli` package, whose `opencode --version` prints `opencode v2.…`. 1.x (npm's `opencode-ai`) cannot run it, and a box that has 1.x is refused by name before anything runs (`this box runs OpenCode 1.18.35; the opencode runner drives OpenCode 2 …`) rather than failing on 1.x's usage text. A box with no `opencode` on its PATH says so and exits 127; one whose `opencode` is there but fails `opencode --version` (it can't be executed, or crashes) says that instead, with the exit status and what it printed, which is the run's transcript when nothing else was written. Install 2 in your box image; E2B does not say which release its prebuilt `opencode` template carries, so a template that refuses this way needs `template:` pointed at one built with `@opencode/cli`. OpenCode is **provider-agnostic**: an `opencode` entry names `<provider>/<model>` for any provider OpenCode speaks to, a local server included, so a seat on one runs its executor on the same entry, the same model and the same key — no extra secret. 

**A run is a short script around a server of its own**, because 2.0 cannot be driven correctly in one command. `opencode run` alone attaches to a *background service* — detached from the run, on a port compiled into the binary that every box on a host shares, outliving the run and keeping the environment (so the credentials) of whichever run started it. With `--standalone` it starts a private server inside the run instead, and sends the brief at once — before the run's MCP servers have connected, and 2.0 fixes a step's tools as the step starts, so measured on 2.0.32 the first step of every run with a server declared was offered none of the seat's bridged tools. So the run:

1. refuses a 1.x box, and imports the box's login if it was given one (below);
2. starts `opencode serve` on a loopback port of its own and waits — at most 60 s — until it has printed both where it listens and the password it minted, naming whichever of the two it never printed. The server's password is always its own: `opencode serve` takes one from `OPENCODE_PASSWORD` or `OPENCODE_SERVER_PASSWORD` and then prints none, so the run unsets both before anything starts — a box environment carrying either (a seat's `role.sandbox.env`, an image built for OpenCode) used to wait out the whole minute and fail saying the server never listened — and hands the minted one to its own client calls as `OPENCODE_PASSWORD`, the variable OpenCode's client reads first. The server is started without it, so nothing the agent runs inherits it;
3. asks it (`opencode api mcp.list`) until every MCP server the run declares has left `pending`, for at most 60 s, twice the 30 s OpenCode gives one server to list its tools — past that it starts without the straggler and says so on stderr. Each server is looked for by its name exactly as OpenCode's answer spells it, `&`, `<`, `>`, U+2028 and U+2029 literal, so a server named `R&D tools` is seen the moment it settles;
4. runs the brief against that server, **on stdin** — OpenCode re-quotes an argv prompt, so a brief passed as an argument reached the model wrapped in quotes with every quote inside it escaped — under a **session it names**, with a title, which stops 2.0 making a second billed model call to write one;
5. prints the session's usage report as the stream's last line, writes the box's refreshed login back, and stops the server. The run's exit status stays the CLI's own.

The script is plain POSIX `sh`, written for every `sh` a box image is likely to have — dash (Debian, Ubuntu), bash in its POSIX mode (Fedora, RHEL, Arch) and busybox ash (Alpine, which OpenCode 2's musl builds are for).

The run's `--model` is the `opencode` entry's model exactly as written — the same `<provider>/<model>` (`anthropic/claude-sonnet-5`, `openrouter/anthropic/claude-sonnet-5`) every call on that entry on the engine host passes, which OpenCode splits at its first slash into one of its own providers and a model — signed in by that provider's own key from the entry's `env` or the seat's `role.sandbox.env`, or by the entry's login in a local cell.

**A login follows a run into a local cell as OpenCode's own export.** OpenCode 2 keeps its logins in the database it keeps its sessions in, so the entry's login travels as the document `opencode auth export` printed ([LLM Backends](llm-backends.md#1-broker-the-vendors-own-login-any-cli)): a `direct` or `container` box is seeded with it at `~/.crewlet/exported-credentials`, and the run imports it before its server starts. A token OpenCode refreshes mid-run then lives only in that database, and every teardown of a run still in flight — a seat retired mid-run, a launch settled as failed after its job started, the pause reaper — kills the job's group outright (`SIGKILL`, or `docker rm -f` for a `container` box), so nothing in the box runs at its end. So the run **exports the database back over the document while it works**, through its own server every 30 s, as well as once more when it ends; a `SIGTERM`, `SIGINT` or `SIGHUP` to the run exports once more before it goes, exiting 143, 130 or 129, under an engine started with nohup too, since `crewlet run` doesn't hand a hangup it ignores on to the boxes it starts ([Force stop](agent-runtime.md#graceful-shutdown)). Thirty seconds is the window a kill can still lose a refresh in: an OAuth access token lives an hour or more, so under one refresh in a hundred falls inside it, and an export through the server costs about 0.14 s (measured on 2.0.32). An export replaces the document only where it differs and holds a login — a whole, non-empty JSON array, never the `[]` a database that dropped its credential prints — and nothing is exported where the box was given none. The box's teardown then writes the document back to the shared login under the rule every local box's login follows ([Local sandboxes](#local-sandboxes)). A remote box is never given it.

The runner **writes OpenCode 2's own configuration to `<home>/.crewlet/opencode.json`**, beside the run's other artefacts and never in the checkout, and the run's script hands its content to the run's server alone as **`OPENCODE_CONFIG_CONTENT`**. OpenCode takes no config flag, and of its two variables for a process's own configuration, `OPENCODE_CONFIG` (a file's path) ranks *below* a repository's `opencode.json` and `.opencode/`, while `OPENCODE_CONFIG_CONTENT` ranks above them: 2.x reads managed policies, well-known, global, `OPENCODE_CONFIG`, the project's `opencode.json`, its `.opencode/`, `OPENCODE_CONFIG_CONTENT` and managed settings in that order, a later document winning (the same at 2.0.0, 2.0.32 and 2.1.4). So **a repository's own `opencode.json` is not written to**: it stays as it is and loads beneath the run's configuration, the way Claude Code loads a repository's `.claude/settings.json` beneath `--settings`. Measured on 2.0.32 and 2.1.4 with a repository whose own `opencode.json` and `.opencode/opencode.json` disable the bridge and deny every permission: the bridge connected and the shell ran. Every server the run declares, and the agent its turn cap is set on, states `disabled: false`, so a document beneath the run's cannot switch one off under the same name. The login's import and export and the run's own client calls are handed none of it, and a run whose configuration is missing is refused before a login is imported or a server started. For a run wired to its turn's notes, the same file names the run's [notes plugin](#opencodes-notes-plugin) and the server alone is handed the run's session as `CREWLET_STEER_SESSION`.

It declares **no provider**: the model names one of OpenCode's own, which reads its key from the run environment under that provider's own variable, so a credential is never written into the file where the agent could read it back into its report, and a provider declared beside the one the model names would shadow it. The same file sets `permissions` to allow every action and deny only `question` (headless runs have no human to approve a prompt — a gate left at `ask` is auto-rejected — and the one tool that asks a person is replaced by `ask_and_wait` on the run's bridge; the rules of every document OpenCode reads are added together in its order, so these come last and, the last match winning, decide), `share: disabled`, `update: disable` (a CLI that updates itself mid-run swaps the tool under the brief while the seat's turn is suspended waiting on it) and `snapshots: false` (a git snapshot of the checkout at every step, for an undo a headless run never offers). Each MCP server is declared under `mcp.servers` with **`codemode: false`**, so its tools are offered to the model directly as `<server>_<tool>` rather than only through Code Mode's JavaScript `execute` tool — which a model may never take to, and which the transcript would record as `execute` whatever it reached — and a remote server with **`oauth: false`**, since the bridge authenticates with the run's token and a headless run cannot complete an OAuth flow.

**A server's values are referenced, not written into the configuration.** Its `url`, each header value and each `environment` value is a `{file:<path>}` reference to a file of its own under `<home>/.crewlet/opencode-values/`, which OpenCode reads in the reference's place — the file's content with the whitespace at either end trimmed, so an `environment` value that begins or ends with whitespace arrives without it (a URL or a header value has none that counts) — so the configuration and the variable carrying it hold paths and no value. The files are written before the configuration that names them, at the mode a box writes every file with (`0600` on a local box). OpenCode replaces every `{env:…}` and `{file:…}` in the configuration's text before it parses it, and the configuration names the instruction file, the notes plugin and every value under the box's home, so a run on a box whose home that text cannot name — a relative one, or one holding a brace, a quote, a backslash or a control character — is refused, saying so and naming `providers.sandbox.local.state_dir`, which places a local box's home.

Its `instructions` names the file holding the run's [standing instructions](#what-a-coding-agent-is-told), by its absolute path. The configuration is written on **every** run, including one that names no model and no server, and the previous run's configuration and values are removed before it is: a run is configured by its own file or not started at all, never by the vendor's defaults or by a file an earlier run on a reused box left, MCP block and dead per-run bridge URL included.

**Its answer is its last message's text.** Each step of a run is a message of its own, and `run --format json` prints every step's text, so the result is the text of the last message that wrote any — a run handed a [note](#opencodes-notes-plugin) after it had answered answers again, and its result is the later answer, not the two joined — while the transcript keeps every step's. The report the run writes is what the result prefers anyway.

**Its tokens are the session's own totals.** `run --format json` drops the final step's counts, so the run asks its session (`opencode api session.get`) once it ends and the collection reads that: the whole prompt, the cache's two shares included, and the output with the reasoning OpenCode reports beside it added back, as every provider bills it — plus OpenCode's price, as it reported it (zero where it has no pricing for the provider, which the record reads as no price). A run whose report is missing reports zero rather than an estimate.

### A run is bounded by its rounds; each launch is published as its own record

A run is **never stopped by its box's TTL**. The waiter refreshes the box's TTL every poll tick (keepalive), so a legitimately long run is free to finish; the TTL only reclaims a box the engine has stopped heart-beating for. What bounds a run is its **rounds**: `role.sandbox.max_turns`, else `providers.sandbox.default_max_turns` (96 unless set, `0` uncapped), handed to both runners as their own turn cap — Claude Code's `--max-turns`, OpenCode's agent `steps`. And a turn whose trigger carries a wall-clock cap (a schedule's `timeout_seconds`) ends its run at that deadline, the collection recording what it did up to then. Completion is detected by tracking the job itself — see [Durability and completion](#durability-completion-and-observability).

Because its standing instructions tell the coding agent that it is *not* the last step, it writes a structured **findings report** to a known file before stopping; `collect` prefers that file for the result text (it survives a run whose process group died before it printed its final message, and a tool-only run that streamed no final message). **The report names what the run delivered**, a line of its own for each branch it pushed and each pull or merge request it opened — `Delivered: fix/retry-backoff`, `Delivered: https://git.example.com/acme/api/pull/42` — and those lines are the run's **delivered refs**, in the report's order: a branch as well as a pull request, on any host and any scheme. The engine keeps no list of code hosts to match against, because which hosts a box can push to is set by the seat's own [environment and setup steps](#credentials-and-the-run-environment), which it deliberately never names, and a seat can push to a host no integration block mentions. A line counts when what follows the label is a URL carrying no credentials, or a name git accepts for a branch, alone on the line — a list marker, emphasis or backticks around it are fine, and `Delivered: the fix for the flake` is a sentence, not a ref. A report that names none is read for pull and merge request URLs by their **shape**, on any host and port (`/pull/N`, `/pulls/N`, `/-/merge_requests/N`, `/pull-requests/N`, `/pullrequest/N`) — a guess, since a pull request the run only read looks exactly like one it opened, which is why a named ref always wins over a scraped one, and the report's over the CLI's final message. The refs ride the run's phase record and the collected executor's record, which the reviewer reads under `## What the agent delivered`; nothing else judges the turn on them. The runner also reconstructs an **activity transcript** from each CLI's event stream — OpenCode's line-flushed `--format json` events, Claude Code's `stream-json` messages — in one shape: what the agent said, one line per tool call naming the tool and the first line of its subject (`[tool] Bash: go test ./...`, `[tool] Read: <file>`), a failed call marked with the first line of its error, and how a run that did not succeed ended. **Never a tool's output**: a successful result's body is a whole file read or everything a command printed, and it is what the transcript summarises. Nor the model's thinking, nor a message type the build does not know (a CLI release adds them). The error stream is the transcript only where the event stream says nothing — a CLI that failed before it could stream says why there.

**Each collected launch is a record of its own.** When the completion is claimed and the result read back, the coordinator publishes one `executor_collected` — the launch's own record, beside the executor's. It is **no phase**: the executor's phase is the round's own `agent_phase_completed` with `phase: execute`, which states the launch and its answer as one round and carries no tokens, and a launch is that round's work — a round can take more than one, when a person's answer carries a parked run on in a second launch, or a launch lost with its host is relaunched. Every spend reader files a launch under `execute`, its calls its CLI's own turns:

| Field | What it holds |
|---|---|
| `turn_id`, `iteration`, `launch_id` | The identity. `iteration` is the executor round that launched it, written onto the run's record beside the turn's parked state; a round can launch twice (a run carried on with a person's answer is the same round), so `launch_id` tells the launches apart |
| `started_at`, `duration_ms` | From the launch, dated by the store when it named the job, to the collection on the node that read the result — so the completion poll's interval is inside it |
| `input_tokens`, `output_tokens`, `total_tokens`, `cache_read_tokens`, `cache_write_tokens` | What the run spent, as its CLI reported it (for OpenCode, its session's totals — see above) |
| `cost_usd` | What the launch's CLI said it billed, where it says so. On this record only — it is the launch's fact, and the collected executor's record is one a run that parked on a question does not get until it is answered |
| `provider_key`, `model`, `coding_agent`, `sandbox_id` | The `providers.llm` entry the launch picked, the model it pointed the agent at (empty when it named none), the CLI and the box |
| `cli_turns` | The CLI's own count of the turns the launch took, where it reports one (Claude Code's `num_turns`; OpenCode reports none) — what every spend figure's `calls` counts the launch as, one where it reports none |
| `response`, `delivered_refs`, `activity_transcript` | The findings report, what it delivered, and the transcript |
| `delivered_refs_elided`, `activity_transcript_elided_lines`, `activity_transcript_elided_bytes` | What the record's bounds left out: refs it does not list, and the lines and bytes of the transcript's middle. Absent when nothing was left out |
| `failed`, `error`, `error_kind`, `notes` | `failed` and `error` are set, with the kind `launch_failed`, when the launch did not succeed — a failure of its turn, as a failed phase's is. A launch that stopped to ask a question, one a person stopped and one its host cut off are **not** failed; their `notes` say which |
| `work_item`, `work_key`, `conversation_key` | As on the turn's phase records |

It is published **once per launch**, however often the tail is retried: a resume that fails hands the completion back and the retry collects the same job again, so the run's coordination record says the launch's record already went out, in the same write that hands the claim back — exactly as the [charge](#budgets) is recorded. A publish the broker refused is not recorded and is offered again by a retry, if one comes; telemetry never fails the resume. Because every spend reader folds these records — the spend rollup, each data node's daily usage and the turn list — the executor's run's tokens are counted where every phase's are, in the Execute band; before this record existed they reached the budget counter and nothing a person reads.

**The whole record fits its event**, because the broker refuses one over 8 MiB whole and this record is the launch's only spend record — refused, it would take its tokens, cost, report and refs with it. Every piece of text a box wrote that rides it has a bound, in bytes: the report, the failure's detail and the transcript **256 KiB** each (`sandbox.MaxRunTextBytes`), the question in its `notes` one sentence of at most 300 bytes, and the delivered refs **16 KiB** (`sandbox.MaxDeliveredRefBytes`). JSON can grow text six-fold (a control byte becomes `\u00XX`, `<` and its kin `\u003c`, an invalid byte `\ufffd`), so the worst case is (3 × 256 + 16 + 1) KiB × 6, about 4.6 MiB, inside the ceiling with room to spare. What happens past a bound depends on who reads the piece:

- **The report and the failure** are what the collected executor's record carries and the reviewer judges, so one past the bound is **condensed by the seat's auxiliary model** (`llm_auxiliary`, falling back to `llm`) and labelled as condensed — never cut, because a report's opening read as the whole report is a run that seems to have said less than it did. The failure's detail is any piece the engine could not read, the exit status, the coding CLI's own error and the **end** of its stderr, in that order — the stderr read from its end, with its unread start said by size (see *What is read whole, and what is read as a stream* below). The whole of it is held to what one condensation reads (`sandbox.MaxCondenseBytes`, 2 MiB) less 1 KiB the engine keeps for a sentence of its own it may put in front: the engine's sentences are taken as they are, and the stderr gets what is left after them. A failure still past what a condensation reads — a CLI error as long as the file it came from — keeps whole lines from its start and its end up to that, with the lines between counted where they were, and that is what the model is shown. Where no model can condense one, it keeps **whole lines** up to the bound and says how many it left out: a report from its start (it is read from the top), and a failure from both ends — its first 32 KiB, an eighth of the bound, where the engine states the exit status, the CLI's own error and any piece it could not read, and its end for the rest, because the line naming what broke is the last one printed. Kept from its end alone, a failure with a long stderr lost every one of the engine's own sentences.
- **The question** a run parked on is never condensed: the run asks it through `ask_and_wait`, which refuses one past its bounds (a one-sentence question of at most 300 bytes, a context of at most 16 KiB, the decision's own caps) before anything is recorded, so the run rewrites it while it can, and what the person reads is what the run wrote.
- **The delivered refs** are read from the whole report with no count to them — every `Delivered:` line it writes, or every pull-request URL its prose holds where it names none — so they are redacted, deduplicated and listed up to 16 KiB — more than a hundred and sixty pull-request URLs of the usual length — with the rest counted (`delivered_refs_elided`) and said where the reviewer reads the refs, never dropped unsaid.
- **The transcript** is read by a person — no model and no prompt reads it — so it is not condensed: a long one keeps **whole lines from its start, up to 64 KiB, and from its end, up to 192 KiB**, with one note line where its middle was, naming how many lines and KiB were left out. The end gets the larger share because it is where the run's conclusion and what broke sit; the start is kept because it is the run's plan and its first look at the code — some 370 tool lines at their longest, since a tool line is the tool's name and at most 160 bytes of what it ran, never its output — which a log cut to its end loses entirely. A single line longer than its half keeps its own start (or end), on a character, marked `…`. The counts also ride the record as `activity_transcript_elided_lines` and `activity_transcript_elided_bytes`, so the dashboard's Activity fold says the record is not the whole log. The bound is applied once, by the coordinator, after it redacts the whole transcript again — never by a runner, so a runner that forgot it cannot publish an unbounded one.

Everything read out of the box is **secret-redacted whole, before anything is bounded** — a secret straddling a cut would otherwise survive as a fragment the pattern no longer recognises — and again at the publish. That includes the preview a transcript line shows of what a tool call ran, why it failed and how a run ended: each is redacted whole before it is cut to its 160 bytes, because a token whose start fell just before the cut kept most of its body, too little for any later pass to recognise and enough to identify it. A private key — PEM's armour, or OpenPGP's `-----BEGIN PGP PRIVATE KEY BLOCK-----` — is the one shape that spans lines, and it is redacted as a block, **read by its structure** whether or not its END line was written: its headers (RFC 1421's `Proc-Type:`/`DEK-Info:`, OpenPGP's `Version:`/`Comment:`), its base64 lines at the encoder's width and one shorter last line — then its END, when it has one — with any number of blank lines among them (a key printed double-spaced is one key) and at most one other line between two of its own (a log line another process wrote in the middle of it). A key is read **forward from its BEGIN, and back from an END** that no BEGIN's block reached: a body cut off from its BEGIN by two such lines in a row, or whose BEGIN is not in the text at all — a stream's end read from inside a key. Read back, a full line also has to read like a key's, carrying upper and lower case letters as base64 of random bytes does, digit or none: a line of random base64 lacks a digit about once in fifty thousand, and lines a key's encoding fixes in part (an EC key's second line, a last line of forty-odd characters) far more often — so a few lines of CamelCase identifiers or mixed-case paths directly above a bare END line are read as its body and redacted with it. The END's own line is read both ways where what comes before its armour ends in base64 — a diff's `+` is a prefix and a line of base64 both — and the block reaches as far back as either reading does. Two lines in a row end a block, and an END after them reads back **across them** to a line of the key exactly as wide as an encoder writes one — 64 characters (PEM as OpenSSL and Go write it, PKCS#8, OpenPGP), 70 (OpenSSH) or 76 (MIME's base64, which Java's, Python's and .NET's encoders write), one more under a diff's `+` — from a full line of the same width, from the body's last line or from the END itself, with the body's last line and one more line another process wrote above the two; OpenPGP's checksum line (`=` and a CRC-24, after the body) is read back from as its END is. A password prompt — a line ending in a password's key and its separator (`Password:`, `hunter2 Retype password:`, `pwd=x password:`), that key neither the value of a key before it (as in `pwd= password:`) nor part of a token run into it (`sk-…Pwd:`) — is not one of the two: the read back passes over it, so another process asking for a password three times between a key's lines and its END no longer publishes the key above, and the prompt is redacted with the key. So a key read from inside, its BEGIN not in the text, is redacted whole when another process broke it with two lines, wherever they fell, and with two and one more. What no read reaches is published: where three lines in a row, two whose nearest full line of the key above them is at no encoder's width (a key wrapped at some other width), or two and two more with only the body's short last line between them part a key, the part above them is published when its BEGIN is not in the text, and the part below them when it holds no full line — the short last line alone, BEGIN or none. Read back, a blank line under a wrapping that marks every line — a line number, a grep's context mark — counts as a line between two of the key's, so a key printed double-spaced under one and broken by one line as well is broken by three. Where the key's BEGIN is in the text, the block read forward from it and the one read back across the two are one, and so is their marker: the two lines are redacted with the key, as a single line another process wrote into it is. A line that is not a key's straight after a BEGIN ends its block before it has a body, so an END after it closes nothing: a BEGIN line with no key under it, such as a grep's match for the armour line, is left as it is and takes nothing after it, even when a later grep matches the END — and read back from that END, the same prose is where the read stops. Every wrapping a key reaches a transcript in is read the same way: a JSON string with its line breaks escaped (once or twice), a line number, timestamp, grep prefix or diff `+` on every line (shaped like the armour line's own), a string concatenated across lines, a line `echo`ed at a time, or the whole key on one line, its encrypted headers too — and two whole keys flattened onto one line (`echo $A $B`, an env dump with the breaks stripped) are two keys, each closed at its own END rather than the first abandoned the moment the second's BEGIN appears. Read forward, the body's short last line that ends in the text around it — the quote closing the string the key was written into — ends the block at its base64 unless it reads like a piece of a key (below), and what follows a full line on its line ends nothing, since only the last line is short. **A cut is read wherever it lands.** A tool that bounds what it shows keeps a key's line up to a point (`MIIEow…[...truncated]`, or `MIIEow…` before a bare ellipsis), from a point (`[… 812 bytes truncated]q3O4Ou…`, a window's first line) or both, with its mark between them (`MIIEow…[… 2,345 characters truncated …]…Xyz`) — on one line, on every line, or every line cut short with no mark at all. What is read is the piece of the key such a line still holds where a key's line would stand — the run of base64 that opens the line after its prefix, or the one that ends it before its suffix, eight characters or more in upper and lower case with a digit — and never the mark, which no two tools spell alike; once a piece has said a cut wrote into the line, the run at its other end is the key's too when it reads like one, digit or none, since the first sixteen characters of an RSA key's line (`MIIEogIBAAKCAQEA`) hold none. Read forward, such a line is a line of the body, its key material running to that run or to its last piece, and the block goes on from it; so is a short line that is a piece straight after the BEGIN or with text after it (the head a cut kept and a short last line a quote closes read alike), and a short piece with another below it, since a body has one last line and two in a row are a key cut short on every line; and so is the tail a cut kept between a BEGIN's armour and its line break. Read back, every line a cut wrote into is a line of the body, however narrow and whichever end of it the cut kept, and so is a short line that is a piece — so a key cut on every line, from its start or its end, behind a mark or with none, is read back from its END whole — and since the cut hid the width the line was at, a read across two lines another process wrote lands on it from a line at an encoder's width below, and goes on from it to one above. And a key written on one line is read back from its END on that line as it is read forward from its BEGIN, across one cut in it — once, as a block carries one line that is not the key's between two that are — to the key's runs beyond the mark, when they hold one at a full line's width, or, where nothing written up to the END reads as the key's, one exactly as wide as an encoder writes or wider than any, since a path in mixed case before a grep's match for the END is forty characters too. Nothing another rule redacts is a piece of a key: a password's key, its separator and its value, and a token, are left to their own rules, so no cut's reading takes part of one into the key's redaction and publishes the rest. What a cut leaves that reads like no key's is published: a piece shorter than eight characters, or one with no digit or in one case alone, where it is all a line holds of the key — and that line is one that is not the key's, so straight after the BEGIN it ends the block before it has a body, and two of them together end a block anywhere, the key's lines below published unless an END reads back to them; a piece between two marks, at neither end of its line; on a key written on one line, what lies across a second cut, or across a cut beyond which no run of the key is that wide; with no END below, the tail a mark on a line of its own kept after a head cut short, and the key's lines after it; and, read from inside, the lines above two another process wrote into a key cut short on every line. A line of prose beside a key that opens or ends in such a run — `=== RUN   TestSHA256Sum` above an END — is read as one a cut wrote into and redacted with the key, and lines of prose that each open or end in one, straight above an END, are read as a key cut on every line, as far up as they go; a line holding such a run anywhere else is not, except an END's own line, where such a run before the armour, up to one shorter run after it, is read as the body a window kept, key or none (`=== RUN   TestSHA256Sum x -----END PRIVATE KEY-----`, a wrapping's gutter `[Worker1A] ` before the END). And after a key whose END was never written, a short line after a line a cut wrote into is read as the body's last line, as it is after any full line, so a word the tool printed next is redacted with its mark. A line another rule names is no line of the key — a token, or a password's key and its separator: under a key whose END was never written, `Password:`, or a `pwd=` whose `=` ends its line, is a line interrupting the key rather than its last, so the value on the next line is redacted with the key, or by the password's rule when it cannot be the key's last line — never published with the separator left behind. What that costs is a key's last line that ends in a password's key and `=`, about one key in fifty thousand, which is published when no END follows it. Another block's armour, a certificate's, ends a key's block in either direction, on a line of its own or on the key's, and so does a key already redacted, whose marker stands where its armour stood — which is what makes text redacted twice read as it did once: a one-line key whose END was lost is redacted up to the certificate or the next key written after it, and so is one whose END comes after a word. A password's key is read **as the text writes it**: closed by the quote or the markup it is written in (`{"password": "x"}`, `**Password**: x`, `` `password`: x ``) — a quote only where it closes the key's own string, a name such as `"db_password"`, so a longer string ending in the word (`"POST /auth/password": () =>`) is no key — and separated from its value by `:`, `=` or the operator a language assigns or compares with (`:=`, `==`, `=>`) — read with a bare `:` or `=` straight after the key, a JSON object's password was no key at all, and an operator's second character was taken for the value. The markup that closes what the key's line opened before its label is the key's too (`**Root password:** x`, `| Password: | x |`, `| **Password:** | x |`), and the value is read after it — on its line, or, where nothing follows it there, on a line below as after a separator (`**Password:**` over the value, `- **Password:**` over the value indented under it); a quote is no such markup, since a logged string closes with one and what follows it is the next field. A password's value is read **where its wrapping puts it**: when what follows `password:` on its line is only the punctuation the wrapping writes after every line — the quote closing an `echo`'s string and its redirection, the `" +` of a string concatenated across lines, a table's ` |` — or nothing, the value is on the first line after it that is not blank, read past the **gutter** that line opens with — the start of what the key's line has before the key (a reader's line number, a grep's context mark, a diff's `+`, a log's timestamp, the quote opening a concatenated string), shaped so that a number moving on from line to line, or a timestamp's fraction written on one line and not the next, is still the gutter, and ending where a word of both lines does — and ended before the same punctuation, or before what a list's or a concatenation's last line closes with instead, or before the `>>` that appends to a file the key's line opened with `>`. The wrapping's blank lines between — an empty numbered line, `echo "" >> key.pem` — are passed over; a line holding a password's key where the value would be ends the read, since its key names what is there, while a key further along the line is the line's own and the value before it is still read; a line that does not end in that punctuation says it was no wrapping's, so the punctuation is the value, as `***` is; and a word in any script, or an empty quoted string, is a value, never punctuation. The value alone is replaced, so the gutter, the punctuation and the blank lines stay. Taking the first word after the separator wherever it stood, the rule redacted the wrapping's own syntax — an `echo`'s closing quote, the quote that closes a concatenated string's piece, the number of a numbered line a tab follows or of a blank one — and published the value on the line after. What is still published: a value under a quoted key whose name is more than letters, digits, `_`, `-` and `.` (`{"Admin Password": "x"}`); a value `printf '%s\n'` writes a line at a time (the escaped break is inside every line's own prefix); a blank numbered line that lost the tab after its number, or a log's blank line that lost the space after its timestamp, which is read as the value; a value shaped like the word the key's line opens with, a space after it on both (`pass2 next` under `pass1 Retype password:`), which is read as the gutter as one timestamp is under another; a value on a line that opens with the punctuation the key's line has straight before its key, after words that line does not repeat — a list's dash after a logged message (`msg: - Password:` over `- hunter2x9`), a string's first line (`{"text": "> Password:\n> hunter2x9"}`) — which is read as the value, since the gutter is read from the line's start and ends where the two lines' words part; where the markup that closes the key ends its piece of a string (`{"text": "| Password: |\n| hunter2x9 |"}`), no value is read at all; a value written over several lines — a YAML block scalar (`password: |`, `password: >-`), a YAML sequence under the key (`- hunter2`), a heredoc — of which the first word at most is read; a diff whose key is on a context line and whose value changed, of which the removed line's first word is read and the added value published (where the values are indented, that word is the `-` alone, and both are published); a value under a gutter that holds an armour, or under a blank line of the wrapping whose gutter holds a password's key; under a wrapping's suffix, a value on a line that holds a password's key of its own (`echo "hunter2 password:" >> f` under `echo "Password:" >> f`), the key's line taking its own punctuation for its value instead, or the closing of the markup that alone ends it (`| Password: |` over `| > Retype password: |`), since redacting the value would change how that line ends once the second key's value is replaced, and a second pass would read the first key's value elsewhere; the part of a value after an escaped break inside it when that part is punctuation alone (`pwd=ab\n!!`), which reads as a string's closing quote; and a key's piece on the line of a value read below a password's key that a key's END line goes on to (`-----END RSA PRIVATE KEY-----|passwd:`): the keys are read with that value claimed, in the text as written, so the piece is no line of a key, while the rule reads the value in the text the keys' blocks leave, where the END's line is a marker that can join the value's line to it or take the gutter the END's line opened with, and reads another value, or none — and a second pass, the block gone, can read the piece as a key's and redact it. What it costs is a line after the key that ends as the key's did and holds no value: a prompt logged as `msg="password:"` over `msg="connected"` has `connected` redacted, where the rule used to replace the quote; a key a quote closes whose separator ends its line — a Go `case "password":` — has the next line's first word redacted, and so does a JSON key whose value is on the next line, as it should; a code span in prose, `` `Password:` and a value ``, has the word after it redacted; and a name in a string or a code span that is no key where it stands is read as one, so a choice between two strings that opens with one (`masked ? "password" : "text"`) has the other redacted, and the shell's `` `pwd` `` before a colon (`` -v `pwd`:/app ``) the path after it. What the other rules write once the keys are read leaves a second pass nothing new to read either: a password's rule replaces its value alone, so `password:` and the line break before a value on the next line stay where they were, and an escaped line break inside a value stays too, the value redacted on either side of it (`pwd=ab\ncd` becomes `pwd=[REDACTED:password]\n[REDACTED:password]`, since whether the `\n` is a break or two characters of the password the text does not say); a value or a token stops at an armour or a marker; and an armour line that holds a marker — before its armour or after it, which is what a pass leaves beside an armour it read no key from — holds no key read across its lines, and a key written on it is read back from its END no further than the marker. So the coordinator, redacting again a transcript the runner redacted, changes nothing — save the key's piece beside an END line that goes on to a password's key, above. A block is never read more than 64 KiB from its armour (`redact.MaxKeyBlockBytes`, the largest key there is more than twice over in any wrapping), so a BEGIN on a line that runs on past that — a minified bundle naming the armour — holds back nothing after that line. And the pass stays linear on a line of many armours: each one's scan stops at the armour next to it.

**What is read whole, and what is read as a stream.** A file meant to be read whole — the findings report, the result line, the exit status — is read whole, and one past **32 MiB** (`sandbox.MaxFileBytes`) is refused rather than read in part, on the engine host exactly as on a remote box, because a clipped report reads as a finished one. A refusal degrades **only that piece**: it is described by its size, the run reads as not succeeded with that as the reason, and its tokens, delivered refs and transcript are still collected, charged and published. A run's **machine streams** are never refused for their size, because the engine keeps a bounded share of each anyway: the event stream is decoded a line at a time in bounded memory (a single line past 32 MiB is skipped and counted where it was), and the error stream is read **from its end** — at most what one condensation takes beside the engine's own sentences in front of it (2 MiB less 1 KiB, and less those sentences), with its unread start said by size, because a process's conclusion is the last thing it prints. It used to be read to the whole 2 MiB and carried behind those sentences, which put every failure with a long stderr a few hundred bytes past what a condensation reads, so none of them was ever condensed. Reading them whole used to refuse a run for the size of its own log: a poll that could not read a 32 MiB stdout never reached its liveness probe and held a finished-but-hung or dead job's seat for good, and a collection that could not read it lost a result its report file held. On the engine host **every access to a box's files goes through the box's home opened as a root** (Go's `os.Root`): a read, a write, a directory made and a file removed alike, by a name relative to the home, walked a component at a time. A link on the way is followed only to somewhere beneath the home; one that leads out of it — an absolute link, or a relative one climbing past the home — is refused at the access, whenever the box put it there, in the same words as a path named outside the home. The engine's records about a box are reached the same way, through the box's `records/`. And a box's file is read only if it is a **regular file where it lies**: the other side of a `container` box's mount is the agent's, and a named pipe made at the done marker used to block the completion poll for good (an open waits for a writer and cannot be cancelled), so anything that is not a regular file — a symbolic link at the path included, whether it leads nowhere or was put there after the path was checked — is refused, naming the path and what it is, and never read as an empty file. So is anything but a directory where a directory on the way to the file was — a named pipe in place of `.crewlet/`, say — which is refused at once, naming that path and what it is, rather than opened. The poll reports it; a collection degrades **only that piece**, exactly as for one past the size cap — described for what it is, the run not succeeded with that as the reason, and the rest collected, charged and published (a refused result file is read from the event stream's last line, which is what the wrapper copies into it) — because what a path names is the box's own doing, and a collection retried over it would be refused again until the run was settled as lost. A **write** takes the same rule, and **replaces the file whole**: what the engine writes into a box on its host — a setup step's files, a coding CLI's configuration, each written after something may already have run there, and the token file the completion poll rewrites under a running job — is written to a fresh file beside the path, synced, and renamed over it in one step, so a process in the box reading the file meanwhile reads the old file or the new one, never an empty or half-written one (written in place, the token file was empty for a moment on every renewal, and a push whose credential helper read it then had nothing to authenticate with). The rename writes through nothing at the path, and it replaces only a regular file, or puts one where nothing is: a link at the path is refused rather than followed (one that led nowhere used to have its target created on the engine host) and a named pipe is refused rather than waited on, each left as the box made it, and the launch fails naming the path and what it is. A write that fails leaves nothing staged beside the path, and the new file is `0600` whatever mode the one it replaced had. An `e2b` box's file is replaced the same way, through its envd: uploaded under a fresh name beside the path, then moved over it, because envd writes an upload in place. The engine's own records about a local box are kept beside its home rather than in it (see [Local sandboxes](#local-sandboxes)) and read and written the same way, so a record that is not a regular file answers at once rather than blocking the poll, a collection or a reaper: an unusable record of the box's logins is logged (`local_sandbox_credential_map_unreadable`) and costs only the write-back of a login the run refreshed, and an unusable job record reads as not knowing whether the job runs, which keeps the box.

The dashboard renders each launch **inside the card of the round that launched it**: how it ended, what it spent, the report, and the transcript as a closed **Activity** fold. Every turn therefore reads as the executor — one card per round, from its launch, with the prompt the run was sent, to its collection, with what the run submitted and its bridged calls inside it, and the round's launches under them — then the review. A launch whose round has no record of its own — a run that parked on a question and ended before an answer resumed it — is drawn on its own, in its round's place. In the company's list of recent phases a launch is a row of its own, drawn as the executor's: the `execute` phase word with the CLI that ran it. Where the record's bounds left something out, the screens say so rather than showing the part as the whole: the Activity fold counts **kept of all** lines (`412 of 4,000 lines`, or the bytes left out of a single over-long line), and a run's **Delivered** — on its page and on its span in the turn trace — names how many more refs its report holds than the record lists (`… (+41 more its report names)`).

## Setup steps — provisioning the box

A coding agent's box needs environment wiring beyond the CLI itself: git auth, registry credentials, toolchains. Provisioning is a declarative **setup-step** framework (`internal/sandbox/setup.go`); each `sandbox.SetupStep` contributes:

- `files` — content written into the box (helper scripts, config files), at paths that are not shell-expanded but are cleaned, in every cell, so a trailing `/` or a `.` segment names the same file. A relative path is under the box's home, and so is one starting `~/`, which names the home in every cell; that is how to name a file a step needs (`.npmrc`, `~/.config/tool.toml`), since it lands in the home whichever cell the box runs in. A local box writes one only inside its home — a `direct` box's is minted per box, so no absolute path names it, and a `container` box's is its mount at `/home/user` — so a step that must put a file anywhere else has a command do it, with whatever rights that box's commands run with, and a document whose step writes a file a seat's box would refuse is **refused when it is written**, naming the step, the path and the seat (see [Local sandboxes](#local-sandboxes)). An `e2b` box writes a file at any other path — its in-box agent creates it where the path says, missing directories included, and gives it to the account every template runs as (`user`), whose home a relative path lands in — but refuses another account's home (`~name/…`) and a path naming a directory: the home itself and the directories above it, which every template has, are refused on the write too, while a directory only the template made (`/tmp`) is refused by the box at setup. A setup *command* there runs as that same account, not as root;
- `commands` — shell commands run after the files land; a non-zero exit **fails the acquisition** and tears the box down, so a half-provisioned box never receives a brief promising an environment it doesn't have, and its status says whether a wait clears the failure (75 for one that does, below);
- `env` — variables merged into the coding agent's run env (`${VAR}`-resolved with the rest);
- `optional_keys` — keys of the step's `env`, and paths of its `files`, whose value may resolve to nothing: such a variable is left out of the run and such a file is not written, quietly, where any other reference that resolves to nothing is left out the same way and the run's start logs it as a gap, `sandbox_env_unresolved` (see [Credentials and the run environment](#credentials-and-the-run-environment));
- `brief` — a paragraph folded into the coding agent's "## Your environment" block, one of its [standing instructions](#what-a-coding-agent-is-told), *telling* it what the step made true (an agent that wastes rounds rediscovering how to authenticate is slower than one that knows).

Steps come **entirely from company config** — the engine ships none of its own, git auth included — applied in order: `providers.sandbox.setup` (engine-wide, every agent seat's box) then `role.sandbox.setup` (the seat's own extras). Setup commands execute **with the run env**, so a recipe can read the engine's per-launch identity facts (`$CREWLET_AGENT_HANDLE`, `$CREWLET_AGENT_EMAIL`) and its own configured tokens at provisioning time. A reused box skips re-apply — its provisioning survives with its disk state — except for a file holding the seat's GitHub App token, which its launch brings up to date before the job starts ([below](#the-git-auth-recipe)).

**A command's status says who clears its failure.** A setup command that fails is a setup an administrator has to fix (`configuration`), whatever status it exits with, 124 included (its `timeout_seconds` ran out), but one: **75**, `EX_TEMPFAIL`, which `sysexits.h` defines as a temporary failure. A command that exits 75 says a download its setup makes failed for now, which a wait clears rather than a person (`setup_unavailable`, see [When a run does not start](#when-a-run-does-not-start)). Only the command knows which of its failures a wait clears, so it says so itself: retry a fetch where it fails, so a blip never fails the step, and exit 75 only when the service is still answering, once those retries are spent, that it is failing on its side (a 408, a 429 or a 5xx). Never put `|| exit 75` on a whole command. It says a wrong pin, a refused credential or a blocked network will clear by waiting, which none of them does, and inside a pipeline it binds to the command before it alone: `curl … || exit 75 | sha256sum -c -` never checks a download that succeeded. [Recipe 1](#bring-your-own-image) does both for npm and for `curl`.

Every step has a `name`, unique within its list: it is what a setup failure points at, and because a step's `env` and `files` are credentials, it is also what a config read masks them under and what [sending the read back restores them by](configuration.md#reads-and-export). A document with two steps of one name in the same list is refused on every write; the same name in `providers.sandbox.setup` and in a seat's own `sandbox.setup` is fine. A config read shows a step's `env` and `files` values only when each is exactly one `${VAR}` reference.

**A file is content, and it reaches the box as written.** A step's `env` is a setting: a `${VAR}` anywhere in it is the engine's, expanded at launch with the rest of the run environment. A file's body is written into the box, so a `${…}` inside it belongs to whatever reads the file there — the script's shell, npm reading `.npmrc` — and the engine never expands one. The single exception is a body that is **exactly one** `${VAR}` and nothing else: that names the whole file, and at launch the box receives the value the variable holds (the secret store first, then the engine's environment), byte for byte. So `//registry.npmjs.org/:_authToken=${NPM_TOKEN}` in an `.npmrc` is left for npm to expand from the `NPM_TOKEN` the step's `env` puts in the box, while `.npmrc: "${NPMRC}"` writes the whole stored file, into the box's home in every cell. A whole reference that resolves to nothing — nothing answers for it, or what answers is empty — is never written as an empty file: it is not written at all, and the run starts with the gap logged (`sandbox_env_unresolved`, naming `<step>:<path>`) exactly as an `env` value that does not resolve is left out ([below](#credentials-and-the-run-environment)); where the step lists the path under its `optional_keys`, the file is left out quietly. The same rule holds for a file on a seat's own `sandbox.setup`. A file whose whole body is the seat's own GitHub App token, left out because the app could not issue one yet, is written by the first poll after it can ([The git-auth recipe](#the-git-auth-recipe)).

**A tool a step installs for the run goes in `$HOME/.crewlet/bin`**, the box's own bin directory, which the run's wrapper puts first on the CLI's PATH (inside the login shell, after the profile, so a profile cannot replace it). It is under the box's home rather than a system path because a `direct` box runs as the engine's unprivileged user, and two boxes there would otherwise overwrite each other's tools.

### The git-auth recipe

Injecting a code-host token is necessary but not sufficient: a headless `git clone https://github.com/...` has no way to *supply* it and dies with `could not read Username`. The recommended wiring is a config recipe — a credential helper plus rewrites, shipped as an ordinary engine-wide step:

```yaml
providers:
  sandbox:
    setup:
      - name: git-auth
        commands:
          - mkdir -p "$HOME/.local/bin"
          - |
            cat > "$HOME/.local/bin/git-credential-crewlet" <<'SH'
            #!/bin/sh
            [ "$1" = "get" ] || exit 0
            token="$GITHUB_TOKEN"
            file="$HOME/.config/crewlet/github-token"
            [ -s "$file" ] && token=$(cat "$file")
            [ -n "$token" ] || exit 0
            ok=""
            while IFS= read -r line; do
                [ -z "$line" ] && break
                [ "$line" = "host=github.com" ] && ok=1
            done
            [ -n "$ok" ] || exit 0
            echo "username=x-access-token"
            echo "password=$token"
            SH
          - chmod +x "$HOME/.local/bin/git-credential-crewlet"
          - 'git config --global credential."https://github.com".helper "!''$HOME/.local/bin/git-credential-crewlet''"'
          - 'git config --global --add url."https://github.com/".insteadOf "git@github.com:"'
          - 'git config --global --add url."https://github.com/".insteadOf "ssh://git@github.com/"'
          - 'git config --global user.name "$CREWLET_AGENT_HANDLE"'
          - 'git config --global user.email "$CREWLET_AGENT_EMAIL"'
        env:
          GIT_TERMINAL_PROMPT: "0"
        brief: >-
          When a GitHub token is available, git authenticates to github.com
          with it automatically: clone, fetch and push over plain HTTPS, SSH
          remotes are rewritten, and the token is read fresh at every call, from
          $HOME/.config/crewlet/github-token or else $GITHUB_TOKEN. For the gh
          CLI, pass the current token on each call: GH_TOKEN="$(cat
          "$HOME/.config/crewlet/github-token" 2>/dev/null || printf %s
          "$GITHUB_TOKEN")" gh pr create ... Without a token, public
          repositories still clone anonymously and nothing you push is
          accepted. Never embed a token in a URL or print it. Your git commit
          identity is preconfigured.

roles:
  - name: Senior Engineer
    handle: senior-engineer
    sandbox:
      env:
        GITHUB_TOKEN: "${GITHUB_APP_TOKEN_SENIOR_ENGINEER}"
      setup:
        # The seat's own token as a file the completion poll keeps current
        # for as long as the job runs. Per seat, because the variable is.
        - name: github-token
          files:
            .config/crewlet/github-token: "${GITHUB_APP_TOKEN_SENIOR_ENGINEER}"
```

**The token is the agent's own GitHub App's**, issued by the engine at launch
and good for at least 50 minutes in the environment
([Acting as the app](../integrations/github.md#acting-as-the-app-the-seats-token)).
A run is never stopped by its box's TTL, so it can outlive that, and a
process's environment cannot change under it. What can is a file: a setup file
whose whole body is the seat's `${GITHUB_APP_TOKEN_<HANDLE>}` is rewritten by the
completion poll every time the token behind it is renewed — the launching
node's own poll for a `direct` or `container` box, the fleet's for an `e2b`
one — and by the launch of a job that continues in its turn's kept box, before
that job starts: no poll reaches a box while it is paused for the reviewer or
for a person's answer, and a kept box runs no setup. So the helper above, which
reads the file at every git call, always offers a token GitHub accepts. The
file is **replaced whole**, never rewritten in place: the new token is written
beside it under a fresh name and renamed over it (on an `e2b` box, uploaded and
then moved by envd), so the helper reads the token from before the renewal or
after it, never an empty or half-written file. A run launched before the seat's app was
installed starts without the token (said as `sandbox_env_unresolved`) and
without the file, and the first poll after the app can issue one writes it.
The file falls back to `$GITHUB_TOKEN` where a seat writes none, which is the
shape for a personal access token that does not expire within the run.

Each piece is load-bearing: the helper is **scoped to the code host twice** (the credential config key *and* the `host=` check in the script), so the token can never be offered to a foreign host such as a malicious submodule URL; it reads the token at git-runtime, from the file the engine keeps current or else from the env, and stays silent without one, so public clones fall through to anonymous; the `insteadOf` rewrites use `--add` because the key is multi-valued (without it the second value replaces the first and scp-style `git@…:` remotes stay SSH, failing on host-key verification in a keyless box); and commit identity comes from the engine's generic `$CREWLET_AGENT_*` facts, so commits attribute to the seat without the recipe hardcoding a name. An engine-wide step reaches every agent seat's box, including a seat that declares no token, so its `brief` is written for both: a brief that promised every box a token would send a tokenless seat's run pushing with nothing to push as. And the helper lives in the **box's home**, the one place every cell lets a setup step write it (see [Local sandboxes](#local-sandboxes)), and is written by a command rather than a `files:` entry, though a relative `files:` path would land in the same place: git has to be given the helper's absolute path, which only the box's shell knows (`"$HOME"`, expanded), and the helper has to be made executable, both of which are commands. It is registered as a shell snippet whose path is quoted, `"!'$HOME/…'"`, because git runs a helper's value through the shell and a box's home may hold a space: a `direct` box's sits under `local.state_dir` (by default `~/.crewlet/sandboxes`), and a relative one, like the examples' `./nimbus-data/sandboxes`, is resolved against wherever the engine was started. Written this way, the one step works in every cell.

The GitLab form of this recipe — same shape, `gitlab.com` scoping, `oauth2` username, MRs opened via `git push -o merge_request.create` push options — is in [GitLab Integration](../integrations/gitlab.md#how-code-authoring-works); the block above is itself the GitHub form, and [GitHub Integration](../integrations/github.md#how-code-authoring-works) covers the rest of a GitHub seat's code authoring. The repo to work in is **not** role config — it is task context: the turn's ask names it, and the run clones it inside the box with the seat's injected token.

## Commit attribution

The recipe above commits as the seat, so the seat is each commit's author. On top of that, every commit a run makes as itself credits Crewlet:

```
Co-authored-by: Crewlet <noreply@crewlet.ai>
Crewlet-Run: 6f0c2a41-…
```

- **`Co-authored-by`** is the trailer GitHub turns into a participant on the commit. The address belongs to Crewlet's own GitHub account, so the commit shows Crewlet beside the seat that authored it. It is not `Signed-off-by`: that line certifies the Developer Certificate of Origin, which only whoever answers for the code can do, and it credits nobody.
- **`Crewlet-Run`** is the turn the run belongs to, the one its page in the dashboard is addressed by (Live › Executors). Ask Crewlet's deep work has no such page, so its commits carry the co-author line alone.

It is on unless `providers.sandbox.commit_attribution` is `false`, which turns it off for every run the company launches from then on.

**Git adds the credit, not the model.** Each run's box is given a `prepare-commit-msg` hook, and the run's environment points git at it: one more `GIT_CONFIG_COUNT` entry setting `core.hooksPath`, added after the box's login profile is read. Nothing is written to a git configuration file, so your setup recipe's `git config --global` and the repository's own settings stay as they are. Git runs `prepare-commit-msg` on every commit, including one made with `--no-verify`, so the credit does not depend on the agent remembering an instruction. A coding CLI may add its own line as well, such as Claude Code's `Co-Authored-By: Claude`; the two sit side by side.

**The repository's own hooks still run.** The run's hooks directory stands in for the repository's while the run works, so every hook in it hands on to the repository's hook of the same name, from `.git/hooks` or from the repository's own `core.hooksPath` (husky's, for example). A repository hook that refuses a commit still refuses it.

**Only the run's own commits.** A commit is credited only when its author is the identity the run commits as. A person's commit that the run amends, rewords, cherry-picks or carries through a rebase keeps its author and gets no credit, because Crewlet did not write it. Amending a credited commit never adds a second copy of the trailers.

**What it does not reach:**

- A commit made through a code host's API, such as a GitHub tool that writes a file, runs no git in the box.
- A box whose git is older than 2.31 does not read `GIT_CONFIG_COUNT`, so its commits go uncredited.
- A hook the repository keeps under a name git did not have when this build shipped is not handed on while the run's entry stands.

The credit never stops a commit on its own account: a hook lookup that fails hands nothing on and credits nothing, and a credit that cannot be written lets the commit through with a one-line warning.

## Credentials and the run environment

The run env injected into each job is assembled by the engine at launch (`internal/engine/sandbox.go`), and `internal/sandbox/launch.go` adds the telemetry variables. The engine contributes only **tool-agnostic** facts:

- **The model's entry**, the role's resolved `providers.llm` entry (the chain above), whose own CLI is the seat's runner — a launch passes over an entry whose CLI has none: its whole `env`, as every call the entry makes on the engine host is given it, and whatever authenticates that CLI in its environment — the headless token in the profile's own variable (`CLAUDE_CODE_OAUTH_TOKEN`) under `subscription`, the entry's key in the profile's `api_key_env` (`ANTHROPIC_API_KEY` for Claude Code) under `api-key`, the variables `inherit-env` forwards, and, for `opencode`, the credential-named `env` keys of the provider its model names. So a gateway's `ANTHROPIC_BASE_URL` and the `ANTHROPIC_AUTH_TOKEN` it takes, a `CLAUDE_CODE_USE_BEDROCK` or `CLAUDE_CODE_USE_VERTEX` switch and the region beside it, or a proxy reach the executor's run in every cell, a remote one included. They are the values the entry's own calls use, its `${VAR}` references resolved through the secret store and the environment when the configuration was applied, with what its `auth.mode` removes from those calls removed here too (a `subscription` entry's `api_key_env`, an `api-key` entry's `token_env`); a value that resolved to nothing is left out. What tunes a call on the engine host stays there: the host's own allowlisted variables, the seat home's isolation (`HOME`, the XDG directories, the CLI's configuration directory and switches — a box sets its own) and the profile's fixed `env`. Its login — credential files, or OpenCode's exported login — travels only to a [local](#local-sandboxes) box, never to a remote one.
  **A seat that signs Claude Code in itself gets the entry's `env` without its sign-in.** Claude Code has several sign-ins under different names and ranks them — `ANTHROPIC_API_KEY` above a plan's `CLAUDE_CODE_OAUTH_TOKEN`, and a Bedrock, Vertex AI or Foundry toggle above both — so the precedence below, which is by name, cannot see that a seat is already signed in. When `role.sandbox.env` or a setup step carries any of `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX` or `CLAUDE_CODE_USE_FOUNDRY`, a Claude Code run carries that and none of the entry's sign-in: none of those six, not the profile's token or key variable, and no [credential-named](llm-backends.md#6-a-provider-key-in-env-opencode-hermes-pi) variable of the entry's `env` (a cloud's own key, such as `AWS_BEARER_TOKEN_BEDROCK`) — so a seat on its own plan is never moved onto the company's metered key or its cloud. The rest of the entry's `env` still lies beneath the seat's: a base URL or a region says where the run's requests go, not whom they are made as, so a seat on its own token still reaches its model through the company's gateway, and a seat meant to bypass it names `ANTHROPIC_BASE_URL` itself. OpenCode reads one key per model provider, so there a variable the seat names simply wins over the entry's under the same name.
  **An entry's `env` and its key sit in every box run on that entry**, remote cells included, readable by the coding agent, which runs with every permission. What the run reports back is passed through the engine's redaction, but that matches known credential **shapes** (the vendors' `sk-…` prefixes and the like), not values: a key of no recognisable shape that the agent prints into its report or transcript is carried into the phase record as printed. Give a box a key scoped to the work — a provider project with a spend limit, a gateway token of its own — rather than the company's broadest one.
- **Agent identity** — `CREWLET_AGENT_HANDLE` and `CREWLET_AGENT_EMAIL`, the per-launch facts static config cannot know, which setup recipes map into tool shape (git commit identity above).

Everything tool-specific comes from config: external-service tokens (`GITHUB_TOKEN`, `GITLAB_TOKEN`, registry tokens, a test `DATABASE_URL`, …) are declared in `role.sandbox.env` or a setup step's `env` and merely `${VAR}`-resolved: the engine never extracts, names, or special-cases them. One variable is the engine's to answer rather than the store's: a seat's own `${GITHUB_APP_TOKEN_<HANDLE>}`, the installation token of its GitHub App, issued for this seat's run alone and good for at least 50 minutes from launch ([Acting as the app](../integrations/github.md#acting-as-the-app-the-seats-token)). Precedence, later wins: the model's entry (its `env` and its sign-in), then agent identity, then setup-step env, then `role.sandbox.env`, then non-secret OTel values.

**A reference that resolves to nothing is left out, and said.** A `${VAR}` reference that resolves to nothing — whole (`"${TOKEN}"`) or embedded (`"Bearer ${TOKEN}"`), unset or set to an empty value — is never handed to the box as an empty string, by the rule every tool server is held to ([Tools & MCP](../guides/tools-and-mcp.md#shared-vs-per-role-servers)): its key is left out of the run environment whole. The run is **not refused** for it: it is the seat's turn itself, and refusing it would fail every message the seat could answer over its tool bridge for a token a pass may mint in a minute. It starts without what is missing, and its start logs **`sandbox_env_unresolved`** naming the keys, the files and the variables (never a value or a body), because a run handed no code-host token clones nothing and pushes nothing, and that line is how an operator finds out why. It says why the value is missing: at info while a [provisioning pass](integration-reconcile.md) is minting it for the seat — the same `${VAR}` an `mcp_env` code-host credential points at, for example; a run launched once its seal reaches the node is given it — or while the seat's GitHub App is not yet created or installed, for its own `${GITHUB_APP_TOKEN_<HANDLE>}`, whose token file a running job is handed by the first poll after the app can issue one; and as a warning, with the remedy, where nothing will mint it, that pass cannot until somebody acts, or GitHub didn't issue the seat's token ([each story](#failure-modes) is told under its own field). The engine's own identity facts never refuse a run: each is contributed when it has a value, and a seat `email:` naming a variable nothing sets is left out of `CREWLET_AGENT_EMAIL` and said on the same line, so a setup step's `git config user.email` reading it empty has a reason beside it.

A setting a run can go without — a test `DATABASE_URL`, a proxy — is declared by its **key** under `optional_keys`, beside the `env` that writes it: on `role.sandbox`, or on a setup step, where a file's path may be listed too. Such a key whose value does not resolve is left out of the run environment whole, never handed on half-substituted, as any other is — but quietly, since its absence is expected, so the line names only the gaps that are not:

```yaml
roles:
  - name: Backend
    sandbox:
      env:
        GITLAB_TOKEN: "${SWE_GITLAB_TOKEN}"            # expected: a run started without it has no code-host
                                                       #   identity, and sandbox_env_unresolved names it
        DATABASE_URL: "postgres://${TEST_DB_HOST}/app"
      optional_keys: [DATABASE_URL]                    # left out when TEST_DB_HOST resolves to nothing
```

The declaration that counts is the one beside the value that won: a key in `role.sandbox.env` replacing a setup step's is judged by `role.sandbox.optional_keys`, never by the step's. A value a provisioning pass is still minting for the seat, or the seat's own GitHub App token before its app can issue one, is said at info whatever the declaration says — an `optional_keys` entry does not quiet it, since it is on its way rather than expected to be absent — and the run starts without it; a run launched after its seal reaches this node, or after the app is installed, is given it. An entry that leaves nothing out — a key or path its block does not write, a variable's name where its key belongs, or a key whose values reference nothing — is refused on the write that adds it (an [admission rule](configuration.md#what-a-stored-revision-is-held-to)), because the key it was meant for stays expected. Resolved values are injected only into that sandbox's process env and die with it; the DB stores only the `${VAR}` references. Shared infrastructure secrets — above all the OTLP backend's ingest token — never enter the sandbox at all (see below).

## MCP inside the sandbox

The coding agent is itself an MCP client, so the engine renders the seat's scoped servers into the box, beside the [tool bridge](#the-tool-bridge--a-seats-own-tools-from-inside-a-box) every box is given as the server `crewlet` (`internal/sandbox/mcprender.go` → Claude Code's `mcp.json` in the run's work directory, via `--mcp-config --strict-mcp-config`, or the [configuration an OpenCode run is handed](#opencode)). Scoping is at the **server level only**: `role.sandbox.mcp.servers` names which of the role's `mcp_servers` to expose, and the coding agent gets **every tool those servers expose**. There is no per-tool allowlist — OpenCode has no allowlist flag and Claude Code runs `bypassPermissions` headless, so a curated list couldn't be enforced uniformly and would give a false sense of restriction. A role that shouldn't reach a surface simply doesn't list that server.

Credentials from `role.mcp_env` are resolved into the rendered specs (HTTP servers get them as headers, stdio servers as env), so the in-box server instances authenticate as the seat. So is every `${VAR}` in the server's own `env`, `headers` and `url`: the engine resolves each through the secret store and its own environment, exactly as it does for the server's child on the engine host, and never writes a `${VAR}` reference into the box for the coding CLI to expand — OpenCode does not read that syntax, and Claude Code would read it from the run environment, which holds a company secret only where the seat's `sandbox.env` or a setup step repeats it. (What OpenCode is handed is the resolved value, in a file of its own its configuration names — see [OpenCode](#opencode).) So a server's reference means in the box what it means on the engine host: one the secret store and the engine's environment do not answer is not answered by a value the run environment happens to carry either. The connected server names are also listed in the coding agent's environment brief. A server any of whose values does **not** resolve — the seat's or its own, under a key the server does not [declare optional](../guides/tools-and-mcp.md#a-key-that-may-go-without-its-value) — is not rendered at all, by the rule the server's own child follows ([Tools & MCP](../guides/tools-and-mcp.md#shared-vs-per-role-servers)): handed an empty token, an in-box server refuses to start or acts as nobody, and the agent would spend a round finding that out. A key it does declare optional is left out of what the box is given. The run logs `sandbox_mcp_server_withheld` naming the variables: at info while the integration that mints them is minting them — a run launched once the seal reaches the node, or for the agent's GitHub App token once its installation is recorded, is given the server — and as a warning where they are unset, where that integration cannot mint them until somebody acts, or where GitHub didn't issue the seat's token.

A named server the company's `mcp_servers` does not carry is **skipped**, with a warning, rather than rendered empty — the agent must never be offered a server it cannot reach, because it spends a round discovering that. The same holds for a server whose `transport` is neither `stdio` nor `http`. One skipped entry does not cost the seat the rest of its surface.

Three practical caveats:

- **A cloud sandbox cannot reach your laptop.** An HTTP MCP server (or a git host) on `localhost` / a private LAN address is unreachable from an E2B cloud box. For laptop-local development stacks, use a self-hosted E2B `domain` on the same network, a tunnel, or scope those servers out of the sandbox.
- **stdio servers must exist in the box.** A stdio spec is *spawned inside* the sandbox, so its command must be present in the template (E2B's prebuilt templates cover common cases; anything else belongs in a custom template or a setup step).
- **A container box reaches the engine host by name.** An HTTP server the engine host serves on loopback is handed to a `container` box under the runtime's name for that host ([Local sandboxes](#local-sandboxes)), so a server the engine's own child reaches at `http://localhost:3000` is reached from the box too, on Linux as long as it listens beyond loopback.

## The tool bridge — a seat's own tools, from inside a box

Every run is its seat's executor ([LLM Backends](llm-backends.md#the-executors-run-in-a-box)). Beside the servers above, it needs the seat's *whole* tool surface, including the engine's own builtins and the delivery tools the turn is judged on. Those cannot be shipped in: most are MCP children holding the **seat's** credentials, several are engine control, and a box is given only the credentials the seat acts as.

So the box also gets **one** MCP server on the engine, `crewlet`, and every call comes back out:

```mermaid
flowchart LR
    BOX["The run's CLI, in its box"] -->|"MCP over streamable HTTP: POST /mcp/{token}"| SURF["The seat's live tools.Surface: grant, skill guard, recording"]
```

**The dispatch is the seat's own.** A bridged call goes through the same `tools.Surface` a phase on this host calls, so the grant, the [required-skill guard](tool-skills.md), the failure shape and the recording are all the ones an operator already knows. `internal/api/mcpbridge` never grows a second idea of whether a tool is allowed — a second copy would drift, and it would drift on the security half. The MCP server behind the route is the one a run on this host reaches over its unix socket (`internal/toolsession`), kept in step with the seat's live tool set: a tool the run activates is listed on its next request, the activation's answer held until the box's CLI has re-read the list.

**Every call is held to the run, as a phase holds its own.** What the bridge adds is what a detached run's calls are owed that a surface cannot know: the **seat's fence**, before and after each call — once this node stops holding the seat, or a person asks the seat to stop, that call and every one after it are refused rather than made as a seat the node no longer speaks for, each written on the run's record as refused; the **order the calls arrived in**, fixed as each is admitted (`Surface.Admit`) rather than as it returns, so a response's calls made at once read the same call log a re-run would; the **run's context, never the request's**, so a box that disconnects mid-call abandons only the answer and never a tool half-way through a write; a **panic contained** — the call answered as failed, logged with its stack, and the run's tools closed to it; and a **run that is over refuses** — a call reaching a session after its run ended, or after a relaunch replaced it, is answered and not run. A call whose arguments did not parse is answered with the same words a phase on this host uses, never run on an empty object — though a box's CLI is read by no record, so an object the CLI made of what its model wrote (Claude Code's of an array) reaches the tool as the CLI sent it, and the tool's own validation is what judges it. What it does not add belongs to a tool loop — rounds, a terminator, a per-request budget — because an executor run's loop is its CLI's own, its turn is parked while it runs, and those are settled when the run is collected and its turn resumes (a person's notes reach the run over the bridge too, between its steps: see [Notes to a running run](#notes-to-a-running-run)).

**The credential is per-job and expires with the run.** The box holds no API token; what admits a request is a signed token in the endpoint's own path, the same shape the OTLP receiver uses (`internal/runtoken`). It names the run, the **seat** it acts as and its **job** — the launch id the store mints and keeps on the run's durable row — never a process, and it is signed under the fleet's keyring. Two gates stand behind it: the signature says this fleet minted it, and the session map on the node holding the seat says the job it names is still the run's, so a box that outlived its run keeps no working key, and a relaunch is a new job whose old box's token stops resolving. The session is opened as soon as the job is named and before any box exists, so a launch that cannot be served is refused with nothing started.

**Where a box dials it depends on its cell and its node.** A `direct` box is a process tree on its node's own host, so on every node that binds `api.port` it dials that node's own listener on loopback and needs no setting at all. On an `ingress` node that is the listener the bridge is served on (`api.public.port` where it is set, `api.port` otherwise), so a single node with an API port runs the quickstart's company as written. On a node without `ingress` it is `api.port`, where the node serves the bridge beside its probes to its own host's loopback alone — a caller from anywhere else meets the route's absence — so a seat pool with no address of its own runs its seats too, provided `api.host` takes every interface or a loopback address. Every other box — a `container` or `e2b` box, which is not on the host's loopback, or a `direct` box on a node with no such listener (`api.port: 0`) — dials `CREWLET_MCP_BRIDGE_URL`, set on every node to the fleet's bridge address as the sandbox reaches it (below); a loopback one reaches a `container` box under the runtime's name for the engine host ([Local sandboxes](#local-sandboxes)), which on Linux needs the API to listen beyond loopback. The bridge takes a call under whatever `Host` it arrives with, because the token in its path is the credential and a page cannot make one: a reverse proxy or tunnel agent on the engine host that connects to the node on `127.0.0.1` and passes the public `Host` on, as ngrok, cloudflared and Caddy do unless told otherwise, reaches it as a box that dials it directly does, on its MCP endpoint and the run's notes route alike. The one session whose `Host` is judged is an Ask Crewlet [deep-work](../guides/assistant.md#where-a-run-happens) run held to the engine host's loopback: it admits a call only from that loopback, under a loopback host name or the runtime's name for the engine host (`host.docker.internal`, `host.containers.internal`, the name a call from Docker Desktop or Podman's machine arrives under), and refuses any other with `401`, because a page in a browser on the host, under a name its author points at `127.0.0.1`, can send requests there, and only ever under its own name. A launch whose box has no address to dial is refused naming what to set — `api.port` on an `ingress` node that binds no listener for the route, the variable for a cell it is missing for — rather than starting a run that cannot call anything, and each such cell is said once when a company is applied (`executor_bridge_unreachable`), before any turn is refused for it. A box off its host reaches a node without `ingress` through the ingress nodes, whatever that node's own `api.port`. The phases on this host need none of this: their runs reach their tools through a socket, with no listener at all.

**Every bridged call acts as the run's seat.** Because the token is the credential, the caller is the seat the run belongs to, and the bridge states that on every call — the same identity a turn's phases on this host carry, with the same four grants — so the [authority table](identity-and-access.md#the-authority-table-one-function-decides) decides a bridged `list_work_items` exactly as it decides the native one. It is set by the bridge itself rather than read off the request, because `/mcp/` is exempt from the credential guard: the guard resolves a box that presents nothing as anonymous, and a development build started with `-dev-principal` resolves it as that principal. Neither may decide a seat's tool call, so the bridge replaces the request's answer with the seat's on this route and nowhere else. A session whose tool surface is bound to no seat is refused at `Open` rather than served.

**Every call is written down where a resume can read it.** A phase on this host keeps its calls in memory and the turn writes them at the end; a bridged run's calls are made by a process outside the engine, minutes apart, possibly across a restart. Each one is appended to the run's own coordination row — with its order, when it started, how long it took and which server answered it, a call refused once the run's tools had closed included — bounded, dropping from the *middle* rather than the start: how a run began and how it ended are what explain it. A resume orders the calls by the order they reached the session in. Without that, the reviewer of a resumed run judges a turn whose entire tool log is gone, which the delivery check reads as a turn that acted on nothing.

**One address for the fleet; the seat's holder answers.** A session is a live tool surface in the process holding the run's seat (the seat's MCP children, its skill guard, its recording), so only that process can answer a call — but the box need not dial it. `CREWLET_MCP_BRIDGE_URL` is the **fleet's** address: any node that serves the API (the `ingress` role), a load balancer in front of several included, and every node is given the same value. The node a call lands on reads the seat's lease, which the token names, and relays the whole HTTP exchange to the node holding the seat over the broker (`internal/httprelay`), event stream included; the holder answers it from its own session. So a node without `ingress` — one that serves the network its probes and nothing else, a [satellite](../guides/satellite-nodes.md) at the edge of a network included — runs agent seats as well as one that serves the API: nothing a box off its host needs is a route on it, and its own `direct` boxes dial it on loopback (above). A call for a seat that node has since handed on is relayed to the seat's holder from there as from any `ingress` node. Ask Crewlet's [deep work](../guides/assistant.md#where-a-run-happens) has no seat whose lease could name a holder, and nothing takes its session over, so its token names the process that opened the session and a call for it is relayed straight there; once that node runs a later process, the call is refused. With Tier A `api.public.port` set, the route is served on the ingress nodes' public listener instead of `api.port`, so the bridge URL names the public port and a direct box dials it there ([Exposing webhooks without the admin API](../guides/deployment.md#exposing-webhooks-without-the-admin-api)). The token is signed from Tier A `secrets.keys`, under a domain that separates bridge tokens from telemetry tokens; every node holds that keyring — a node without one does not start — so any node can tell a token the fleet signed from a forged one before it relays a call, and a keyring that cannot sign for the fleet is refused by name when the bridge is built. Every relayed request and every frame of its answer is signed under that same keyring ([ADR-0031](../../adr/0031-every-state-log-record-is-signed.md)), because the broker authenticates nobody and both are instructions.

**A call waits for a holder that can answer it.** A call that lands while no node can answer — the seat's holder has died and its lease not yet run out, or a peer has the lease and is still taking the seat — waits, reading the lease again, for up to two seat-lease lifetimes (90 seconds at the default `coordination.lease_ttl_seconds`): one for a dead holder's lease to lapse and one for a peer to claim the seat and open its running jobs' sessions again. A holder that has finished taking the seat and holds no session for the job answers `401`, as for any run that is over. One that cannot be found within the bound is answered `503` with a `Retry-After`, never that the run is over, which nobody said. A holder that took a call and stopped answering before it had written a status is answered `502`, and the call is not offered to another node: it may have run.

**A run outlives a restart, or a move, of the node that holds its seat.** Because the token names the job rather than a process, whichever node takes the seat over — the same node after a restart, or a peer — re-opens the run's session as it recovers the seat, before the seat's mailbox opens: the surface rebuilt from the run's own row — the tools and skills it launched with, those it activated or loaded over the bridge — with its call log and what its bridged calls have cost carried over. Only once the seat's running jobs are recovered does the node answer that a job it holds no session for is over. The node that hands the seat on ends its runs' sessions as it releases the seat, so the box's next request is routed afresh and reaches the new holder. The box's own MCP session lived on the node that let it go, so its next request there is answered `404`, which the MCP protocol answers by connecting again — through the same URL, to the new holder, with the box's unchanged token. A session that cannot be re-opened logs `bridge_not_reopened` and never fails the recovery. A run whose ending is already decided is not re-opened, and neither is one on a seat whose pause asks for its running work to stop: the node that takes that seat ends the run as it recovers it (see [Stop now](agent-runtime.md#pausing-a-seat)), so its box never gets the seat's tools back in between.

## Notes to a running run

A person can [steer](turn-engine.md#steering-a-running-turn) a turn while its
executor works in its box. From the executor's launch until its turn ends, the turn's notes
wait on the **run's record** in the coordination store, each sealed under the
fleet keyring by the node that filed it, beside a sealed anchor naming the seat
the run serves ([ADR-0067](https://github.com/crewlet/crewlet/blob/main/adr/0067-a-note-to-a-coding-run-waits-sealed-on-its-record.md)).
The run reads them at four kinds of step, and every read is recorded on the
record by the write that hands the note over — so a note is never handed to a
model twice, and the record's read notes are exactly what the turn carries into
its review, whichever node resumes it:

- **Its brief.** A note waiting when a run is launched — the first one, a
  relaunch the reviewer sends back, or the one that carries a person's answer —
  goes into the brief, read by the write that opens the job.
- **Between its steps, through its tool bridge.** The run's bridge serves its
  notes to its CLI two ways, behind the run's own token and nothing else:
  - **`steer_take`**, a tool on the run's MCP server that a CLI's hook calls
    after a batch of the main agent's tool calls (`PostToolBatch`) or as the
    run is about to finish (`Stop`). It is **never listed**, so no CLI offers it
    to its model, and it is answered before the seat's surface sees the call,
    so it is never recorded on the run's ledger: it is the CLI asking, not the
    model. Its answer is always text — the hook's answer, with the notes as its
    additional context, or empty for nothing — and **never an error**, because a
    hook whose call failed makes the CLI drop and re-initialise the run's whole
    bridge. Only the main agent's loop takes notes: a subagent's batch, and a
    hook whose agent id the CLI did not fill in, take nothing, because a note
    handed to a delegated loop binds that piece of work alone. One answer
    carries the oldest waiting notes within **9,000 UTF-16 code units**, measured
    as the CLI measures its context, and the rest wait for the next step; it is
    answered within **five seconds**, half the hook's timeout, or not at all.
  - **The notes route**, `/mcp/{token}/steer/notes?after=<seq>` and
    `/mcp/{token}/steer/read`, which a plugin inside the CLI polls: a poll is
    held for up to **ten seconds** while no note waits, and answered at once
    when one arrives. Once the node is stopping, or the session's opening has
    ended, a held poll is let go and every later one turned away with a `503`
    and a `Retry-After` — never an empty answer a poller would ask again at
    once — and its notes wait on the record for the session's next opening, on
    this node or the seat's next holder. That holds as well for a poll the
    stopping node is relaying to another node that holds the session: the
    stopping node lets go of it at once rather than wait out the holder's hold
    on its listener's grace. A read names the notes
    (one to ten) the CLI put in front of its model, and is recorded read at the
    run's next step. Each note carries an id the CLI admits it under, unique to
    the note and the job, so a poller that admits it twice admits it once.

  A CLI takes notes here only where its run is set up to ask for them; a run
  whose CLI asks for none still has every note read, by its review. Both
  coding CLIs are set up to: **Claude Code** through [hooks](#claude-codes-hooks)
  that call `steer_take`, and **OpenCode** through a [plugin](#opencodes-notes-plugin)
  that polls the notes route and hands each note to the run's session.

  A take is pinned to the run's **job** and to a run that is launching or
  working with its ending undecided: a relaunch's job, a run parked on a
  question, a collected run and a run whose tools are closed — its seat moved,
  or a person stopped it — take nothing, and their notes wait for whatever reads
  the turn next. The bridge itself decides nothing about notes; it routes the
  call, like every bridged call, to the node holding the run's seat, whose
  inbox for the run is rebuilt from the record — so a run whose node restarted
  is served its notes by whichever node reopens its session.
- **The review's first round.** A note the run never took is read by the
  segment that reviews the run, before its first provider call.
- **After its question is answered.** A run parked on a question takes nothing
  while it waits; `steer_turn` answers `reads: "after_answer"`, and the launch
  that carries the answer carries the notes.

What became of each note is published as `agent_turn_steered`: `delivered` by
the node whose step read it, with the kind of step (`boundary`: `brief`,
`tool_batch`, `finish`, `step`, or `round` for the review) and, for a read by
the run, its job (`launch_id`); or `expired`, for a note no job ran with when
the turn ends — still waiting, or read into the brief of a launch that failed
after writing the record, whose job never started — by the node that finishes
the run's ending, and by nothing else: before the record is deleted, under an
id derived from the ending, so a retried ending records it once. A park is
never an ending. Whether a job started is on that job's own record, written when
its command is attached and kept when a park or an expired pause lets its box
go, so a note a started job's brief carried, recorded `delivered`, is never
then recorded `expired`.

A proxy between the boxes and `CREWLET_MCP_BRIDGE_URL` holds a poll open for
up to those ten seconds, so it needs a request timeout of at least fifteen —
see [Deployment](../guides/deployment.md).

### Claude Code's hooks

Every Claude Code run its launch wires to its turn's notes — every seat's
executor run; not Ask Crewlet's deep work, whose session has no inbox — is
started with a settings file of its own, `claude-settings.json` in the box's
work directory, written afresh at `0600` and named with `--settings`, which
Claude Code ranks above the repository's own settings and below a managed
policy. It holds two hooks and the setting that keeps them on, nothing else:

```json
{
  "disableAllHooks": false,
  "hooks": {
    "PostToolBatch": [{"hooks": [{"type": "mcp_tool", "server": "crewlet", "tool": "steer_take",
      "input": {"event": "${hook_event_name}", "agent": "${agent_id}"}, "timeout": 10}]}],
    "Stop": [{"hooks": [{"type": "mcp_tool", "server": "crewlet", "tool": "steer_take",
      "input": {"event": "${hook_event_name}", "agent": "${agent_id}"}, "timeout": 10}]}]
  }
}
```

- **An `mcp_tool` hook**, a call of `steer_take` on the run's own `crewlet`
  server: it rides the bridge connection the run already holds, under its
  token, so there is no new credential, no URL to allow and nothing to run in
  the box; its input is the two values the CLI fills in, where an `http` hook
  would post every batch's tool calls; and every way it can fail is
  non-blocking, where a `command` hook that exits 2 ends the loop. The server
  and tool names are the ones the bridge serves, filled in by the engine, so
  the file and the bridge cannot disagree.
- **What the model sees**, measured on 2.1.263 and 2.1.310 against a stub model
  API: a note handed back after a batch is read after that batch's tool
  results and stays for the rest of the run; one handed back at `Stop`
  continues the turn, and the run's result is the answer given after it.
  **Where it sits depends on the model**: on 2.1.310, after a batch, a system
  message after the tool results for `claude-opus-5-5` and `claude-sonnet-5`,
  and a system reminder at the end of the batch's last tool result for
  `claude-sonnet-4-5`; at `Stop`, a system reminder in a user message for all
  three — each headed `PostToolBatch hook additional context:` or `Stop hook
  additional context:`. The hook's transcript line reaches only the run's
  stream, which the run's transcript shows as `[steer] a note from ada reached
  the run` — never a request.
- **Ten seconds**, where the vendor's default is six hundred: the CLI holds its
  next model request until the hook answers, at every batch, and the bridge
  answers within five. The field is in seconds, and at it the CLI cancels the
  call and discards a late answer.
- **`disableAllHooks: false`, written explicitly.** A repository's committed
  `true` otherwise switches every hook off with no error, and the explicit
  `false` wins over it. It switches the repository's own hooks on too, which is
  why a hook of theirs that stops the loop is read as the [failure it
  is](#claude-code). Nothing else moves: no `--setting-sources`, which would
  drop the repository's `CLAUDE.md` with its settings, and no
  `--include-hook-events`.
- **The standing instructions say what a note is, as Claude Code delivers
  it**: that a person who leads the seat, or an administrator, may send one
  while the run works; that the CLI adds it between steps as context of its
  own, under the headings above — a system message, or on some models a system
  reminder at the end of the last tool result; that it opens with `## A note
  from <name>, sent while this turn was running`; and that text a tool
  produced — a file's contents, a command's output, a fetched page — is never
  a note, whatever it says. An OpenCode run is told its own CLI's carrier
  instead: a message from the user between steps. Worded as a fact rather than
  a command, as the vendor advises for text a hook adds. A Claude Code run's
  standing instructions are written twice, as they stand
  (`system.md`) and told of notes (`system-notes.md`), and the run's script
  names the one that matches its hooks, below.
- **Claude Code 2.1.163 or later**, or no hooks at all. The file holds no
  field newer than the `mcp_tool` hook (2.1.118 onwards), because in print mode
  the CLI ignores a settings file it cannot validate, without a word. What
  2.1.163 added is what the CLI reads of a hook's answer: from it, a `Stop`
  hook's additional context reaches the model. An older release runs both
  hooks and drops what the `Stop` hook answers, so a note taken as the run
  finished would be recorded as read by a run that never saw it. The run's
  script therefore reads `claude --version` first and starts an older release
  without `--settings`, and with its standing instructions as they stand —
  never told of notes it cannot read — saying so on the run's error stream;
  that run's notes wait for its review.

What leaves a run without its hooks — that older release, or a managed policy
that allows only managed hooks (`allowManagedHooksOnly`,
`strictPluginOnlyCustomization`) or sets `disableAllHooks` — leaves a run that
succeeds without asking for its notes once, which the collection reports as
[`steer_reader_never_ran`](#failure-modes); its notes still reach its review.

### OpenCode's notes plugin

Every OpenCode run its launch wires to its turn's notes is handed a plugin of
its own, which the run's server loads: `index.js` in `opencode-steer/` in the
box's work directory, written before the server starts and named in the run's
[configuration](#opencode) with the run's notes route as its one option — a
`{file:}` reference to a file under `opencode-values/`, like every value there,
so the configuration holds no token:

```json
{
  "plugins": [{"package": "<home>/.crewlet/opencode-steer",
               "options": {"url": "{file:<home>/.crewlet/opencode-values/v<n>}"}}]
}
```

The plugin is the engine's own, embedded in the binary: plain JavaScript with
no imports, so nothing is installed or fetched to load it. The run's script
hands the server the id of the session the run works in, as
`CREWLET_STEER_SESSION` on `opencode serve` alone, and the plugin reads that
session and no other:

- **It polls only while the session works** — from the session's
  `session.execution.started` (or any of its steps starting) to its
  `succeeded`, `failed` or `interrupted`, again for an execution OpenCode
  starts itself — and nothing before, so the brief is always the first thing
  the session reads. Its setup only registers and returns: OpenCode holds
  every prompt until each plugin's setup has resolved.
- **Each note is admitted as a steer**, under the id the route gives it
  (`ctx.session.prompt` with `delivery: "steer"`): OpenCode hands every steer
  waiting at its next step boundary to the model as a user message after that
  step's tool results — or after a final step that called no tool, whose
  boundary reads the inbox again — so a note sent while the run writes its
  answer is still read in the same run. The id is derived from the job and the
  note, so a note admitted twice is admitted once. The cursor moves past a note
  only once it is admitted.
- **With `resume: false`**: a note admitted once the session has settled
  starts nothing — an execution `opencode run` no longer watched would answer
  nobody — and the plugin admits none then anyway. Such a note waits on the
  run's record for its review. One whose admission landed just as the session
  settled, after OpenCode last read its inbox, is left pending in the session
  too, and the session's inbox outlives the server: a run carried on in the
  same session with a person's answer would be handed it ahead of its next
  prompt, beside the continuation brief's copy. So once `opencode run` has
  exited, and before the server stops, the run's script lists the session's
  inbox and **cancels every steer the plugin admitted and OpenCode never
  delivered** (`session.inbox.cancel`, an id of the plugin's own shape and
  nothing else), and the record alone carries the note — read once, by the
  review or the next launch's brief.
- **It confirms only what OpenCode delivered**: on the session's
  `session.inbox.delivered` for a note it admitted, it posts the note's id to
  the route's `read`, which records it read by the run's job (`boundary:
  step`). A note admitted and never delivered is never confirmed, and its
  review reads it.
- **It asks, and never insists**: a poll is held up to the route's ten seconds
  and given twenty, a confirmation ten; a failed request — a stopping node's
  `503` among them — is made again after a pause of a second, doubling to
  thirty and reset by the next success; a poll that admitted nothing is
  followed by the next no sooner than a second after it began, so no answer
  can drive it into a loop of requests; and a refused token (`401`) or a run
  with no notes route (`404`) ends the plugin for the rest of the run, its
  notes waiting for the review.
- **It writes nothing**: OpenCode reloads a configured plugin whose directory
  changes, and a note never touches the box's disk.

Measured against a stub model API: on OpenCode 2.0.32 and 2.1.4, a note
admitted while a tool call ran was read by the next request, after the tool's
result, and one admitted during the final model call was read in the same
execution, after the answer it superseded; on 2.1.4, one admitted after the
execution settled, with `resume: false`, started nothing, stayed pending in the
session across the server's restart and was handed to the next run in that
session ahead of its prompt — and, cancelled, was handed to nobody. The run's
[result](#opencode) is its **last** message's text, so a run steered past its
answer reports the answer it gave after the note.

A managed policy that denies the plugin (`integration.use`), or a plugin
OpenCode fails to load — which its own log names — leaves a run that succeeds
without asking for its notes once, which the collection says as
[`steer_reader_never_ran`](#failure-modes); its notes still reach its review.

## Mid-run clarification (`ask_and_wait`)

A run may hit something only a person can answer — an ambiguous spec, a design decision above its remit. A headless CLI cannot pause to ask interactively, so every executor run's [standing instructions](#what-a-coding-agent-is-told) carry `## When you need a person's answer`, with two ways to ask:

- **If it can go on without the answer**, it asks with its own tools — `comment_on_work_item` with an `ask` naming whoever owes the answer, or a message where it was asked — keeps working, and finishes its turn as usual with `submit_work`, saying what is waiting on whom. The answer wakes a new turn of the seat's, like any other message; this run does not wait for it.
- **If it cannot go on without it**, it **parks**: it commits and pushes its work-in-progress branch, calls **`ask_and_wait`** on its [tool bridge](#the-tool-bridge--a-seats-own-tools-from-inside-a-box) (`internal/agent/builtin/runask.go`) with the question, and ends its turn without calling `submit_work`. The audience (`to`) is `requester`, `team`, `manager`, or a named teammate: the instruction carries the seat's unit roster and its manager, by handle, so the run can name a real person and the park can resolve the name exactly. When the person answers, the run **continues where it stopped**, in its own CLI session in the box it left, with the answer as its next prompt, where the relaunch reuses that box: the box was kept, the member the launch picks runs the same CLI in the same cell, and the box is this node's to drive (any `e2b` box, or a local one on this node's own host). Otherwise a fresh run starts in a new box from the branch, told the question and the answer ([Answering a parked run](#answering-a-parked-run)).

The rest of this section is the second path.

**A run asks in the shape a decision is asked** ([ADR-0068](../../adr/0068-a-run-asks-a-person-in-the-shape-a-decision-is-asked.md)). `ask_and_wait` takes:

| Argument | What it is |
|---|---|
| `question` | What the run needs answered, in one sentence of at most 300 bytes: the title the person reads first. Required. |
| `context` | What the person needs to answer well, in Markdown (what the run found, what is at stake, links to what it cites), at most 16 KiB. |
| `options`, `recommended`, `rationale`, `role`, `evidence` | When the person has to **choose**: 2 to 6 options (`id`, `label`, `detail`), the one the run recommends and why, the role the person answers in, and what it looked at. The same shape, caps and checks as a [work item's decision](../guides/worklet.md#asking-for-a-decision): a cited task is resolved to its id and a cited page must exist. Absent for an open question, which is answered in words. |
| `to` | Who should answer, as above. Required. |
| `branch` | The branch the run pushed its work to, exactly as pushed. |

**The ask is validated whole before anything is written**, and every fault comes back to the run at once, while it can still fix it ([ADR-0059](../../adr/0059-a-tools-contract-is-its-validators-and-every-fault-comes-back-at-once.md)): a question past its cap, a choice part without its options, a branch git would refuse, an option id that is not a slug. A run's ask carries no `inform`: its answer resumes the run itself, so there is no answered turn of the seat's to hold to a promise. A valid ask is **recorded on the run's row** by the job that made the call (`question`, `question_context`, `decision`, `audience`, `branch`), redacted, and only while that job is running: a second question in one job is refused (one answer resumes a run, so it asks one question at a time), and a call from a job that has ended or been replaced records nothing. The tool then tells the run to end its turn, and from then on the job's `submit_work` is refused (`not_running`) with the same instruction: the job is parked on the answer, so a submission it makes is not delivered work, and a CLI told it was would end believing so. The bridge nudges the run's waiter, so the run is collected and parked at once rather than at the waiter's next pass. **The branch** is what a run re-seeded on a fresh machine is told to check out ([below](#answering-a-parked-run)), so it is recorded as its own fact at the one moment anything knows it, and is never inferred from the refs the run delivered, which name a pull request's URL as often as a branch. A run ended at its turn's wall-clock cap is never parked on a question it asked on its way out: it is collected and resumed like any ending. When a run completes with a recorded question:

1. The engine (never the sandbox) **announces** the question as `executor_asked` on the event stream, attributed to the seat whose run asked and carrying the question, its context and its decision, the audience as the agent wrote it, the run's conversation and its work item, and resolves that audience into the people it is put to ([below](#who-a-question-is-put-to)), keeping identity attribution and capability guards on the engine. **That is how it reaches them**: the run becomes a row in each of those people's own decisions on the dashboard (Home and the Inbox's *Needs you*, and *Asked of me* on My work, all served by [`GET /worklet/decisions`](../reference/api-endpoints.md#queries)), a banner on the run's page and its rail in Live › Executors, a row of Live › Now running's *Waiting on a person*, and an entry on the board an operator reads (`GET /executors?audience=<handle>`, "what is waiting on me"). **Nothing is posted to a chat surface**: the engine sends no message into the run's conversation or to anybody's direct messages, so a person who works only in chat learns of the question from somebody who has seen it there. It is answered from that row, [by turn](#answering-a-parked-run), or by a reply on the run's conversation (step 3).
2. The run is parked (`awaiting_clarification`) with both conversation values; the turn's parked state is kept on the row untouched; the box is left **paused** so the checkout and the CLI's session survive. Unlike a running job, **the agent goes free** — a human reply can take days, so its inbox flows and it can do other work. The question is announced first and recorded second, and the agent is freed only once the record lands: a question recorded but never announced would wait for an answer nobody was asked for, and a seat freed ahead of the record reads as idle with nothing open, which is the state in which a person's reply is run as an unrelated turn.

   **A park that could not be written is not a park.** The run reaches this step holding the claim a completion took, so a step that fails leaves the claim to give back: handed back, the completion poll fires again, the paused box is collected a second time and the park is retried. If the claim cannot be handed back either, nothing retries at all — a row left in the claim is read by no poll, re-claimed by no redelivery, matched by no answer and expired by no reaper — so the run is ended like any other lost turn (record deleted, box reclaimed, `executor_failed` with reason `claim_unreverted`) rather than left to strand a billed box until the seat changes hands. It is ended **only while it is still the claim**, though — its status, its job and its lease, which the store checks as it decides the ending: a hand-back that reported a failure may still have landed, and a run it did reach is back where the claim found it and owed its retry, so it is left to that retry rather than killed under it — and an ending that could not reach the store either, kept and finished later, that finds the run handed back after all resumes it with its reply instead of settling into nothing. The ending is decided first and the box reclaimed second for the same reason, since the decision is what establishes the run was still the claim's to end.
3. The **first reply posted in that conversation after the question was asked** is the answer. The row records the instant the question was put (`asked_at`, taken before the question is announced, so nobody can have read it earlier), and a delivery answers only if it was posted at or after that instant — its envelope's own timestamp, which for a chat message is the vendor's post time. Without that anchor the rule was purely positional ("the next thing to arrive here"), and two things went wrong with it: a message written while the job was still running was taken as the answer the moment the run parked, and a reply that answered an *earlier* question, held back and redelivered, was taken as the answer to whatever the run asked next. The conversation is matched on the [conversation identity](event-system.md) the row was written with, which lets the answer arrive wherever the person actually replies. It has to be the identity rather than the inbox partition: a run launched from a *top-level direct message* parks under the bare DM channel, and the engine's own chat prompt tells the seat to reply **as a thread** — so the person's answer arrives partitioned on that thread, and comparing partitions meant the clarification was never delivered and the box waited out its pause TTL. A direct message is one conversation however it is threaded, which is exactly what the identity says. A row with no identity — a run launched by a schedule tick or an A2A wake — is answered by no chat reply at all. Every question is parked with its anchor — a park without one is refused — and a delivery that cannot show it was posted after the question answers nothing: it goes its ordinary way.

   **The answer is recorded before anything is done with it.** The first qualifying reply is written onto the run by a compare-and-set (the run moves to **`answered`**, carrying the reply, `answer`), and only then is the delivery acknowledged. From that moment the answer is durable and nothing about it depends on the inbox again: a second reply racing it, on this node or across a seat handoff, loses the compare-and-set and finds the question answered. The coordinator then claims the answered run (at-most-once) and **resumes the same turn, which carries the run on**: the round the run asked in is not over, so the answer is never filed as the run's report: the executor is relaunched, in the paused box, **continuing the CLI's own session** (Claude Code's `--resume`, OpenCode's session) with the answer as its next prompt, so the run that asked goes on knowing everything it had read and tried, where the relaunch reuses that box, as [Reuse across launches](#how-a-coding-task-runs) has it: the box was kept, the member the launch picks runs the same CLI in the same cell, and the box is this node's to drive. Otherwise (the box reclaimed while the question waited, a fallback onto a member of another CLI or cell, or a local box left on the host of a node the seat has since moved off) the run carries on **fresh**, in a new box, its brief telling it the question, the answer and the branch to check out. Either way it is the same round: the calls the run made before it asked stay on its record, the carried-on run's calls are numbered after them, and its collection judges the round whole, reading every call in the order the run made it. **Its submission is one made after the answer.** The job that carries the run on records where the answer cut the round, the place of the last call the row held when it opened (`answered_through`), and the collection replays only a `submit_work` placed after it: one the asking job made before its question was made without the answer. The cut is that recorded place rather than the round's last `ask_and_wait`, because the row's call log is bounded: past 200 calls it drops from its middle, its ordinary calls first and a submission or an ask only once nothing else is left there, so a long enough run can still lose the ask from it. A job carried on after a loss keeps the cut, and a new round starts without one. No fresh turn and no re-investigation.

   **The answer is sealed on the run, like every other instruction channel.** Its words and who gave them are written onto the row only inside a seal under the fleet keyring (Tier A `secrets.keys`, in a key domain of its own), bound to the run, the question it answers — the job that asked — and the deliveries it was made of ([ADR-0031](../../adr/0031-every-state-log-record-is-signed.md)). Whichever node resumes the run opens the seal first, and the turn is handed only what the seal carried. An answer whose seal does not open as an answer to that question is never handed to the run and never attributed to anybody: it is logged at error (`sandbox_answer_unverified`) and let go of — nothing handed back, nothing announced — and the run waits on its question again, where the next reply answers it. One sealed under a key the node does not hold waits instead, recorded and owed with the seat's mail behind it, logged at warning with the keys the node does hold (`sandbox_answer_key_unknown`), until a node that holds the key takes the seat or this one restarts with it ([Rotating the keyring](secret-store.md#rotating-the-keyring-with-nothing-in-flight-lost)).

   **Recording and resuming were split because the inbox's retry order is the wrong order for an answer.** The answer used to be held by its delivery until a resume succeeded, and a resume that failed handed the *message* back to the broker with a NAK. On JetStream a NAK'd message comes back after its redelivery backoff, **behind** the conversation's newer mail ([event system](event-system.md#delivery-semantics)): so the person's next message reached the still-waiting run first and was taken as its answer, and the real answer came round afterwards to answer whatever the run asked next — or ran as a turn with no context. The in-memory twin replayed a NAK at the head, so every engine test certified the order production never gave. A resume that fails now is the **coordinator's** to retry, on its own schedule, and the person's message is never handed back for it.

   **The seat's later mail waits behind the answer.** While a seat owes any of its runs an answer's resume, the coordinator holds the seat's inbox (the `sandbox` hold a busy seat is held under too) and lifts the hold once the resume has *returned*, so the person's follow-up is worked as an ordinary turn — with the run's own replies already in the thread it reads — rather than racing the resume. A hold rather than a park: the mail waits on the broker with its order and its delivery count intact. A later reply is an ordinary message, not a note to the resumed run: a [steer note](turn-engine.md#steering-a-running-turn) is sent with `steer_turn`, and one sent to a parked run waits on the run's record and is read in the brief of the launch that carries the answer ([notes to a running run](#notes-to-a-running-run)).

   **Every delivery to a seat with a question open is offered to that match first**, and that follows from step 2 rather than adding to it: a parked run frees its seat, so the answer arrives on the ordinary path looking like any other message — nothing about a chat reply says which parked executor it answers. So the dispatcher offers each delivery to the parked run *before* consuming it, and only what no parked run claims becomes a turn. It is offered after the completion ledger has had its say, so a redelivered trigger that already produced a turn is never taken as an answer as well. A **held** seat offers nothing — its inbox is held, so a reply to a second run of the same seat, waiting while the first is still going, waits with the seat's mail and is offered when the first stops holding the seat. A delivery that **becomes** an answer is recorded in that same ledger, so a copy of it — a redelivery whose acknowledgement was lost — is dropped rather than run as a turn, on whichever node it reaches; while the run still holds the answer, a copy is recognised on the run itself and spent as the answer it is.

   **The offer answers what to DO with the delivery, in three words, and an error is never one of them.** *Consumed* — the answer is recorded on the run (whatever its resume then does), or the delivery is a copy of one already recorded — so it is acked and no turn runs. *Deferred* — a run is waiting and the answer could **not be recorded**, because the coordination store failed or could not say whether the write landed — so the delivery is **handed back by deferral** and offered again: it keeps its place at the head of the seat's inbox (a NAK would put it behind the person's next message), and the seat's inbox stops until the seat host's next renew. *Not mine* — nothing was awaiting this conversation, or the delivery was written before the question — so it is worked as the ordinary message it looks like. A delivery whose answer was recorded is *consumed* even when the run's first resume ends it for good — no conversation to re-enter, a claim that could not be given back, a resume that broke before its turn: the ending hands the reply back through the run's row as below, with the seat's inbox held until the copy is out, so it still reaches the seat once and in order. The inline attempt used to hand the delivery it held on as the ordinary message instead, which needed the store to delete a run still holding the reply on that caller's word — and an ending that could not land then left the reply both on the row and handed on. The ambiguous cases resolve towards the run, because an answer that arrives twice is recoverable and an answer that is spent is not.

   **A lookup that cannot be made is decided by what this node already knows.** It is the ambiguous case in its purest form — the store could not say *which* of the seat's runs is awaiting a reply — so it is not answered by the store at all, but by the seat's own awaiting count, which the node holds in memory (seeded from the store when it claimed the seat, moved since by its own transitions) and can therefore read when the store is exactly what is failing. No awaiting run on the seat: *not mine*, because nothing is owed the delivery and an unreadable store must not swallow an ordinary message — on a company with no parked runs that is every message a seat receives. An awaiting run: *deferred*, because something here **is** waiting for somebody's reply and only which row could not be read. Its hand-backs are bounded by the same count as any other, under a key naming the seat; past it the message is let go to the ordinary route and `sandbox_answer_lookup_exhausted` says so.

   **Both series are bounded, and the bounds are the old ones.** *The resume of a recorded answer* is retried by the coordinator a second after it fails, doubling to a 30-second ceiling (the queue's own failure backoff, deliberately), for at most **10 attempts** and at most the run's own **`pause_ttl_seconds`**, measured from the first failure: about two and a half minutes, long enough for the failures that actually reach it to clear (a seat lease moving to a node that can resume the run, 45 s; a config apply that brings the missing runner; a store blip). A retry the seat's own conditions refuse charges nothing, and it **waits for what refused it** rather than re-checking on a timer: a person's pause is waited out until the pause watch hears them resume the seat, a company with no model until the apply that brings one, a spent budget window until the instant it turns over (or an apply that moves the ceiling), a relaunch every member of which is at a usage limit it already reported until the first is tried again, a node whose posture refuses new work until the reconcile tick that finds it admitting again, and a seat whose ownership cannot be proven until it can: the moment the seat's acquisition is established (which is how an answer the seat inherits from its last holder resumes as soon as the new holder can run it, rather than a heartbeat later), or the renew that proves it again after a store blip, with one heartbeat on the clock behind both for a renew that was merely late. A retry the **node** refuses waits the same way and is charged nothing either: every resume asks the node's admission before it claims the run (see *Completion → resume*), and a draining node refuses it until the drain hands the seat back, which lets the answer go to the seat's next holder, recorded on the run as it was. The inline attempt asks too, under the delivery that carried the answer, whose own admission answers for it. An answer's admission asks its models' limit as well, of the call it makes first, the relaunch: the members of the executor chain a launch can take. It asks the seat's budget too, a window full or too short for a launch. A completion's admission asks neither (only whether its seat is parked, below), because its job is over and its tokens are spent: it is collected first, charged in the window it ran in and its box paused, and its review and relaunch meet the budget themselves (below), while a limit its review's chain (`llm_review`, else `llm`) already reported refuses its resume once it is collected, before its turn runs, and parks the seat on that limit. Refused before its claim, a completion stayed uncollected until the condition cleared: on a full window it was collected only once that window had turned over, its tokens charged into the next one; on a limit its reviewer's entry already knew (every seat on a plan another seat's run had just spent) it was left uncharged for as long as the entry sat out, the seat never parked; and the waiter kept its box awake meanwhile. A completion the admission refuses is acknowledged and kept until the condition clears, and the waiter announces it again meanwhile, so it spends none of its deliveries. A resume that meets its models' limit before its turn writes anything (a limit its review's chain already knew once its job was collected, its reviewer's chain at the call, or a relaunch whose every runner member sits out) is reverted and waits the same way, rather than spending one of its attempts, and a completion's is also held by the node that met the limit, until the instant the limit names: the gate admitted it and would admit it again, so that node refuses the waiter's announcements of the job itself meanwhile, before its gate and its claim, rather than collect the box and run the review into the same limit at every poll. **The resume parks its seat on the limit too**, as a dispatch's turn that met it would ([the provider park](llm-backends.md#falling-back-between-entries)): `seat_provider_parked`, the seat reading `stopped` with the reason `provider`, and the chain's probe, whose answer releases the park and re-fires the resume. While the park stands the admission refuses every resume of the seat, so a completion whose own instant passes while the probe finds the limit still there is refused before its claim, where its reviewer's chain, ready again, admitted it into the same window, and its relaunch launched a box into it, once an hour. An answer the park refuses waits for its release, and for the instant of the probe's next call only while that is still to come: from the probe's instant until its call comes back (a whole run of the entry's CLI) the instant is past and the park still stands, so the refusal names none, and a retry that re-checked at that instant re-checked at once, thousands of times a second, until the call came back. A refusal that names an instant already past is waited out as one that names none, whatever refused it. **The hold is that node's alone**, like the limit it waits on: it is kept in the node's memory and never written to the run's record, so a restart forgets it and so does the node's letting go of the seat, and the next announcement asks whoever holds the seat then, whose own models may know of no limit at all. The waiter goes on announcing the job meanwhile and leaves its paused box asleep, since the job was read back already (see [Durability, completion, and observability](#durability-completion-and-observability)). One its seat's budget refuses once it runs (a completion's review on a full window, or a relaunch on a window full or too short for a launch) waits that window out, whether or not it wrote: a completion held on its record, collected in its paused box, which the waiter leaves asleep until the window turns over or a revision moves the ceiling, and an answer reverted to wait uncharged in its own series. A signal that lands while a retry is being refused is not slept through: the wait that follows it re-checks at once. Each of those is a discrete event the engine already observes, and it re-checks exactly the answers waiting on it, at once; nothing runs while the condition holds. A five-minute backstop re-checks a wait whose signal never came, so a missed signal costs a late resume, well inside the 30-minute default `pause_ttl_seconds`, and never a stranded answer. Past the bound the answer is **let go**: the run goes back to waiting on its question, the reply is handed to the seat's inbox as the ordinary message it is (under a new id derived from the original, because the original is spent in the completion ledger), and that reply is **declined** for this question (`declined_answers`) so it never answers it again, and `sandbox_answer_requeue_exhausted` says so. **Letting go is exactly once**, across a crash at any step: one write clears the answer, declines the reply and its copy, and records the copy on the run as owed to the seat (`hand_back`); the copy is published off that record and cleared from it afterwards. A node that stops before the write leaves the answer recorded and nothing published, and the seat's next holder drives it again; one that stops after the write leaves the copy owed, and whoever reads the run next (this node's retry, the seat's next holder before it opens the mailbox, or the run's own ending) publishes it; one that stops after the publish leaves the copy published *and* owed, and the repeat is the same message under the same id, which the inbox's same-id dedupe and the completion ledger collapse. It used to publish first and write second, so a crash between the two delivered the reply twice: as an ordinary message and as the answer a later resume used. The run is **not** ended, because every failure that gets there is a statement about *this node* (no resumer, a parked turn state of an `execstate` version this build does not read, a seat not in this node's company), and the seat's next holder, or this node after a restart, takes over an `answered` run from its record and drives the resume itself. **A run that ends still owing a copy is not deleted until the copy is out**: the store refuses to delete a row that owes the seat anything, so the ending publishes the copy, clears it, and only then deletes the row: a copy published off the deleted record, as it used to be, was lost to a crash between the delete and the publish. A publish that fails keeps the row, holds the seat's inbox behind the copy, and the ending is retried with the hand-back. **What a run owes is bounded by one decline**: a second answer is let go of only once the first one's copies are cleared, so the row never carries more than one delivery batch of copies (20 events by default, the size of the answer they were made from); past it nothing is lost: the second answer stays recorded and owed, its seat stays held, and the retry publishes the copies already owed before it decides again. And **each answer gets its own attempts**: one recorded while an earlier answer's copy is still owed starts a fresh count, rather than being let go of on the strength of the earlier answer's spent one.

   **A reply that leaves its run without a turn taking it goes back to the seat, once — whoever ends the run.** The run can end under its own resume, on the inline attempt or a retry — it has no parked turn state to resume, its claim cannot be given back, or the resume broke before its turn began — or under a seat that left the company, or a reap, and the delivery that carried the reply was spent when the answer was recorded, so nothing else would ever bring the reply to the seat. The ending is [decided on the run's record](#how-a-coding-task-runs) first, and **the decision settles whether the reply goes back**: a turn cannot take the answer once the ending is decided, so one no turn took by then goes back to the seat, and one a turn took has been used and goes with the run. The ending then **lets the answer go** in one write that takes it off the run and records its copy as owed (`hand_back`), and hands the copy back before it deletes the row — **the store will not delete a run still holding a reply the ending owes the seat**, so an ending can never take the reply with the record. An ending is decided only under its own terms: a hand-back that landed and reported a failure, or an old holder's hand-back landing under a reap, puts a run back to `answered` with the reply on it, and a claim's own ending is licensed for the claim alone, so it decides nothing about that run, which is left to its retry, reply and all. The crash guarantees are a decline's: stopped before the let-go's write, the reply is still on the row and whoever reads it next lets it go; after it, the next reader publishes the copy; after the publish, the repeat is the same message; after the clear, nothing is published again. An ending that cannot be finished — the let-go not recorded, the copy not published, the announcement refused, or **the delete itself not taken** — keeps the row and its terms: the seat's inbox is held behind it, and this node finishes it, once the store takes it, exactly as decided — the box included, where the ending reclaims that only after its decision. A delete the store did not take used to be left for the seat's next recovery pass, which comes only when the seat moves, and the record it left was a claim, which holds the seat: the seat took no mail at all until it changed hands. And a kept ending used to be finished without the reclaim it was decided with, so the only record of a paused box was deleted and the box billed, named by nothing, until its provider's TTL. A reply used to be published straight off the retry *after* the ending had deleted the row, and later straight off a refused record, so a crash between the delete and the publish, or a broker refusing that publish too, lost it.

   **A claim whose node stopped before its turn took the answer is revived, and the run resumed with it.** The coordinator claims an answered run for its resume, and between that claim and the resumed turn lie steps that can stop the process — a crash, a deploy, a seat that moves. The row reads `resumed` from the claim until it is settled either way, so the seat's next holder, finding the claim as it takes the seat, could not tell a reply nobody had acted on from one a turn had used, and read every one of them as spent: the person's answer was lost without a trace. The resume now records, in one compare-and-set at the last moment before the turn runs, that **the turn took the answer** (`answer.taken_at`); a resume that cannot make that write does not run, and a release that gives the claim back for a retry clears it. A claim whose answer no turn took never used it — and never touched the box, because the take is the first thing a resumed turn does — so the seat's next holder **gives the claim back to the answer** (`sandbox_answer_revived`): in one compare-and-set the run is `answered` again, fenced to the holder's lease, with the lost claim counted on the answer (`answer.lost_claims`, `answer.first_lost_at`), and the holder drives its resume exactly as it drives any answer its last holder recorded and never resumed with — the seat's mail held behind it, and the box still paused or, past `pause_ttl_seconds`, reclaimed and the run re-seeded from its branch, as any answered run's is. It used to be reaped, the run ended and the reply handed to the seat as an ordinary message, so the answer reached the seat but never the run it answered, which was lost. A revival the store does not confirm — a write that failed, or a claim that moved under it and could not be read again — is retried by the holder on the hand-back's spacing with the seat's mail held behind it (`sandbox_answer_revive_owed`), never read as a reason to end the run; finding it landed after all, or the claim given back, the holder resumes the run it finds. A claim a node made itself and lost track of — the claim's write reported a failure and landed — is held by no resume either, but it is **not a lost claim**: no node stopped. The answer's next attempt on that node finds it and gives it back to the answer under the lease it was taken under (`sandbox_answer_claim_given_back`), **uncounted**, and goes on with the answer's own attempts — resuming, or declining the answer once those are spent, never ending the run. That holds on the answer's last attempt too, and when its window lapses under a claim: the attempt that spends the budget gives the claim back first and then hands the reply back once, rather than declining a run that is not answered any more — which the store refused, leaving the run in a claim nothing drove, the person's answer on it and the seat held behind it. The run used to sit in that claim, the seat busy behind it, until the seat happened to move; and once that was fixed, a few of those claims in a row were counted as dead ones and ended the run as an `abandoned_tail` on a node that had never stopped. **Revival is bounded, by two counts kept on the row**, because a node that stops resets every count it kept: after **3** revivals of one answer (`sandbox.MaxAnswerRevivals`), or once the run's own `pause_ttl_seconds` has passed since the first claim of it died, the next claim that dies is reaped instead. Three claims dying in a row is not bad luck but a resume that takes its node down before its turn begins, and reviving it again would hand it to the next holder to fall over the same way, the seat's mail held behind it each time. The store will not delete that run with the reply on it, so the reap lets the answer go as above — the copy handed back, the run ended, and its loss announced once as `abandoned_tail`, saying why it was not resumed again and that the reply went back to the seat (`sandbox_answer_not_revived`). A claim whose turn took the answer has used it, and a copy or a second resume now would answer the person twice: it is spent, the run reaped, and the announcement says nothing went back. **The take, the revival and the ending are exclusive in the store's own compare-and-set**: a revival and an ending both refuse an answer a turn took, a revived run has no claim left to take it under, and a decided ending takes no take — so whichever lands first wins, whatever any lease says, and a node still on its way to its turn when the seat's next holder revives or ends the run cannot also answer the person with it. (Only the claim's own ending lets go of an answer its turn took: a turn that gave its claim back as a retry has said nothing it did reached anybody, and once the hand-back cannot land, no retry will hand the reply to a turn again.) The reap **fences the row first**, moving the run to its own, newer lease, so a node that lost the seat but is still on its way to that turn has its take refused and the person is answered once, through the seat's next holder, rather than also by a turn the seat's lease will stop. That fence holds because **every claim carries the claimant's own lease**: the claim stamps it on the row and every write the claim makes after it — the take, the hand-back, the ending — carries it back off the row; a launch stamps the lease that launched it the same way, and the seat's new holder stamps its own on every run it recovers, parked ones included. And **a take, a claim and the record of an answer are refused under no lease at all** on a run any lease owns, which other writes let through so that a recovery holding no lease yet can still write: a run launched under no lease, or one nothing re-stamped, sat at the zero epoch, and a stalled claimant that held no lease took the answer on a row its successor had fenced — the person was answered by its turn and by the copy. **A node that knows it lost the seat writes nothing on it.** Its seat host no longer holds the lease, and every write the coordinator would make on the seat's behalf — recording an answer, claiming one or a completion, giving a claim back, launching a run — is refused before it reaches the store (`sandbox_seat_not_held`): a reply or an answer by turn goes back to reach the seat's holder, a completion is handed back to be fired again for the holder, and a retry this node was making is dropped for the holder's recovery pass to drive. It used to write under the zero fence, which constrains nothing, so a node that had noticed it lost the seat recorded and claimed a person's answer past its successor's fence, took it and ran the turn on a seat it no longer held; one that has not noticed yet writes under its old lease, which the successor's fence outranks — an answer it records is refused rather than left on a run its successor recovered as waiting, which nothing would then drive. The reap reads the row again after fencing it, so a claim its old holder gave back first is taken over as the run it is, owed its retry, rather than reaped. Where the reap can neither fence nor read the row, it is revived or reaped as listed: the revival is a compare-and-set that stamps the holder's lease itself and refuses an answer a turn took, and past the bounds the store's refusal to delete a reply no turn took is what hands the reply back. A resume that broke before its turn began — a panic re-entering the conversation — is settled without a retry like every abandoned resume, but nothing ran, so its reply is handed back the same way rather than read as spent, and the run is announced lost once, as `resume_broken`: no turn ran to publish a completion of its own, and the run used to end with a guard breach and nothing else, so the turn parked on it read as parked for good.

   **A reply's original delivery is spent the moment the reply leaves the run.** When a turn takes the answer — on the inline attempt and on a retry alike, at the same commit that records the take — and before the write that lets an answer go, by a decline, an ending or a reap, the delivery that carried it is recorded as worked in the [completion ledger](seat-ownership.md#the-completion-ledger); a reap that finds an answer a turn took records it again, for a node that stopped between the take and its spend. A node that recorded the answer — or took it inline, holding the delivery unacknowledged through the whole resumed turn — and stopped before acknowledging the delivery leaves it to come round again, and by then the run may have used the reply (its turn may already have answered the person), handed a copy back, relaunched, or be gone, so nothing on the run would recognise it; the ledger drops it instead of running it as a second message — or, for an answer by turn, instead of asking the run about it again and announcing it `gone` or `not_awaiting` after it resumed the run. That holds for an answer by turn because its route reads the ledger before it reaches the run, and because its delivery is recorded whatever its type: the ledger otherwise keeps only the types that run a turn, which an answer by turn never does, so its spend used to record nothing at all. It used to be spent only once a retried resume's turn had *returned*, so a node that stopped mid-turn left the original to run as a second turn on whichever node took the seat. A reply spent and still on its row is not lost: the row, never the delivery, is what resumes it or hands it back, and a copy handed back goes under an id of its own.

   *A delivery whose answer could not be recorded* is handed back by deferral, and that series has three clauses. The first is the one the *message* carries: every hand-back spends one of the message's deliveries, so the offer stops while **5 deliveries are still left** and those are kept for the ordinary route. That reserve is read on **each message's own** count, never on the partition's: a delivery is a whole partition, its messages sit at different counts as a matter of course, and gated on the partition's number a person's clarification reply on its *first* delivery would be refused the answer route whenever an older message on the same conversation is near its own budget — and refused for good. One message with the deliveries to spare is enough to keep the offer open; `sandbox_answer_offered_over_a_spent_sibling` says when the hand-back may spend the last delivery of a co-partitioned one, and `sandbox_answer_headroom_reserved` when the route lets go. The second is **10 attempts on one message** inside one process, and the third the run's own `pause_ttl_seconds` (`sandbox_answer_record_exhausted`). A second reply gets its own count, and one run keeps at most four of them at a time.

   **Two questions open on one direct message** are told apart by the thread each was asked in: the identity admits both — that is what makes a DM one conversation — and the run whose own partition matches the reply's wins, with the most recently parked question answering a top-level reply that matches neither.

### Who a question is put to

The audience a coding agent names is its own words, so the park resolves it — once, against the org chart, in the same write as the question — into the seats the question waits on (`audience_handles` on the run's record and on [`GET /executors`](../reference/api-endpoints.md#get-executors)):

| Audience | Put to |
|---|---|
| `requester` | The seat whose message, notice or ask woke the turn that launched the run. The launch records it on the run (`requester`), because the park runs when the job finishes — days later, perhaps on another node — and sees no trigger. |
| `manager` | The seat's manager. |
| `team` | The lead of the seat's unit and the **people** in it; the unit's other agents are left out, since the seat could ask them itself. |
| a name | The one colleague it names exactly — a handle, an id on a chat surface, or a role name, case aside. A partial or approximate match is not a person: a guessed colleague is somebody else's question in their inbox. |

When the audience names nobody the chart has — no requester was recorded, the seat has no manager, the name matches nobody — the question is put to the seat's **lead chain** instead (its managers, nearest first, or, for a seat nobody manages, the leads of the units that hold it) and `audience_fallback` says so. A question is never parked waiting on nobody while somebody is answerable for the seat, and a person can tell a question put to them from one that reached them because nobody else could be named. `?audience=<handle>` on the board is "what is waiting on me".

### Answering a parked run

A reply on the question's conversation (step 3 above) is one way to answer. The other is to **name the run by its turn**, with the operator tool [`answer_executor`](../reference/api-endpoints.md#answering-a-parked-executor) — from your own assistant over `/operator/mcp`, or from the dashboard. It is the only way for a run started by a **schedule, a task assignment or a colleague's ask**: those turns have no conversation, so the run's record names none and nothing a person says in chat can reach it. Until this existed such a run's question waited out its pause TTL however promptly somebody knew the answer.

In the dashboard it is the **Answer** on a parked run's banner — on the run's page and its rail in Live › Executors, on Live › Now running's "Waiting on a person", in the Inbox and on Home. The banner names who the question is put to (the audience resolved when the run parked), how long the box is held, and whether a reply on the turn's conversation would reach it too.

**Who may answer is the run's requester — the person whose message, notice or ask woke the turn that launched it — or whoever leads the run's seat, or an administrator (`admin`)**, and never a seat: the person who asked for the work answers what it asks them, and nobody who merely leads that person does (see [the authority table](identity-and-access.md#the-sixteen-rules)).

`answer_executor{turn_id, launch_id, choice, answer}` checks the run is waiting (`not_running` if it is not), that it waits on the question the person read (`launch_id`, the job that asked it; `stale_version` once the run has moved on to another) and, where it names a `choice`, that the choice is one of the options the run's question offers (refused, naming them, otherwise, and on an open question); an answer is a choice, words, or both. It then puts an `executor_answer_given` event on **the seat's control topic**, answering `pending`. The control topic, not the seat's inbox, because the answer is addressed to the run, like a completion: the inbox is held while the seat's executor holds the seat for any turn and is worked oldest first after that, so an answer that rode it waited behind every launch and every older message, and on a busy seat it never arrived. The node holding the seat takes it off the control topic and hands it to the coordinator, which **records it on the run** at once (the run reads `answered` from that moment) exactly as it records a chat reply, the answer, the credential and the person it names, sealed, and the event it arrived in, and carries the run on with it as above, the answer attributed to the person who gave it. From the record on, an answer by turn is a recorded answer like any other, except that its first attempt is queued rather than made inline: the resume starts a turn, so it waits until the seat's executor holds it for no other turn, no other turn of the seat is running on the node (a seat runs one turn at a time) and no person has the seat paused, and is then the seat's next turn, with the seat's mail held behind it. Its retries are the coordinator's, a resumed turn **takes** it at the last moment before it runs, and a claim whose node stops before its turn took it is revived by the seat's next holder, which resumes the run with it (see [Mid-run clarification](#mid-run-clarification-ask_and_wait)). It used to be resumed with directly, held only by the claim the resume took: a node that stopped between that claim and the turn left a claim its successor reaped as an abandoned tail, and the answer's delivery, coming round to the new holder, found the run gone. It is **never a turn**: whatever it finds, the delivery is spent there, and only an answer the run is still owed but could not be recorded against (the store could not be read, or the record could not be confirmed) is handed back to the broker for its spaced retry, a redelivery that finds the record landed after all is spent as the answer it already is. Once it has become something, recorded, declined, `gone`, `not_awaiting`, it is recorded as worked in the [completion ledger](seat-ownership.md#the-completion-ledger), and so is an answer its run spends (taken by a resumed turn, let go of, reaped); the route reads the ledger first, so a redelivery after either is acknowledged without reaching the run and without a second announcement (`sandbox_answer_by_turn_already_spent`). That hand-back is a NAK, and on this route it is safe in a way it is not for a chat reply: the answer names its run, so coming back behind the seat's newer mail lets no later message take its place, and it cannot be taken as the answer to anything else. An answer already recorded against the question wins: the run is `answered`, no longer waiting, and the answer by turn reports `not_awaiting`. **An answer by turn the run could not be resumed with is let go of** like a chat reply, after the same attempts: the run waits on its question again, and the copy handed back to the seat's control topic (it has no ordinary form to become) is spent there and announced `declined`, once, so the person knows to answer again; it is never recorded against that question again. One let go of because its run ended is announced `gone` the same way. An answer given while the seat is [busy executing another turn](#how-a-coding-task-runs) is recorded at once and its resume waits until that turn's executor settles or parks; one given while the seat is paused is recorded and resumed when the pause lifts; one given while the holder restarts is still on the control topic afterwards. **It answers the question it was given against, and no other.** The resume's wait can outlast the question, and so can a NAK's backoff or a retried copy: somebody else's answer resumes the run meanwhile, its turn relaunches (a reviewer's send-back), and the new job parks on a question of its own, and an answer that named only its run claimed whatever the run waited on by then, resuming it a second time with the first question's answer presented as the second's. So the event names the question too, the job the run held when it asked (`launch_id`), off the row `answer_executor` checked, and the run is resumed with it only while it still waits on that question; once it has moved on, the answer is spent as `not_awaiting`. Every new question comes with a new job, so the job identifies it. The question is **required**: an event naming none is spent without resuming the run, with the reason logged (`sandbox_answer_names_no_question`), it cannot be told from an answer to a question the run has moved past, and `answer_executor` never delivers one. Two answers to one question, a chat reply and an answer by turn, or two people, or a retried `answer_executor`, contend for the one record, and the run is resumed once, however far apart they arrive.

**A node that has let go of the seat hands the answer on once.** An answer or completion that reaches a node whose seat host no longer holds the seat is deferred: it goes back to the head of the control topic for the seat's holder, at the cost of one delivery, and the node stops consuming that topic until its release detaches it. It used to be handed back on the broker's backoff, one delivery per attempt, which walked a person's answer to the dead-letter subject while a stale node kept refusing it. A refusal on the run store's word alone (a newer lease stamped the row) while the host still holds the seat is still handed back on the backoff, because quiescing a seat the node does hold would leave it hearing no answer or completion at all; the heartbeat settles that disagreement within a beat. The fencing epoch the store compares is monotonic across restarts on every topology ([Coordination](coordination.md#the-leases-follow-coordinationtype-the-shared-state-does-not)), so a seat's own holder is never refused as older than its runs.

**Both routes leave a record.** `executor_answered` names the run, the question it answered (`launch_id`, `question`, `question_context`, `decision`, `asked_at` and the audience), the option chosen (`choice`) and the person's own words (`answer`), which is the one account of the question that outlives the run: a person's [answered decisions](../guides/worklet.md#asking-for-a-decision) read it back from the event log. It also names the route (`chat` or `operator`), who answered (the chat sender, or `answered_by` and `answered_by_kind` as `iam.ActorFor` names the person, the seat they hold, which every person does, with the credential they came through in `operator_id`) and what the answer became: `resumed`, `not_awaiting` (another answer had it first, or the run is running a job), `gone` (the run had ended), `declined` (an answer by turn every attempt failed to resume the run with, let go of; the run waits on its question again) or `unoffered` (an answer by turn whose choice the question it names does not offer, spent without being recorded; the question still waits). The chat route used to leave nothing at all. A chat message that matched no parked run was never an answer and records nothing; an answer recorded on its run whose resume is still being retried has not become anything yet and records nothing until it has. A chat reply let go of becomes the ordinary message it is, and records nothing either.

The durable state is always **git plus the persisted row** — the WIP branch is pushed *before* the agent asks, so the paused box is a fast-resume optimization, never the store. Clarifications chain within the same round of the same turn — an answer carries the run on rather than spending an iteration — bounded by the budget: every relaunch is held to `turn_engine.executor_min_budget_tokens` and each run to its `max_turns`. The wait for the person has no deadline: `pause_ttl_seconds` bounds only how long the paused box is held, and past it the pause reaper below releases the box and the run re-seeds from its branch when the answer comes.

**The pause reaper.** A human reply can take days, and E2B holds a paused box — billing for the snapshot — until something kills it. Nothing else would, so the completion poll enforces `pause_ttl_seconds` on the same tick it uses for running jobs. The box's age is durable (`paused_at` on the run record, stamped when the box is paused), so the deadline survives an engine restart — and a seat handoff — instead of resetting with the process. Past the TTL, a parked run gets:

1. **the box killed by id** with `sandbox.Provider.Kill`, never `Connect`, which auto-resumes a paused sandbox and would boot the VM back up purely to shut it down;
2. **the box released on the row** (`sandbox_id` cleared, `paused_at` cleared) — which is also what makes the answer's relaunch provision a fresh box (a re-seed) rather than reattach to a dead id;
3. **the run flipped to `reseed`** — still claimable, still matched by conversation, because the run is not over. The answer can arrive days later and still carries the run on: the same round is relaunched fresh in a new box, its brief telling it the question, the answer and the pushed branch to check out.

**A pause that was never recorded is still a pause.** Stamping `paused_at` is a *second* store write, made once the box is already paused, and it is warn-only: the job is over by then, and refusing a collected result over a timestamp would throw the whole run away. So a run can park holding a snapshot its row does not date — and reading that as "no snapshot" skipped exactly the box that needed reaping, on a remote provider, for ever. A parked row naming a box therefore *is* a held box: with no stamp, the deadline runs from the row's own last write, which on a parked run is the park itself (a park that does not land is not a park — see step 2 above), and which can only be later than the pause it failed to record, never earlier. The same reading draws the dashboard's `paused_at`, so the screen and the reclaim cannot disagree about which boxes are being paid for. A pause held for any *other* reason takes no such fallback: every one of those lasts a single dispatch and is settled by the tail that made it, so there a missing stamp means the box is live.

**An answer still waiting on its resume is still a clarification wait.** A recorded answer (`answered`) is resumed by whichever node holds the seat, when the seat's own conditions allow — and a seat that no node holds, or one that stays paused, can leave that resume waiting as long as the question waited. Its box is held for the whole of that wait, so the reaper treats it exactly as it treats a parked run: it kills the box and clears it from the row (with the same last-write fallback when no pause instant was recorded). It does not change the status. The answer stays recorded and is still owed its resume, which re-seeds from the pushed branch just as a `reseed` run's would. If the answer is later let go, the question reopens as `reseed` rather than `awaiting_clarification`, because the box it was parked in no longer exists. A resume that has already claimed the run moved it out of `answered`, so the reaper's flip loses, exactly as it does against an answer's claim.

`pause_ttl_seconds: 0` takes the same path with no snapshot at all: the box is torn down the moment the run blocks and the run parks straight into `reseed`.

The reaper is scoped to **clarification waits** on purpose. The lifecycle pauses a box in one other place — between collecting a completion and the turn's settle or relaunch — but that pause lasts a single dispatch and is settled by the tail that made it, so expiring it would only break a relaunch's reuse. The one paused box no tail will ever settle is a run whose engine died mid-resume; that one is reaped by the coordinator's recovery pass when the seat is next acquired, the single moment the row is unambiguously abandoned.

## Durability, completion, and observability

**Pending runs survive restarts, and seat handoffs.** Every detached run is a record in the fleet's [coordination store](coordination.md#what-the-fleet-shares), not in the node's own database, and the difference is the whole reason it is durable at all: a run outlives its turn, its process and sometimes its *node*, and the node that owns the seat next is the one whose recovery pass has to find it. Per-node, that pass listed nothing, so the parked turn was unreachable and a billed box was neither resumed nor reaped. On acquiring a seat (boot included), and for every seat a node already holds when an apply brings its sandbox up, the coordinator's recovery pass (`Coordinator.RecoverSeat`) takes ownership of the seat's running jobs and marks the seat busy again; the waiter then drives those jobs to completion. Recovery also takes over a run left in `resumed`: that state can only mean the previous engine died between claiming the run's tail — a completion, or a person's answer — and settling it, so nothing will ever pick it up again (the at-most-once claim already flipped) and its paused box would stay billed with nothing to reclaim it. A completion's claim is reaped. A claim taken for a person's recorded answer that no turn took yet is **revived** instead — given back to the answer, and the run resumed with it — and reaped, its answer handed back to the seat, only past the revival's bounds; one whose resumed turn had already taken the answer is reaped as spent (see [Mid-run clarification](#mid-run-clarification-ask_and_wait)). The store revives and lets go of only an answer no turn took, and will not delete a run still holding one, so neither can happen beside the take. The reap fences the row to the new holder's lease first, so the node that stopped cannot take the answer after all, and reads it again, so a claim that node gave back first is taken over as the run it is rather than reaped. Every run the seat holds is fenced the same way, a parked one included, so a node that lost the seat cannot claim the answer that arrives for it either. A run left in `launching` is reaped for the same reason one step earlier: that engine died between starting the job and writing the parked turn state a resume reads, so there is nothing to resume and never will be. Both are only safe to reap *here*: taking the seat's lease is what proves no live process is still driving the row, which for a `launching` row is the whole argument, since one on a seat this node already owns is a launch happening right now. A restart never orphans a job: an E2B box runs server-side, independent of the engine, and any process can reconnect by `sandbox_id`; a `direct` or `container` box keeps running on its host while the engine process alone restarts, and the node that launched it picks it up again when it is back (below). A restart that takes more than the engine process with it — its container, its systemd unit's control group, its host — takes a `direct` box's job too, and that job is not collected as though it had finished: its round is carried on (*A job lost with its host*, below).

**The completion poll is THE completion signal.** The box's waiter — the fleet's duty for an `e2b` box, the launching node's own for a `direct` or `container` one (below) — attaches to each running box every 15 s (`DefaultPollInterval`) and asks the runner whether the job finished; a run's `submit_work` nudges an immediate poll, and the 15 s tick is the fallback. Nothing from inside the box replaces it: only a poll can see a job that died before its last step, and the tick has to run anyway because it **doubles as the box keepalive** (the TTL refresh that keeps a running box from being reclaimed on its clock).

**Two waiters: the fleet's, and each node's own.** A box in the `e2b` cell can be reached from any node, so one node polls all of them: the **fleet's waiter**, a [singleton duty](seat-ownership.md#singleton-duties) (`sandbox-waiter`). A `direct` or `container` box is a process tree or a container on the host of the node that launched it — the run's record names that node, `launch_node` — and no other node can reach it: polled from another node, it reads as gone. So **every node runs a waiter of its own** for the boxes on its own host, whoever holds the duty and whatever roles it has: it polls those runs, keeps their boxes alive and reaps their pauses, and no other waiter touches them.

**A run that submits is polled at once.** When a run's `submit_work` is recorded on its row over the [tool bridge](#the-tool-bridge--a-seats-own-tools-from-inside-a-box), the node serving the run's session tells the waiter that drives it — on whichever node that is — to poll it now, and again 1, 3 and 7 s later while its CLI makes its closing model call and exits; the schedule doubles its gaps and stays inside one poll interval, past which the ordinary poll is as soon. The run's completion is found within seconds of its exit instead of up to 15 s after it, and the 15 s poll stays the fallback for a run that ends any other way — one that died, was cut off at its turn's cap, or never submitted. The nudge is a hint on an ephemeral broadcast, never an instruction: the waiter it reaches reads the run's row and does what its own poll would, so a nudge that is lost costs one interval, never the run.

**No box waits on another.** Each tick of the fleet's waiter claims the waiter duty — a node's own waiter claims none, since nothing else reaches its boxes — lists the runs and hands every box that needs work — a poll, or the reclaim of a pause past its TTL — to a task of its own, at most **16 at once** across every tick in flight (`sandbox.MaxConcurrentPolls`, half the shared transport's warm connections to one host, so the launches and collections beside the poll keep the other half). The tick does not wait for its tasks: the next one comes on schedule, renewing the duty and polling every box whose last poll has finished, and passes over a box whose poll is still running, so one box is never polled by two polls at once. A box's completion is announced the moment its own poll finds it. Free slots go first to the boxes whose last poll ended longest ago, so a box that held one goes to the back of the line after its turn. Each poll — reaching the box, its keepalive and asking its runner — is bounded by the **duty claim that authorised it**: the claim's TTL less one interval, **30 s** at the default cadence, or **60 s** (the control plane's whole-request budget) where that comes first. A peer can take the duty only once it lapses, so a poll never overlaps a peer's on the same box; a node told the duty is a peer's stops its polls at once. A box that took the whole bound is not answering, and it costs that box's poll (counted against reaching it, where it was reaching it) and a slot, never anybody's tick: with N boxes held at the bound, a healthy box waits at most N/16 bounds, rounded up, for a slot — against a fifteen-minute TTL. The tick used to poll its boxes one after another, so a box whose in-box agent held a command open for its ten-minute silence bound held every box behind it, their completions unannounced and their keepalives unsent toward a fifteen-minute TTL.

Two signals cover every way a job can end:

1. **The done-marker** — the wrapper shell wrote the exit code after the agent process returned (clean finish or crash; the marker is non-empty by construction so it can't be confused with "not yet").
2. **Process liveness**: the box is asked whether the detached wrapper is still running. **A read that fails never skips this probe**: the probe still runs, a dead wrapper is still a finished job, and the read's error is reported beside a "not done". A remote or container box answers with `kill -0` on the wrapper's pid inside its own process namespace; a `direct` box answers from the job's recorded identity (the pid and its start time, see [Local sandboxes](#local-sandboxes)), because on the engine host a pid the kernel has handed to another process would otherwise read as the job and hold a dead run open. A dead wrapper with no marker means the whole process group was killed (SIGKILL / OOM); the run completes and `collect` surfaces the partial output and exit code instead of stalling forever — unless nothing saw it die: a job on the engine host whose last witness, the engine process that last saw it running, is gone too was **lost** with that process rather than ended, and is not collected as a result (below).

Both coding agents this build drives exit when their work is done, so nothing is read off the end of a stream to decide it. OpenCode 1.x did not — it finished and held its process open — and was once polled for a terminal event at its stream's end; OpenCode 2 exits when its session does, and its run's script exits after it.

**A reader never wakes a box.** The poll and the live view reach a box with `Provider.Attach`, which never resumes it: on E2B it reads the box (`GET /sandboxes/{id}`) and refuses a paused one, rather than `POST /connect`, which wakes a paused box and resets its timer; a paused container is refused too, since its liveness probe is an exec it cannot take; a `direct` box is read as it is, stopped or not, since its files and its probe are the host's. Only the collection and a follow-up run reconnect with `Connect`, which resumes. This closes a race: the poll's list of running runs is a moment old, and a collection claims a run, reads its box and pauses it — a poll reaching the box after that pause used to wake it, nothing renewed it again, and on E2B it was killed at its timer, taking the parked run's snapshot with it. A paused box sends the poll to the run's record instead. A record still running the same job in the same box whose job a collection already read back — the collection paused the box and its resume then handed the claim back, held by the node that met a model's limit or to be tried again — has the job announced again and its box left asleep, neither woken nor kept alive: the job is over, and the collection that next claims it wakes the box to read it. A poll that woke it kept a running box alive at every tick for as long as the hold lasted, up to the hour a vendor's window is sat out. Only a box under a job no collection has read back is woken, kept alive and polled, since only the poll can say whether that job finished, and no finished job is left that way for a condition of its seat's: a completion is refused for its seat's budget or a limit its models know only after it is collected.

**A local box is the node's that launched it** ([ADR-0065](../../adr/0065-a-local-box-is-driven-by-the-node-that-launched-it.md)). The seat a run belongs to can move while its job works — a rebalance, a drain — and the run's tool calls follow the seat over the bridge, but a `direct` or `container` box stays where it is, so every touch of that box is made on its host. The seat's new holder collects the run by asking the host to read its box back, over a channel the fleet signs (`sandbox.box_read`), and fits the result itself; the host makes the read only where the run's own record licenses it, and a host that does not answer — restarting — has the claim handed back uncounted (`sandbox_collect_host_silent`) and announces the completion again from its own poll once it is back. A person's stop of such a run is decided and its tool-bridge session closed at once on the seat's holder, and that node's own retry asks the host what the run had spent, off the frame the pause reached it on: a host that does not answer is asked again rather than having the run's spend written off (`sandbox_stop_read_waits`), until it answers or has been silent for `default_timeout_seconds` since the stop — the bound after which the fleet takes a silent launch node for gone — and only then is the run ended with nothing read (`sandbox_stop_unread`). A relaunch on the new holder starts in a fresh box of its own, from the pushed branch, rather than continuing in one it cannot reach. A box no run names any more — its run ended, stopped or relaunched elsewhere — is reclaimed by its host: each box records the run it was made for, every pass of the host's own waiter kills the box whose run no longer names it (`sandbox_host_box_reclaimed`), and the node that left the box there tells the host to look at once. A box whose run ended while its host was stopped is reclaimed the same way on the host's first pass. The run's [live output](#watching-a-run-live) is read on the host too, and a `from_sandbox` publish on another node is refused rather than reading a box it cannot reach.

**A node that never comes back.** If the node a local box is on leaves the fleet and does not return — its presence lease lapsed and stayed lapsed for `default_timeout_seconds` (15 min), the same bound an E2B box gets without its engine's keepalive — the fleet's waiter records on each of that node's running jobs that it was lost with the node (`sandbox_launch_node_gone`) and announces their completion, and the seat's holder carries each job's round on in a box of its own, as for any lost job (below). A run of that node parked on a question has its box released and waits for its answer without it, resuming from its pushed branch. A node that is merely restarting — a drain gives its presence up at its first step — is back inside that bound, and its own waiter picks its runs up again; the bound is measured from when the fleet's waiter first found the node away, within one stint of its holding the duty: a waiter that loses the duty, or cannot confirm its claim, forgets every absence it was timing, so an absence nobody watched whole is never counted, and a move of the duty can only make a verdict later. Raise `default_timeout_seconds` for a deployment whose nodes are routinely away longer than that.

**A vanished sandbox can't orphan a run.** If reconnecting fails on several consecutive ticks (~1 min at defaults), the waiter gives the box up and fires completion anyway. A box its backend says is **gone** — a local box root that did not outlive its node (a pod recreated with its scratch volume), a VM E2B reclaimed while the engine was down past the keepalive grace — took its job with it: the waiter records it lost (`box_gone`), and its round is carried on (below). A box that is only **unreachable** — a network partition — may still hold a working job, so the coordinator's collection asks again for its own minute of retries, which a partition that heals in that minute survives (see [Failure modes](#failure-modes)), and only then frees the agent, ends the run and announces it as `executor_failed` with reason `collect_unreachable`, rather than polling a dead box forever.

**A job lost with its host is carried on, not collected.** A job can go without ending: a `direct` box's job is a process tree of the engine host, detached into a session of its own so that it outlives the engine process — and it does, when only that process dies — but a container restart takes every process in the container, a systemd unit stopped or restarted kills every process in its control group (the default `KillMode`), and a host reboot takes a `container` box's job as well. Each kills the job mid-step, before its wrapper writes the marker that says how it ended, which is exactly what a job that crashed on its own leaves; read that way, the turn resumed on a truncated run as though the run had failed, or — once its box was gone too — the run ended the turn, which the park had already acknowledged, so nothing would ever start it again. So each local box records its job's **witness**: the engine process that last saw the job running — the one that started it, and then whichever process of the engine first finds it still running after a restart — by its pid and the start time the kernel gives it, which together do not repeat. A job that is not running ended in its witness's sight while that process is still there, and is collected as before, a crash included; a job whose witness is gone too went with it, or after it, before any engine could see it end, and is **lost** (`sandbox_run_lost`, cause `engine_restarted`). A box with no witness record is read as ended. A `container` box's runtime is asked whether the container is up before the job is (a listing it answers, absence included), so a daemon that is briefly away is no answer at all rather than a job that ended.

The waiter that drives the box records the loss on the run's row before it announces the completion — `engine_restarted`, `box_gone`, or `launch_node_gone` for a node that left (above) — and the seat's holder, claiming it, never collects it as a result. Where the box is still there it reads what the job did up to then off it, charges what it spent once and publishes it as the job's own record, noted *cut off* rather than failed; a box that does not answer is asked again like any collection, and one that has not answered for the give-up window is left behind, its spend uncharged (`sandbox_lost_run_unread`). Then the turn resumes and **carries the round on** (`sandbox_run_lost_carried_on`): the same round relaunched, its calls so far kept and counted, in a fresh CLI session — in the lost job's box where the relaunch runs on that box's host with the same CLI, its working tree as the job left it, and in a fresh box from whatever the job pushed otherwise — and the run is told that a run before it was cut off, why, where to look for its work, and that what it did through the seat's tools did happen. Two exceptions: a job whose round's calls already hold its `submit_work` finished its work and was lost on its way out, so the round is collected; and a job that had asked a person before it went is parked on its question, as one that finished asking is. **A round is carried on after at most two lost jobs** (`sandbox.MaxRoundLosses`): one loss is routine — a deploy, a drained node, a patched host — and two in one round is a long run that saw a deploy and its rollback, but a third is a run taking its own host down (exhausting the memory its container is held to kills every process in the container on a cgroup-v2 Kubernetes node), and each further relaunch would take the node's other seats down with it. The next loss ends the round's executor phase, and with it the turn, saying how often the round was lost.

**Per-run OTel, without handing the sandbox a secret.** The coding agent's telemetry exports to an **engine-fronted OTLP receiver**, enabled for a box off its node's host by setting `CREWLET_SANDBOX_OTEL_RECEIVER_URL` to the engine API base the sandbox can reach — the public listener's address when Tier A sets `api.public.port`, since an `ingress` node serves `/otlp/` there and nowhere else. A `direct` box needs no address: on a node that forwards — `OTEL_EXPORTER_OTLP_ENDPOINT` set, which the engine's own spans read too — and binds `api.port`, it exports to that node's own listener on loopback, by the tool bridge's rule (above), whether or not the variable is set. A node that forwards nothing hands its own boxes no endpoint of its own, since it would drop what they sent, and a box with no address that reaches it gets no telemetry endpoint at all. Each run gets a **per-run, trace-scoped, expiring token embedded in the endpoint path** (`POST /otlp/{token}/v1/{signal}`), so `OTEL_EXPORTER_OTLP_HEADERS` — the backend's ingest credential — never enters the box; the receiver validates the token and forwards upstream, adding the real auth outside the sandbox. That variable is set **empty** in the box rather than left unset, because an exporter reads it from its ambient environment otherwise — and while a box inherits nothing of the engine's own environment, its image or E2B template may export a value of its own, and so may a `-e` in `local.run_args`. The empty value is what makes the endpoint's token the only credential the run's exporter presents.

The token is **signed and self-describing** rather than a key into a store, because minting and verifying can happen on different nodes: the node running the seat mints when it launches a run, and whichever node the box exports to verifies. Every node derives its signing keys from the Tier A keyring, so a fleet agrees without sharing state. There is no per-process fallback: every node holds a keyring (a node without one does not start), and a keyring that cannot sign for the fleet is refused by name when the receiver is built, because a key of one process's own would validate at the node that minted and nowhere else. Expiry rides in the token, so nothing is reaped and a restart does not invalidate a live run's endpoint. The token also **names the key that signed it**, so a keyring rotation does not invalidate a run already in flight: the key stays on the ring until the operator drops it, and a token naming a key a node no longer holds is refused rather than retried against the active one. The runbook is in [Secret store](secret-store.md).

The receiver **accepts and drops** when no upstream is configured: the engine's own per-turn span still carries the trace, and a deployment with no backend should not have every export fail. A failing backend is never reported to the box either — an exporter that gets a 5xx retries, and retries against a backend that is down turn one outage into two. The run env also carries non-secret resource attributes (`crewlet.turn_id`, `crewlet.agent_handle`) and a `TRACEPARENT`, so Claude Code's spans/metrics nest under the turn (its `CLAUDE_CODE_*` telemetry toggles are injected only for that runner). OpenCode emits no OTLP today — its observability is the published transcript plus the engine-side lifecycle events.

**A run keeps the work item its turn is on.** The launch writes the turn's `work_item` onto the run's record and onto `executor_launched`, and a question the run parks on carries it on `executor_asked`. The record is where the resumed turn reads its item from — the event that resumes it, a box's completion or a person's chat answer, names none — so the second half of the turn is charged to the same work as the first, under the basis `resume` (see [Which work a turn is on](turn-engine.md#which-work-a-turn-is-on)). What the turn had written before it parked travels on its parked state (`execstate`, `Written`) for the same reason. **A record keeps every key it cannot read**: each status flip, claim and release rewrites the whole record, and a node running an older build writes back the keys a newer one added rather than dropping them, so a rolling upgrade cannot strip the item, or anything added after it, off a parked run.

**Dashboard.** The live-state projection keeps the set of runs in flight, and it builds that set from two sources, because neither is enough alone.

- **The lifecycle events keep the set current.** `executor_launched` adds a run. `executor_asked` moves the run to `awaiting_clarification`. `executor_finished`, `executor_failed` or `executor_stopped` removes it. A failure used to be read by nothing, so a lost run stayed on the panel as running; a stop is read the same way, so a run a person stopped leaves the panel the moment its stop is announced rather than at the next reconcile.
- **The durable run record decides which runs exist.** The record is read once when the node starts, before the node serves (before its listener is handed the API surface), and then every 30 seconds (`livestate.ReconcileInterval`). What the record holds replaces what the events built. A process that starts while runs are in flight never saw their starts, and a completion that never arrived would otherwise leave a finished run on the panel with nothing to remove it. Two cases keep the event's version. A run whose event arrived after the read began is newer than the read. A run whose end the events already reported is not put back, because the record lags the end by the collection the end starts. A completion names the job it finished, and a failure is compared with the record's last write.

This replaced a twelve-hour age-out, which was wrong in both directions. A finished run whose completion was lost stayed on the panel as running for twelve hours. A run parked on a question for longer than twelve hours disappeared from the panel, and a run waiting on a person is the one the panel most needs to show.

Each entry is `{turn_id, role, agent_handle, agent_id, coding_agent, provider_key, model, sandbox_id, task, status, started_at, question, audience, body_withheld, work_item, owner, paused_at}` — `provider_key` and `model` the `providers.llm` entry the launch picked and its model. The entry is the company's configuration, sent to an admin alone, as it is on the [`executors`](../reference/api-endpoints.md#get-executors) board; every other reader, a seat's lead included, is sent the model the run runs under.

- `body_withheld` is set for a reader who may not read the launching seat's body, which only an administrator and the seat's lead may: `task` is then empty, and so is `question` unless the question is put to that reader ([A status reader never receives a transcript](../reference/api-endpoints.md#a-status-reader-never-receives-a-transcript)). A reader without Worklet is sent no `work_item`.
- `status` uses the record's own vocabulary: `launching`, `running`, `awaiting_clarification`, `reseed` or `answered` (a reply is recorded and the engine is resuming the run with it). A `resumed` run is over, because its turn has already taken back the result, so it is not listed. The panel used to write `awaiting_input`, a status the record cannot hold, so the dashboard never saw a live run as waiting on a person.
- `owner` is the node driving the run.
- `paused_at` is the pause reaper's own reading of when the box began being held.

Every node reads the same fleet-wide record, so every node's panel shows the fleet's runs. The dashboard's **Executors** screen reads the record directly (`executors`). A run whose box has already been reclaimed is therefore still listed there, with the row's own facts that the panel does not carry.

### Watching a run live

Nothing a running job writes leaves its box until the run is collected, when its transcript — held to the record's bound, its start and its end — rides the launch's own `executor_collected` record. While it runs, its live output is a **question**, asked only while somebody looks: `executor_tail{turn_id, launch_id}` (`GET /executors/{turn_id}/tail?launch_id=…`). There is no event and no row behind it.

```mermaid
sequenceDiagram
    participant D as Dashboard
    participant A as API node
    participant O as Owning node
    participant B as Box
    D->>A: executor_tail{turn_id, launch_id, epoch, after, digest}
    A->>A: read the run's record (launching? not running? who owns it?)
    A->>O: ask on crewlet.observe.executor_tail, with the asker's budget
    alt the reading was read in the last 2 s
        O-->>A: the text after `after`, from the shared reading
    else
        O->>B: attach without waking, then read what each stream grew
        B-->>O: new complete lines
        O->>O: decode, settle and redact, then append to the reading
        O-->>A: the text after `after` — or a reset carrying the last 256 KiB
    end
    A-->>D: {outcome: tail, output: {text, start, end, epoch, digest, reset, held}}
    D->>D: append (or replace on a reset), then trim the front past 256 KiB
```

- **It names the job, not only the run.** A turn can launch more than one job, so `executor_launched` carries the job's `launch_id` (the one the run's record holds and its `executor_collected` record repeats) and the instant the store recorded the launch (`started_at`). A request naming only the turn would show whichever job the record holds now.
- **The node that owns the run answers it, from one reading per job.** Every node serves `crewlet.observe.executor_tail`; the asker reads the run's record, and the incarnation it names as the owner (`PendingRun.Owner`) — or, for a `direct` or `container` box, the node that launched it (`launch_node`), the one node that can reach that box whoever holds the seat now — re-reads the record and answers from its **reading** of the job (`Runner.Follow`): the transcript the CLI's decoder builds from the event stream, or the error stream while the event stream has said nothing yet (a CLI that failed to start), read through a box attached without waking it (`Provider.Attach`). A reading begins at the start of each stream's last mebibyte, on a line, and every read after takes only what was written since — a ranged read of the stream's end sized to what it grew. When that mebibyte holds no line break at all — a run writing a line longer than the window, `\r`-only progress or a minified blob — the reading has no line to begin after, so it DROPS the rest of that one line, up to the first break that lands after it, the way a partial first line always is, and begins showing from there — rather than show it as a whole line redacted with none of the text before it, which could have put the tail of a credential straddling the window's edge on screen. Those bytes are not counted as held, since nothing will ever show them; the reading says instead that it began after the stream's start (`front`), which is what that line is. Nothing in the box is written, signalled or cleared.
- **What it shows is settled.** A line is shown only once nothing written after it can change how it redacts (`redact.Settled`): a line still being written waits for its line break, a private key's BEGIN and the lines under it wait while what comes next could still be the key's body or its END — so a mention of the armour line waits only for the next line, which is not a key's — a line that reads like a key's body — base64 as wide as a key's line, in upper and lower case both — waits until two lines in a row that cannot be one follow it with two more lines after them (four such lines in a row, most often, and five for a run exactly as wide as a key's line, 64, 70 or 76 characters, which an END can read back to across two lines — counted again above a line that could be OpenPGP's checksum, which an END reads back from as from itself), since an END written next could read it back — and a password key waits for the line that decides its value: the value's own, past the wrapping's blank lines, or the next one holding a key or not ending as the key's line did. Not where that line only confirms what the key's line gave on its own, so a run of `password:"` lines is shown as it is written rather than held back whole. A key followed on its line by punctuation and then more — `msg="Enter password:" level=info`, whose quote may be a wrapping's — waits for the next line too, and so does a key a quote closes whose separator ends its line (`case "password":`): one line. Over the 53 files of Go's source tree and x/crypto that hold a password's key, read as written, numbered or as a diff, 14 or 15 lines wait one line longer than they did before a value was read on a later line, by at most 84 bytes. A hash in hex or a path in lower case is in one case and is shown at once; a Go test's name, a CamelCase identifier or a path in mixed case as wide as a key's line is in both, with or without a digit, and waits like a key's line, so a verbose test run's output can arrive in bursts, held as far back as 64 KiB until lines that are no key's release it. A line holding a run that reads like a piece of a key anywhere on it — eight characters or more in both cases with a digit, which an END written next could read back to as a line a cut wrote into — waits too, until four lines that hold none follow it. Fed `go test -v` output of Crewlet's own packages a line at a time, a few hundred bytes wait on average and at most about 4 KiB. So what a viewer sees, read by read, is exactly the whole text redacted — never a key's body that its END line, a moment later, would have hidden. What is held back is counted (`held`), so the screen can say why a line has not appeared.
- **One read of the box answers everybody watching.** The owner reads a job's box at most once every two seconds (`sandbox.LiveReuse`), however many people have the run open, and requests that arrive while a read is in flight wait for that one. Each answer waits for the box at most three quarters of its asker's budget (the request carries it), so a request the asker gave up on frees its answer slot instead of holding it for as long as a slow box takes; the read itself goes on, under its own budget of one completion-poll interval, and the next request is answered from what it found — or, if the box is still being read, from the last read there was, stamped with when it was taken. A reading nobody has asked about for 30 seconds is dropped by the owner's own sweep, every ten seconds, whether or not anything asks it anything again — which in a fleet nothing does once a run stops: the node serving the dashboard reads the run's record, answers `not_running` itself and never asks the owner again, and a viewer who closes the page asks nobody.
- **A viewer is sent only what it lacks.** Every request says what the asker holds — the reading's `epoch`, the byte offset it holds through (`after`) and the `digest` the owner gave it there, all three absent on a first request, which holds nothing — and is answered with the text after that offset, its `start` and `end` offsets beside it — always both, `0` included, since a run that has settled nothing yet is answered at `0` and followed from it. Anything else is a **reset** carrying the last 256 KiB in whole lines (the most a viewer holds, the record's own bound): an epoch that names another reading (the owner restarted, the reading began again further on, the account switched from the error stream to the transcript), a digest that does not match the window the asker holds (a node on a build that derives the stream differently), or a viewer more than 256 KiB behind. A run whose owner moves to a node on the same build **continues**: the new owner's reading of the same stream from the same place derives the same text, and the digest says so. A `direct` or `container` box is read on the node that launched it whoever holds the seat, so its run is followed there across a move of the seat with no reset, and a launching node that does not answer is `owner_silent`, naming that node.
- **Six outcomes, never an empty answer standing in for another.** `tail` is the output (possibly empty: a run that has written nothing yet says so). `launching` is a job whose box is still being made and provisioned — not a run that stopped, and a screen keeps asking. `not_running` names the record's own status — parked on a question, `replaced` by a later job on the same run, or no record at all because the run was collected. `owner_silent{node}` is the node that reads the run's box — its owner, or a `direct` or `container` box's launching node, held or not — not answering inside the two-second fleet read budget (one that is draining or whose heartbeat lapsed is asked like any other, and its silence is this), and it names that node; or an `e2b` run no node holds right now, which names none. `box_paused` is a running record whose box is paused where its backend cannot read it without waking it — the moment between a collection pausing the box and the record moving on — and the box is left paused. `box_gone` is a running record whose box its backend says is gone for good: its provider reaped it, or it's a local box whose root didn't outlive its node. Nothing more is read from it, and its waiter records its job lost, so its round is carried on in a fresh run (see *A job lost with its host* under [Durability](#durability-completion-and-observability)), and a screen keeps asking until the record says so. A box the owner couldn't read is an error, and what crosses from the owner is its class, never its text: the owner logs the failure (`sandbox_tail_failed`, the class as `failure`, at warn for a fault and for a class no wait clears and at debug otherwise), whether it is answering a peer or the person asked it directly, and the asker answers the class. The surface that answers the person writes its own line about the answer at debug, because the failure is in the owner's log already; an owner on a newer build that names a class this one doesn't know is answered as a fault, and the asker logs `sandbox_tail_failure_unknown` naming it. A provider that didn't answer or is at its limit, and an owner that couldn't answer just now (the run's seat moving off it, the node stopping, its coordination store not answering), are `unavailable` with a `Retry-After`; a sandbox setup somebody has to fix, a refused key or an unpaid account are `unavailable` with none, by the [classes a launch is told by](#when-a-run-does-not-start); and a fault of the owner's own is `query_failed`, whose detail is in the owner's log.
- **The dashboard asks every three seconds, and only while somebody is looking**: while a running run's span is open on the turn trace, or while the run's own page (Live › Executors, `#/live/executors/{turn_id}`) is open on a running job. Each request is chained after the last answer, so one open view has one request in flight; closing it or the run ending stops the poll, and so does a failed read the engine says no wait clears (a sandbox setup somebody has to fix, a refused key) until the socket reconnects or the view is opened again. The run's page asks by the `launch_id` the run board names (`executors` serves it), so it shows the job the row holds now, and when a later job replaces it the page reads the board again and follows the new one.
- **After collection the record is the turn's.** A collected run's row is deleted, and its page reads the turn instead: every `executor_collected` the turn's launches published — what each job reported, what it delivered, its tokens and its transcript — under the task its `executor_launched` carried. A link to a run that has finished still lands on what it did.

## Budgets

The coding agent calls the LLM itself, from inside the box, so the engine cannot gate it request by request as the engine's own tool loop gates the reviewer, workers and onboarding. The model is **floor + cap + post-account**:

- **Pre-flight floor, on every launch.** The turn's first launch and every relaunch — a reviewer's send-back, or a person's answer carrying a parked run on — is refused when the seat's or the company's remaining budget in any capped window is below `turn_engine.executor_min_budget_tokens`, or when the budget cannot be read: launching on an unknown budget is how a company discovers its ceiling by spending past it. **Unset, the floor is 25000 tokens**, because a run's first request alone is the CLI's harness prompt and tool definitions — about 15k input tokens for Claude Code — plus the seat's bridged tool array and its system prompt, and a run costs a box, a clone and its setup before that; `0` turns the floor off. Below the floor is a **budget refusal**, which waits rather than fails: on a dispatch the seat is [parked](agent-runtime.md#the-budget-park) until the window turns over or a revision moves a ceiling (`seat_budget_parked` with `starved` set), and a resumed segment is held on the same window, its job kept collected and its seat held. A seat or company `token_budget` ceiling below the floor is refused on the write, because such a seat could never launch.
- **Self-limits.** `role.sandbox.max_turns`, else `providers.sandbox.default_max_turns` (96 unless set), becomes the coding agent's own turn cap on both runners — Claude Code's `--max-turns`, OpenCode's agent `steps` — so the run self-limits.
- **A spent seat is not resumed into a refusal.** On a seat no run holds, a person's reply to a run's clarification question is offered to the run only after the [budget park](agent-runtime.md#the-budget-park) has asked whether the seat has room, because resuming the run charges tokens exactly as a turn does. A seat whose window is refusing holds the reply on its inbox until the window turns over, then offers it. A collected run that takes a window past its ceiling parks the seat's next delivery the same way.
- **Post-accounting.** On collect, reported usage is charged to the budget cascade, and the phase event carries the real usage and cost so the Tokens view rolls a run's spend up alongside the phases on this host. Mid-run enforcement is best-effort by design, the price of the capability. OpenCode's tokens and price come from its session's own report ([OpenCode](#opencode)), and a run whose report is missing reports zero rather than an estimate. **What a run reports is never a refund**: the usage is parsed from what the coding CLI printed inside a box the run's own agent can run any command in, so a negative token count or cost is read as nothing spent (`sandbox_usage_negative`) rather than subtracted from the seat's counter and from every rollup — every runner hands such a figure on as reported, so the floor, and the warning, apply to all of them alike.
- **Charged once per run.** A run's tokens reach the seat's counter and the company's once, however many times its completion is delivered. A resume that fails (the seat moved between the publish and the receive, say) sends the completion back, and the retry collects the same finished job again; the run's coordination record says its spend is already counted, so that retry charges nothing, whether it lands on the same node, on the seat's next owner, or after a restart. The record is written by the same compare-and-swap that hands the completion back, so no retry can find the run reopened without it. A relaunch in the same turn — a reviewer's send-back, or a person's answer carrying the run on — is a second job and is charged on its own. The charge is a **post-charge**: the tokens are already spent, so no cap can refuse them, and both counters record the run in full — in the day, week and month it is collected in, on the company's clock — whatever the ceilings say. A run that takes a counter past a cap is logged as `sandbox_spend_over_budget`, the turn continues regardless, and the next round the seat or the company attempts is refused against the recorded figure — the resumed turn reads the counter once before it calls anything, so its own next round is refused before it is sent rather than billed and then refused. An over-cap charge is recorded like any other, so a retry does not offer it again; only a charge the counter never answered (`sandbox_accounting_failed`) is, and if that one had in fact landed, the retry counts it twice, which trips a cap early rather than late. A charge that reached the **company's** counter and failed on the seat's (`sandbox_accounting_partial`) keeps the company's share — nothing a counter recorded is taken back — and the run's record says so, so the retry records the seat's share alone rather than counting the company twice. A resume that succeeds after such a charge brings no retry, so that one seat's own counter stays short of the run until its window turns over; the company's stays exact.
- **Charged to the task too.** A turn on a Worklet task charges that task for the runs it detached: the turn segment that resumes from a collected run adds the run's tokens to the task's own spend, beside its own phases, along with the condensing of its report or failure where one was past what the run's record carries (see [Spend is on the task](../guides/worklet.md#spend-is-on-the-task)). A run that stopped to ask a question has no such segment until a person answers, so its tokens and that condensing are recorded with the question on the run's row, and the segment the answer resumes is the one that pays them, whichever node it runs on, however long the question waited. Each segment is recorded once, under the run and launch it resumed, so a retried resume adds nothing. A turn a person stops closes with a segment of its own, which charges only what the segments before it left unpaid: a run's spend read when it was stopped, and what a segment charged to nothing handed on — never again what a segment that charged the task already paid for.

## Security model

- **Every run is fully permissioned, and its cell decides what that reaches.** A headless run has nobody to answer a permission prompt, so the CLI runs with every permission in every cell — Claude Code under `bypassPermissions`, OpenCode with every action allowed but `question` — and the engine does not filter what it does inside its box. What it can reach is the cell's: `e2b` runs it on a fresh remote VM per run, off the engine host altogether, and `container` confines it to a container on the engine host with only the box's own directory mounted. Human gating, where wanted, happens at the merge request — not mid-run.
- **`run_in: direct` runs it on the engine host.** There the CLI runs as the engine's own user: per-box state isolation and an allowlisted environment still hold, but the host's files, and whatever that user's credentials reach, are within the run's reach. Pick it only for a dedicated host you are willing to hand to an autonomous agent, for the entry that needs the host itself, or for a first run on your own machine while its seats take work from you alone; pick `container` (or `e2b`) anywhere else, a workstation included, and before a seat takes work from anyone else, with [an image of your own](#bring-your-own-image). It is opt-in twice over — a `local:` block *plus* an explicit `run_in` naming it, on a `providers.llm` entry or as `providers.sandbox.default_run_in` — and because the choice is per entry, a company can run the entry that needs the host login `direct` and point every other seat at an entry whose cell keeps the run off the host.
- **Only the seat's own identity enters the box.** The injected env carries credentials the agent legitimately acts *as*: its LLM entry's key, with the rest of that entry's `env` (a gateway's token among it), and the external-service tokens its config declares (`role.sandbox.env`). Leaking those from inside the box exposes only what the agent already is. Because the code-host token is the seat's **own** (its GitHub App's installation token, scoped to its tier and repositories, or a PAT of its own), an MR/PR the coding agent opens is attributed to the agent, not to a shared bot identity. An app's token in a box lives at most an hour, and is renewed only in the files that name it.
- **Shared infrastructure secrets never enter the box.** The OTLP backend's ingest token is the canonical example: the sandbox sees only an engine-fronted, path-token-scoped OTLP endpoint (`CREWLET_SANDBOX_OTEL_RECEIVER_URL`); the engine attaches the real backend credential upstream. Apply the same rule to any credential you add — if the agent doesn't act *as* it, don't inject it.
- **A run's own tokens are redacted from everything it hands back.** Every per-run token the engine mints — the telemetry endpoint's, the tool bridge's, an artifact view ticket's — opens with the literal `crewlet_rt1` (`crewlet_rt1.<tag>.<subject>.<expiry>.<signature>`), and every text a box hands back — its report, its transcript, its question, its failure, its live output — is redacted of every token of that shape, to `[REDACTED:run-token]`, on the node that collects the run, before anything is stored or shown. It is recognised by its shape, as a vendor's key is, because no node that collects a run holds the tokens its launch minted, and a coding agent that prints its environment or its MCP configuration to debug its setup prints its own.
- **Injected values are ephemeral.** `${VAR}` references are resolved at acquire time into that sandbox's process env only; the database stores references, never values, and the values die with the box.
- **Workers run on the engine host, never in a box.** A delegated worker — including one a run delegates to over its bridge — runs the engine's own tool loop, its CLI's own tools denied and its grant cut from its parent's. No tool it can hold starts a run, and its control denylist keeps `delegate`, `a2a_ask` and the A2A channel tools, and the parent's discovery pair, from it by name.
- **Network egress is the provider's policy.** The engine does not enforce egress rules; use your E2B template's network policy for that, and prefer an allowlist (the LLM endpoint — the gateway its entry's `env` names, where it names one — the git host, the engine's tool bridge and OTLP receiver) in the templates your production agent seats' boxes run.
- **Budgets still bound the run** (previous section), the run's `submit_work` is decoded by the same submission rules as every phase's, and the turn passes the engine's delivery check before it reaches Review.

## Failure modes

### When a run does not start

An executor whose run couldn't be started fails its phase, and the turn with it: the run is the executor itself, so there's no other way to do the turn's work, and the turn's error says what failed. Each backend classes what it failed with at the point it fails, by **what would clear it**, so that whatever tells the failure to a model or a person can say that and nothing of the error itself, which names hosts, statuses, a container runtime's stderr or configuration paths:

| `why` | What failed | What clears it |
|---|---|---|
| `configuration` | The node runs no sandbox runtime for the company, or no tool bridge the run's box can dial (none at all, an `ingress` node on `api.port: 0`, or a cell whose box needs `CREWLET_MCP_BRIDGE_URL` to reach it, with that unset), a cell the catalogue doesn't have, an executor chain with no member whose CLI runs in a box, a login that can't follow the run to its cell (`SandboxCredentialError`), a setup command that exited non-zero (other than 75), a create E2B refuses as malformed (400, 422) or a template it doesn't have (404), an E2B domain that doesn't resolve or whose certificate doesn't match it, an image the container runtime won't start (a pull that failed on a network blip included: only the runtime's own words tell the two apart, and Crewlet doesn't read them), a mount it can't share or the box may not write, a mount probe the runtime refused to run (see the lines below), or a box that can't run its shell, `find` or `head` to list a build | A person: an administrator fixes the sandbox setup. Waiting won't change it |
| `setup_unavailable` | A setup command that exited 75: its recipe saying that a download it makes is failing on the service's side and still was after its own retries (see [Setup steps](#setup-steps--provisioning-the-box)) | A wait, shortly |
| `provider_refused` | E2B refused the company's key (401, 403) | A person: an administrator fixes the provider's credentials |
| `provider_billing` | E2B wants the account paid for before it starts anything (402) | A person: an administrator checks the provider's account |
| `provider_limit` | E2B is at the account's limit of boxes or requests (429) | A wait: a box ending, or the limit's window passing |
| `provider_unavailable` | E2B or the box didn't answer, failed on its side (408, 5xx), or a box went away mid-command, or a container runtime didn't answer the mount probe in time | A wait, shortly |

The executor's phase and its turn carry the class as their `error_kind`, `sandbox_` before it (`sandbox_provider_refused`, …), so the one word an operator acts on is on the record beside the error. A launch this node cancelled (a drain, a lease it lost) is no class: it's `canceled`, however far the provider's request or the container runtime had got; one a person stopped is `stopped`, which is no failure.

A failure no backend classed isn't filed under the nearest class. A seat this node no longer holds, or one a person stopped, launches nothing, and the turn says so rather than that a launch broke (`executor_launch_stopped` for a stop). So does a seat that moves while its launch is under way, its box's setup included. What the launch then meets need not say so, since the seat's next holder ends a launching run without fencing it and the box's attach finds that ending, or no record at all; the turn's own fence is asked again whatever the launch answered, and a closed one hands the delivery on to the seat's holder (`turn_seat_moved`) rather than back for a retry here. A launch below the [budget floor](#budgets) is a budget refusal, and one whose every runner member is sitting out is a limited chain (both below); and a condition of the node (a coordination store that didn't answer, the launch running out of time) or a fault of the node itself carries no class at all. A box the engine host couldn't make a directory for is that fault.

What an operator should recognize:

- **`SandboxCredentialError` at launch** — the entry the launch picked places the seat's run in a **remote** cell, and nothing in the run environment signs in the CLI of its [`providers.llm` entry](llm-backends.md). A login cannot follow it there: it stays on the engine host (it carries a refresh token whose rotation is fleet state), so unless something in the run environment authenticates, the coding agent would fail at its first model call with the vendor's own "not authenticated" — minutes in, naming nothing you could act on. Only a `claude-code` or `opencode` entry reaches this check: a launch passes over any other. The run never starts, and the error carries **your** remedy, chosen by the entry's `auth.mode` before its CLI, because the mode decides what the entry reads at all. Under `api-key` it names the key: the variable `auth.api_key` references, else the CLI's own key variable (`ANTHROPIC_API_KEY` for Claude Code), exported or stored with `crewlet secrets set`, or the seat's own in `role.sandbox.env` — never a headless token, which an `api-key` entry does not read. Under `inherit-env` it names the variables the mode forwards from the engine's own process environment, which the secret store is not part of: export one there, set one in `role.sandbox.env`, or run the entry in a local cell (`providers.llm.<key>.run_in: "direct"` or `"container"`, or `providers.sandbox.default_run_in` for an entry that names none). Both are worded as [`crewlet llm doctor`](llm-backends.md#how-doctor-judges-a-sign-in) words them, and an entry whose CLI names no variable for its mode — `api-key` on `opencode`, which every write of the configuration refuses but an apply only warns about — is told to set `auth.mode: subscription` and run the entry in a local cell for the login it then signs in with. Under `subscription`, Claude Code, which mints a headless token, says "run `crewlet llm login <key> -capture-token`"; OpenCode, which reads its provider's key from its environment, names the provider its model names (`openrouter` for `openrouter/anthropic/claude-sonnet-5`) and says to set that provider's key in the entry's `env` or the seat's `role.sandbox.env`, both exported into the box — for OpenCode any credential-named variable in the run environment satisfies the check, since which variable it reads depends on that provider; and a profile that does neither — a `custom` one, or a built-in one whose `overrides` removed its token or its environment sign-in — says to run the entry in a local cell. A token or key variable the entry's `overrides` names outside the reference grammar (`token_env: MY-TOKEN`, which every write of the configuration refuses and an apply only warns about) is never offered under any mode: no secret store, `${VAR}`, export or token mint can carry a credential under it, so the refusal names that `overrides` field beside the routes the entry still has — OpenCode's provider key, or a local cell, under `subscription`; a forwarded variable in the grammar, or a local cell, under `inherit-env` — and alone under `api-key`, whose one variable it is.
  A credential you declared yourself in `role.sandbox.env` counts, and so does one the entry's own `env` carries into the box — for Claude Code a gateway's `ANTHROPIC_AUTH_TOKEN`, or a Bedrock, Vertex AI or Foundry switch — since the check asks the CLI's profile which variable names authenticate and looks for those in the merged run environment, rather than trying to recognise a credential by inspection. That is what lets it be a refusal instead of a warning. An unresolved `${VAR}` never counts: its key is [left out](#credentials-and-the-run-environment) of the run environment, so the check never sees it.
- **`this seat's executor chain is …, and no member of it can run the executor`**, from `crewlet validate` or a write — every entry the seat's `llm` names drives a CLI with no in-box runner, so no launch could ever pick one and the seat would fail every turn. It is reported at the seat's `llm`, or, for seats that name none, once at the company fallback entry's `agent`, naming the first seat that falls to it. Point `llm` at an entry with `agent: claude-code` or `opencode` and keep the others for the reviewer, workers and side passes, or move one of them to one of those CLIs. It is a [runnable rule](configuration.md#what-a-stored-revision-is-held-to): refused on every write and by `crewlet validate`, and never applied: a node's reconcile refuses a revision that breaks it and keeps the epoch it was serving, and a boot, a reload or a revert refuses it by name.
- **`this seat has N tokens left and an executor run needs at least M (turn_engine.executor_min_budget_tokens)`** — the launch's [budget floor](#budgets). It is not a failure of the turn: on a dispatch the seat is parked until the window turns over or a revision moves a ceiling, logged as `seat_budget_parked` with `floor` and `starved` and a reason that names the window (`budget: <period> window <label> leaves N tokens, below the M an executor launch needs (turn_engine.executor_min_budget_tokens); resets …`), and a resumed segment is held on the same window. A budget that could not be read is refused too, and retried. Raise the ceiling, or lower the floor where the windows are right and the floor is not.
- **`seat "…"'s executor runs in a box, and this node has no sandbox runtime for this company: configure providers.sandbox`** — the launch found no sandbox runtime or no catalogue in the turn's revision. Validation refuses an agent seat with a model and no catalogue, so on a validated company this is a runtime that did not start on this node; its log says why.
- **`an executor needs a tool bridge its box can dial, …`** (or **`… a node serving its tool bridge, and nothing here reaches it`**) — the launch was refused because its box would have no address to reach the seat's tools at: a node with no bridge at all, an `ingress` node with `api.port: 0` that binds no listener for the bridge's route, or a `container` or `e2b` cell — or a `direct` one on a node that binds no listener its boxes reach on loopback (`api.port: 0`, or on a node without `ingress` an `api.host` of one address that is not loopback) — with no `CREWLET_MCP_BRIDGE_URL`. Set what the message names (see [the tool bridge](#the-tool-bridge--a-seats-own-tools-from-inside-a-box)): the refusal is classed `configuration`, which no wait clears. A node that runs seats says each such cell once when a company is applied, as `executor_bridge_unreachable`, before any turn is refused for it.
- **Every runner member sitting out** — every member of the seat's executor chain whose CLI has a runner is sitting out a spent plan on this node, so the launch fails as a call whose chain ran out does, each member's refusal on it: a [limited chain](llm-backends.md#falling-back-between-entries). On a dispatch the turn fails (`llm_unavailable`, the seat's `last_error`, which is no stop) and the seat is parked on its provider (`seat_provider_parked`), reading `stopped` with the reason `provider` until a probe of the chain answers or the company's models change. A resumed segment's relaunch (a reviewer's send-back, a person's answer) that meets it parks the seat the same way, and its resume waits for the park's release: a completion held by the node that met the limit, in that node's memory and never on the run's record, until the instant the limit names, and refused at the admission while the park stands; an answer in its own series, uncharged (see [Both series are bounded](#mid-run-clarification-ask_and_wait)). A completion whose review's chain already sits out a limit parks the seat the same way once it is collected, before its turn runs. A run that ends on its plan's limit sits its entry out on the node that collects it (`cli_agent_run_limit_reported`), so the turn's next launch moves on to the next member; a run that meets the limit midway is not relaunched on another member.
- **`sandbox_run_past_deadline`** (a log line, at info): a turn with a wall-clock cap — a scheduled fire's `timeout_seconds` — reached it with its run still working. The run is ended as if it had finished, its collection reads what it did up to then and marks it cut off, and the turn resumes with that. Raise the schedule's `timeout_seconds` if its runs routinely need longer.
- **`sandbox_prior_reclaimed`**, **`sandbox_reuse_failed`**, **`sandbox_prior_left_to_host`** (log lines): a relaunch did not continue in its turn's previous box — the member it picked runs another CLI or in another cell, the box could not be reattached, or the box is on another node's host — and started in a fresh one from the pushed branch (see *Reuse across launches* under [How a coding task runs](#how-a-coding-task-runs)). Nothing is lost but the box's disk state.
- **`executor_launch_stopped`** (a log line, at info): a person stopped the seat's running work while its executor was launching, so the launch was ended and the turn closes as stopped, naming who stopped it. Nothing needs doing.
- **`setup step "…" writes …, which a direct box refuses`** (or **a container box**, or **an e2b box**), from `crewlet validate` or a write: a setup step writes a file outside the home of a local box some seat runs in, or one an `e2b` box refuses — another account's `~name/…`, or the home itself or a directory above it — so every box of that seat would fail at setup. The problem sits at the file's entry in the step, and names the first seat whose box it fails and how many more. Name the file relative to the box's home instead — `.npmrc`, `.local/bin/tool`, or `~/.npmrc` — which every cell writes under its home, or have a command of the step write it under `"$HOME"`: a `direct` box's home is minted per box, so no absolute path a file entry holds is inside it. Moving the seat to the other local cell helps only one way round: an absolute path under `/home/user`, which a `direct` box refuses, is taken by a `container` box, while a path outside the home is refused by both. Moving it to `e2b` helps for any absolute path the local cells refuse, `/home/user/…` and `/usr/local/bin/tool` alike, since that box writes both; it refuses another account's `~name/…` and the home itself or a directory above it, as both local cells do.
- **`local sandbox (run_in "direct") refuses to touch …`** or **`… is not a file under the sandbox home mount at /home/user`** (a `sandbox.LocalError`): a path a box was asked to write or read is outside its home, which neither local cell writes outside of — `direct` because the path would be the engine host itself, `container` because only the home is mounted. A setup file that names such a path is refused on the write (above), so at launch this is a stored revision that keeps such a step — an apply warns about it rather than refusing it — or a directory in the box's home that is a link leading out of it, which only the box can see: a link in a box's home is followed only while it stays there, so one the box's own work made must be relative and lead to somewhere inside the home. For a setup file the remedy is the one above: name it relative to the box's home, or have a setup command write it under `"$HOME"`.
- **`… neither docker nor podman is on the engine host's PATH`** (a `sandbox.LocalError`): `run_in: container` with no container runtime on the engine host's PATH. Install one, name it in `local.runtime`, or use `direct`.
- **`cannot see its own box directory`** — the runtime is driving a daemon on another host, so the bind mount is that machine's filesystem rather than this one's. Point `local.runtime` at a local daemon, or use `run_in: e2b` for a remote runtime.
- **`refused to run container sandbox …'s mount probe`**: the container runtime wouldn't run the probe in the box it had just started. The container exited at once (its image's own command failed), or the daemon refused the exec. The runtime's own words end the line. It's classed `configuration`, as every refusal of the runtime's is.
- **`did not answer its mount probe`**: the runtime didn't finish running the probe in the box it had started within 10 seconds: its daemon was too slow or wedged, or reading the mount hung. It's classed `provider_unavailable`, which a wait clears.
- **`cannot make a directory in its own home`**: the probe ran, and the container can't write its home mount, because it runs as a user the mount refuses. Run it as a user that can, with `run_args`, or mount the box directory writable.
- **`could not run its mount probe, because this host could not run the container runtime`**: the engine couldn't start the runtime's binary a moment after it started the container with it. That's a fault of this host, and carries no class.
- **`"container" needs the `local:` backend configured under providers.sandbox`** — an entry's `run_in` (or `default_run_in`) names a cell the catalogue does not hold. Add the block the cell needs, or point the entry at one that is configured; the message lists what this catalogue has.
- **`the catalogue offers more than one place to run one`** — an entry a seat's executor launches on names no cell and the catalogue names no `default_run_in`. Name the cell where the message points, or name the default. A catalogue is not refused for being ambiguous on its own — only a seat or entry that would actually fall to the missing default is.
- **`nothing names one, so no backend is built`** — an ambiguous catalogue that *nothing* reaches: no `default_run_in`, no entry's `run_in`. Nothing would be built and no seat could run code, so the block reads as configuration and configures nothing. Name the default, give an entry a seat's executor launches on a `run_in`, or remove the block while no agent seat runs on a model.
- **`writes its box directory as a user this engine cannot manage`** — the container is running as someone the engine cannot follow into the mount, which happens when `run_args` overrides the `--user` the backend chose. Drop that override, or run the engine as the same user the container does.
- **`sandbox_env_unresolved`** — a `${VAR}` in the run environment, or a setup file that is one whole `${VAR}`, resolves to nothing and its key is not declared optional; the executor run starts without it. The line names the keys and the `<step>:<path>` files, never a value or a body, and sorts the variables by why each is missing. It is at info when every variable is only `awaiting`, and a warning otherwise:
  - **`awaiting`**: an integration is setting the value up for the seat. A [provisioning pass](integration-reconcile.md) is minting it, and a run launched after its seal reaches this node is given it; or it is the seat's own `${GITHUB_APP_TOKEN_<HANDLE>}`, which nothing seals: the engine issues it at launch once the agent's GitHub App is created and installed (**Company › Integrations**), a run launched after the reconcile records the installation is given it, and a running job's token file is written by the first poll after the app can issue one.
  - **`stopped`**: the integration that mints or issues it won't until a person acts. Act on its finding, which the line quotes; for the agent's GitHub App that is its **Create** or **Install** on the GitHub card.
  - **`unissued`**: the engine went to issue the agent's GitHub App token and GitHub didn't give one. Where GitHub didn't answer, or answered a 408, its rate limit (a 429, or a 403 its headers mark as one) or a 5xx, the line says GitHub is asked again on the restart schedule, and the first ask it answers issues the token. Where it refused, the line carries GitHub's status (a revoked key, a suspended installation, a permission the installation hasn't approved) and says the token isn't issued until somebody fixes the app: fix the agent's GitHub App, its installation or its permissions.
  - **`unset`** or **`empty`**: set the variable the line names (`crewlet secrets set`, or the integration's provision command for a seat's own bot or account), or list its key under `optional_keys` where the run can go without it.

  `optional_keys` never releases a variable an integration mints or issues for the seat: the line names it whatever the declaration says. And `${GITHUB_APP_TOKEN_<HANDLE>}` is the engine's to issue: it is never set with `crewlet secrets set`.
- **Setup-step failure** (`sandbox_setup_failed`) — a step's provisioning did not complete, and the box is torn down before any brief runs. The message names the step and says which of three things failed: `could not write <path>`, a file the box refused (in a local box, with the reason above), `command #N failed (exit S)`, a command that exited non-zero (in every cell, 124 is its `timeout_seconds` running out, with the timeout named before what the command printed, and a status above 128 is a signal that ended it — 128 plus the signal's number, 137 for a `SIGKILL` such as an out-of-memory kill — as a shell reports one; where the signal ended the box's own shell in a `direct` or `e2b` box, rather than a program that shell waited on, the signal is also named after what the command printed, while a `container` box's command reads as `docker exec` reports it, the status alone), or `command #N reported no exit status`, one the box could not start or whose box went away before it finished, with the box's own account after it — an `e2b` box's in-box agent closing the command's stream with an error of its own names that error there. A command that exited 75 is its recipe saying a download it makes failed for now, which a wait clears (`setup_unavailable`); any other failure is an operator config problem (a broken recipe, `configuration`). Either is logged distinctly from a coding-agent install failure.
- **Sandbox lost mid-run** (`sandbox_run_lost`, a log line at warning, naming the `cause`): the job was lost with the host it ran on — `engine_restarted` (its engine's restart killed it), `box_gone` (its box is gone from where it ran) or `launch_node_gone` — and its round is carried on in a fresh run (`sandbox_run_lost_carried_on` on the node that holds the seat; see *A job lost with its host* under [Durability](#durability-completion-and-observability)). Nothing needs doing for one. A run whose turn then ends with `the executor's round was lost with its host too often to start again` lost more than two jobs in one round: it is taking its own host down, most often by exhausting the memory its container is held to — give the box more, or a cell of its own. Look for `sandbox_connect_failed` streaks before a `box_gone`; if the engine was down longer than `default_timeout_seconds`, E2B reaped the box as an orphan, and that TTL is the knob to raise for deployments with long maintenance windows.
- **Collect failure**: the box could not be read back. **It is asked again first**: nothing the completion writes — the charge, the run's phase record, the park, the resume — happens before a collection succeeds, so handing the claim back leaves the run exactly as the completion found it (running, its box kept alive, its turn parked), and the completion comes back on the queue's backoff while the poll fires a fresh one on its next tick (`sandbox_collect_retried`). The allowance is the poll's own for an unreachable box — at least two **consecutive** failed attempts spanning a minute, counted on the run's record so another node or a restart does not start a fresh one, and ended by a collection that did read the box (one whose park or resume then failed and handed the claim back), so a box that answered is never given up on the strength of failures from before it answered — and past it the box is torn down, the run ended and announced (`collect_unreachable`), and the agent freed. A box its provider says is **gone** is settled at once, since no attempt can read it. A collection **this node** stopped — a drain, a restart, the seat moving to another node — is handed back without being counted (`sandbox_collect_interrupted`), because it says nothing about the box; a collection that ran out of its delivery's time is counted, or a box whose read always outlasts it would be retried for ever. A file merely too large to read whole is never a collect failure: that piece is described by its size and the run is collected without it.
- **`sandbox_suspension_*` errors** (`executor_failed` with reason `suspension_unrecorded`): the turn parked but its parked state (`execstate`) never reached the run's record, because the runner recorded none, it would not serialize, the coordination store refused the write, or the run was no longer launching. The run was already executing, so a run still launching has its box reclaimed at once and is ended, rather than left to run to its TTL with nothing able to collect it. A run that is no longer launching is left alone and not announced: a write reported as refused can have landed, which makes it an ordinary parked run the completion poll collects, and a run already ended was announced by whoever ended it. A store refusal points at the coordination store; the other three are a defect in the engine worth reporting.
- **`executor_failed` with reason `claim_unreverted`**: the coordination store refused two writes on one row in a row. A completion claims a run's tail before collecting it, and every failure after that claim is recoverable only because the claim can be given back — so when the park a run asked for, or the revert a failed resume makes, cannot be written *and* the claim cannot be returned either, the run is ended here instead. The row would otherwise sit in `resumed`, which no completion poll reads, no redelivery can re-claim, no answer matches and no pause reaper expires: an unrecoverable turn plus a paused box billed until the seat changes hands. Look at the coordination store — this reason means it refused or could not be reached twice within one delivery.
- **`turn_rebased`** (a log line, not an announcement): a turn's unit of work began more than twenty-nine days before this attempt — a run resumed that long after its work began, or a trigger dispatched that long after it arrived — so its operation ids are minted at this attempt rather than at that start, and the instant is recorded so a later attempt at the same work inherits it (see [How a coding task runs](#how-a-coding-task-runs)). `seed` is the unit of work, or the run where there is none; `began` is the start, `inherited` the instant an earlier attempt had recorded (the start where none had) and `rebased_to` the new one. Nothing is wrong and nothing needs doing: it says that a tracker or knowledge-base write an earlier attempt made and this one repeats is a second write rather than a retry of the first (a work-item comment, a created item and a created view excepted, which are found by their ids and answered from their rows) — minted at the start, every data node's operation ledger would have answered every new write of this attempt `unknown` instead. It is logged once per rebase; an attempt that inherits a recorded instant logs nothing above debug.
- **`sandbox_answer_headroom_reserved`** (a log line, not an announcement): every message of this delivery has spent nearly all of its deliveries, so the answer route stopped offering it and the 5 that are left are kept for the ordinary route, which is being run on it now. It is what stops a reply being handed back until the broker dead-letters it, and it is the expected end of a resume that fails on *every* node rather than on this one — the per-process attempt count below cannot see that, because a seat handoff resets it and the broker's count is on the message. The line names the seat, what the partition had left and the reserve. A parked run is unaffected: it keeps waiting, bounded by `pause_ttl_seconds`.
- **`sandbox_answer_offered_over_a_spent_sibling`** (a log line): the opposite decision, and the one whose cost is paid elsewhere. A message of this delivery still has the deliveries to spare, so a parked run is being offered it — while another message in the same partition is inside the reserve, and a hand-back returns the whole partition. It is the advance notice for a `dead_lettered` line on that sibling, and it is the expected shape of a conversation whose earlier message has been handed back many times and which is still collecting fresh replies.
- **`sandbox_answer_resume_failed`** (a log line, at warning): the answer recorded on a parked run could not be resumed with — the error says why — and the coordinator will try again after the spacing the line names. The seat's later mail is held behind it meanwhile. Nothing is asked of the person: the answer is on the run.
- **`sandbox_answer_unverified`** (a log line, at error): the answer recorded on a parked run does not open as an answer to that run's question under the fleet keyring — the error says how — so it is handed to no turn, attributed to nobody and let go of with nothing handed back, and the run waits on its question again. A reply given after this answers it as usual.
- **`sandbox_answer_key_unknown`** (a log line, at warning): the answer recorded on a parked run is sealed under a key this node does not hold, and `node_holds` lists the ones it does. The answer stays recorded and owed, with the seat's mail behind it, until a node holding the key takes the seat or this one restarts with it in `secrets.keys`; the line repeats every five minutes while it waits.
- **`sandbox_answer_requeue_exhausted`** (a log line, not an announcement): this node could not resume one parked run with the answer recorded for it in every attempt its budget allowed — ten of them, spaced a second apart doubling to thirty, or as many as the run's `pause_ttl_seconds` left room for — so the answer was let go: the reply was handed to the seat's inbox as the ordinary message it is and is being worked as the turn it looks like, and the run waits on its question again with that reply declined for it. Its box is still bounded by `pause_ttl_seconds`. The line names the run and the window; the error beside it is the one to read, and it is nearly always this node rather than the run — no resumer on this node, a parked turn state of an `execstate` version this build does not read, or a seat that is not in this node's company. The seat's next holder, or this node after a restart, starts a clean set of attempts on the next reply.
- **`sandbox_answer_record_exhausted`** (a log line, not an announcement): this node could not RECORD one message as the answer a parked run is waiting on — the coordination store refused the write — in every attempt its budget allowed, so the message was let go to the ordinary route.
- **`sandbox_answer_lookup_exhausted`** (a log line, not an announcement): this node could not read *which* of a seat's runs is awaiting a reply — the coordination store refused the lookup — for every attempt the message's budget allowed, while the seat's own count said one of its runs is waiting for one. The message has been let go to the ordinary route and is being worked as the turn it looks like. The line names the seat and the delivery; the error beside it is the store's. `sandbox_answer_lookup_failed` is the same failure before the budget is spent, at warn, once per attempt.
- **`sandbox_claimed_settled_unread`** (a log line, not an announcement): the resumed turn came back (cleanly, or having broken after this attempt wrote outside the engine), and the run's record could not be read to find out which box to reclaim. The settle does not go quiet over that: leaving the row in `resumed` is the same unrecoverable state `claim_unreverted` exists to avoid. Instead it asks the coordination store to end the run **while it is still the claim it took**, which is what keeps it off a job the resumed turn relaunched: a relaunch moves the row back to `launching` and reuses the same box, so the ending declines it (`sandbox_claimed_settle_declined`) and that run is ended by its own turn or by the seat's next recovery pass. A store that refuses this too logs `sandbox_claimed_settle_kept`: the ending is kept, and this node finishes it, box included, once the store answers, or the seat's next recovery pass reaps the run if the seat moves first; both lines point at the coordination store.
- **`executor_failed` with reason `abandoned_tail`**: the node that held this seat stopped — a crash, a deploy, a lease that lapsed — between starting a run and writing the parked turn state it resumes from, or between claiming its tail and settling it, and the seat's new holder ended the run as it took the seat (`sandbox_abandoned_tail_reaped`). Nothing retries it: the turn that parked on the run cannot be continued. A claim for a person's answer that no turn had taken yet is not ended this way but revived and resumed with the answer (`sandbox_answer_revived`, below) — unless 3 claims of that answer have already died the same way, or the run's `pause_ttl_seconds` has passed since the first did: then the detail says which, and the answer has gone back to the seat as the ordinary message it is, once (`sandbox_answer_not_revived` names the bound with its `reason` and `lost_claims`; `sandbox_abandoned_tail_reaped` carries `answer_handed_back=true`, and the announcement's detail ends "the answer a person gave it goes back to the seat"). `answer_handed_back` is the field to search: the line's `answer_held` and `answer_taken` say only what the row held, and a held answer a turn took is held too. A line with `ending_decided=false` was written before the store confirmed the ending; its retry decides it, and the announcement it makes says whether the answer went back. An answer a turn had already taken was used by it and is not handed back (`answer_handed_back=false`). Look at why the previous holder stopped — and, past the revivals, at what stops a node between a resume's claim and its turn: three in a row is a resume that takes its node down, not a coincidence of deploys.
- **`sandbox_answer_revived`** (a log line, at info): the seat's new holder found a person's answer claimed for a resume by a node that stopped before its turn took it, and gave it back to the run, which it now resumes. `lost_claims` counts the claims of this answer that have died so far and `first_lost_at` dates the first; nothing is asked of the person. A `sandbox_answer_revive_owed` warning is the same holder unable to confirm the revival with the coordination store: it keeps the claim, holds the seat's mail and tries again every 30 seconds.
- **`executor_failed` with reason `resume_broken`**: the turn a run belongs to could not be re-entered — resuming it broke before the turn began, typically a panic decoding the parked turn state or re-entering the turn (`sandbox_resume_panicked` and a `turn.guard_breach` on the log). It is not retried, because every attempt re-enters the same bytes and reaches the same defect; a person's reply that drove the resume goes back to the seat as the ordinary message it is, and the detail says so. Look at the panic. A resume that broke *after* its turn began is not announced here: that turn published its own failed completion.
- **`sandbox_collect_host_silent`** (a log line, at warning): the seat's holder asked the node whose host a run's box is on to read it back, and it did not answer — stopped, restarting, or gone. The claim is handed back uncounted and that node announces the completion again from its own poll once it is back; a node that never comes back has the run's job lost with it (`launch_node_gone`), and its round carried on.
- **`executor_failed` with reason `seat_removed`**: the seat left the company's agent seats — it was removed from the chart, or made a person's and not made an agent's again within the 24-hour retirement grace — so its runs were ended when its mailbox was retired. See [Seat Ownership § The removed seat](seat-ownership.md#the-removed-seat).
- **`steer_reader_never_ran`** (a log line, at warning, on the node that collects the run): a run whose CLI takes a person's notes between its steps succeeded without asking for them once — a Claude Code run always asks at its finish, and an OpenCode run's plugin as soon as its session starts working — so something in its box switched its reading off: for Claude Code its [hooks](#claude-codes-hooks), by a managed policy that allows only managed hooks or disables them all, or a CLI older than 2.1.163, which the run starts without them (its error stream says so); for OpenCode its [plugin](#opencodes-notes-plugin), by a managed policy that denies it or a load that failed, which OpenCode's own log names. Any note sent while it worked waited for its review rather than reaching it between its steps. The line names the run, its job and its CLI.
- **`a hook in the run stopped its loop before it finished (Claude Code terminal_reason hook_stopped)`** — a hook of the repository's or the image's own settings exited 2 or returned a block, and Claude Code ended the run part-way while reporting a success subtype. The run is a failure saying so; the run's own steering hooks never block. Fix or remove that hook in the repository or the image.
- **`this box's home "…" cannot be named in an OpenCode run's configuration`** — an OpenCode run's configuration names its instruction file, its notes plugin and its servers' values by paths under the box's home ([OpenCode](#opencode)), and this home is one the configuration's text cannot carry: relative, or holding a brace, a quote, a backslash or a control character. A local box's home is under `providers.sandbox.local.state_dir`; move it to a path without one. The run starts nothing.
- **`crewlet: the run has no OpenCode configuration at …`** (the run's error output) — the configuration the runner writes before every OpenCode run was not there, or was empty, when the run's script started: something in the box removed it between the two. The script stops before it imports a login or starts a server, and the next run writes the file again.
- **A run that "finishes" with no report** — the coding agent neither wrote its findings file nor streamed a final message. `collect` surfaces the exit status, the CLI's own account of how it ended (an error subtype, or that its stream stopped before its result) and the stderr as the error; the turn's collected record and its reviewer see a failed run rather than an empty success.

## Testing

`providers.sandbox.fake: true` wires the in-process fakes (`sandbox.FakeProvider`, `sandbox.FakeRunner`): scripted results, an in-memory filesystem, no network, per the project rule that tests never touch real services. The engine's tests script what a run does — its calls to the seat's tools over the real bridge, its `submit_work`, its question — and the end-to-end company runs its executor in a real `direct` box whose `claude` is the test binary. The runner tests pin the exact CLI invocations (`claude -p … --output-format stream-json --verbose`, `opencode run … --format json`) and output parsers — Claude Code's against fixtures written from the vendor's documented stream-json message schema, and its hook lines and result messages against Claude Code's own output for 2.1.263 and 2.1.310 run against a stub model API (no model is ever called), and once through a real shell with a stand-in CLI so the wrapper's copy of the result line and the CLI's own exit status are exercised as they run; OpenCode's notes plugin runs, as the engine writes it into a real box, under `node` against a stand-in of the notes route, against a real bridge's own route, and against a stand-in of the context OpenCode hands a plugin — and `internal/config/examples_test.go` parses the git-auth recipe out of *this page* and holds it to its security properties (host scoping at both layers, `--add` rewrites, identity from the engine's agent facts) so an edit cannot quietly widen them. This is the copy readers take, so this is the copy under test.
