## The decision

**An executor's run launched while its seat holds other runs is told of them and given three tools.** Its brief lists each run in flight on the seat (its turn, stage, work item, and, for a run working for the same requester, its conversation's kind and whether it is the caller's, the branch it named, when it started and its task's title), with one line on when to use the tools: overlap on the same item, branch or conversation; an unrelated run is unrelated. The run's surface then offers `list_runs`, `message_run` and `wait_for_run`, beside `ask_and_wait`. Both are read once, from one listing of the seat's runs, with no model call; a launch that finds none is told nothing and offered none.

**What a run is shown of another follows whom each works for.** Two runs share a requester when their ceilings name one principal, read in the order the ceiling composes it ([ADR-0109](0109-a-turn-somebody-woke-is-held-to-the-apps-they-use.md)), a run's own work as its seat's; a stranger is nobody's. Another requester's run shows its stage and item alone, since its task's words carry that requester's data.

**`message_run` files a message as an item on the receiving run's record**, read at its next step under a wake's heading, fenced as the sending run's executor's words ([ADR-0040](0040-content-a-model-reads-carries-its-provenance.md)), naming the sending run and whom it works for. It is information, never a request: the receiving turn's task, requester and apps are unchanged. It is refused:
- between runs of different requesters, since a run's words carry its requester's data and no label decides whom data is for; the refusal says to tell the requester instead;
- to the caller's own run;
- to a run not launching or running, or whose harness reads no note;
- past the sending job's two messages or the receiving job's two, never cut.

The message rides a wake item ([ADR-0167](0167-a-busy-seats-wake-from-its-requester-joins-the-running-run.md)), an item of its own, sealed in its own domain (`seat.run.message`) and naming its sending run in the clear: so it is served, confirmed, told again to a continued session and kept as the turn's once read, and holds one of the job's four wake items and its hook take. Two each way, because one message tells what a run is doing and one answers it; a third is a conversation for the requester. And never more than half the job's wake items, so the requester's own follow-ups keep room to join.

**`wait_for_run` parks the run as a question does**, with its own words for why, on a run of its seat holding a slot. The wait is put to nobody. The node holding the seat watches the waits on its seats and, once a wait's run leaves its seat's slots (it ends, fails or parks), carries the waiting run on from its row, never recording an answer, telling it how: ended and its outcome, parked and on what, or gone with nothing on record; what it pushed; and, for a run of the same requester, the first lines of what its reviewer said landed, inside that account's fence. A run leaving on the node nudges every watch; a watch reads again at least every minute. The waiting run's requester is told once, on the conversation's line, why its work waits. **A waiting run is a turn still in flight on its conversation**, so a conversation never runs two turns at once through the wait. Answered or not, it keeps its keys, its conversations and its own key, and holds no slot, unlike a run parked on a question, whose next message in the conversation is the answer the park routes. No reply there answers the wait; its mail waits aside behind it ([ADR-0169](0169-a-seat-runs-up-to-its-cap-of-runs-one-per-conversation.md)'s aside), its writer told once that the work waits on the run. Resuming, it hands that mail back to be screened against it running, where a follow-up from its requester joins it; ending while parked, it frees and readmits its keys. A wait whose run outlives it ends as an unanswered question does: its box is reaped at its pause TTL and it waits in `reseed` for the answer.

**A wait that would close a cycle is refused**, followed through the seat's runs' waits for at most eight runs. No cycle can hang (each waiting run has parked, which answers the runs waiting on it), so the refusal saves both runs a park whose only answer is that the other parked.

## Why the obvious alternatives are wrong

**A new item kind beside wakes.** A session read asks about at most sixty-four hook takes, and notes, late calls and wakes use all of them; a message from another run is a wake's shape, read where a wake is read.

**Messages between any two runs of a seat.** A run working for one person passing what it read to a run working for another would hand one person's data to the other, the ceiling ADR-0109 keeps; "the same seat" is no requester.

**Waiting inside the tool call.** It would hold the harness, the box and the slot for as long as the other run takes, which is the reason a question parks ([ADR-0077](0077-a-tool-call-that-needs-approval-parks-its-run-in-the-shape-a-runs-ask-does.md)).

## Amendment: other seats' runs on the same work

A run is also shown other seats' runs on its work: on its work item, in its conversation (its identity, a thread where the surface has them; never a schedule's, which each seat it fans out to works alone), on an item the tracker links to its item (a dependency, a link or a duplicate, either way, at most sixteen), or on an item or conversation one of the two runs created or wrote, named by which way it goes: a run on the ticket the caller's calls filed or in a thread they posted in, or the run whose calls filed the ticket, or posted in the thread, the caller works on. A thread counts where the run's set names it, so a Chatlet thread does; a vendor chat post made through an MCP server names none. They are found in one listing of the fleet's runs, never one read per seat or per run, at most eight, oldest first, after the seat's own, each line naming the run's seat and how it relates. What a line shows follows whom each works for, as above.

What a run created or wrote is the set its log keeps ([ADR-0167](0167-a-busy-seats-wake-from-its-requester-joins-the-running-run.md)), and its row keeps a key of each record (the first sixteen bytes of its SHA-256, in hex), folded in by the write that records the call's spend, so the listing matches both ways on the rows it reads and the caller's own set is on its row. Not the records themselves: at their bound, escaped, they weigh about 200 KB, past the room a row keeps for a later build's keys; nor a read of each run's log, up to 3.5 MB each.

A message to another seat's run, and a wait on one, take the same terms and one more: the caller's seat must reach the other seat as `a2a_ask` reaches a colleague, an agent seat the chart's authority offers the ask's verb to the caller's seat for, so a seat the chart keeps from asking a colleague cannot message that colleague's runs either. A wait on another seat's run also needs the same requester, since its answer carries that run's report. The message carries the sending run's requester as an ask does (`types.WorkingFor`, composed from the sending run's row), and the receiving run reads it as a run's message is read, naming the sending seat and whom it works for. The cycle walk reads each run a chain reaches that the caller's listing does not hold, at most eight. A run waiting on another seat's run is answered by its own seat's watch, which reads the other run's row, and its ending from the executor log once its row is gone, at least every minute.

This answers [crewlet/crewlet#394](https://github.com/crewlet/crewlet/issues/394): a run sees the work in flight around it and may ask it, only where the other run's harness takes a note.

## Amendment: a run parked on its own call

A wait may name the run's own bridged call in place of a run. A harness that gives a call up at a clock no setting moves has its runner state that ceiling, and the tool bridge answers a call still running before it as a phase answers one ("end your turn now: you will be resumed with its result"), first parking the job on the call as a wait put to nobody. The run's collection waits for the call before the job parks, so the seat's watch carries the run on at once, in its own session, told that its call returned, its brief telling the call and what it returned. A job that works on is handed no item of the call, so its relaunch tells it once. Every call promised a resume is added to the job's parked calls, a second one and one after a question or a wait included, never refused as asked already: whatever answers the job, its resume tells each. Not a relaunch cause of its own: a wait already is a question put to nobody that the engine answers, and a question's answer already carries a run on in its session.

## Amendment: the engine's answer is never recorded as an answer

The watch once answered a wait or a call park as an answer by turn, recorded and sealed as an operator's answer with keys saying it was the engine's. A build without those keys, in a rolling upgrade, dropped them and told the run "the person you asked answered". So the watch puts a wake of its own type on the seat's control topic (`executor_wait_over`, naming the run and the job that parked), and the seat's holder carries the run on from its waiting row: it reads how the waited run left, or which calls returned, and claims the run straight out of waiting. The claim keeps its own take and revival on the row, so a holder that stops between the claim and the turn leaves the run waiting again, and one whose turn took it is never carried on twice. A build without the wake drops it as any type it does not know, and finds no answer on the row. A call park is marked in the job's parked calls, never as a wait: that build reads a wait as one on the run it names, and one naming none as that run gone; it parks the call park as the question it reads, put to the seat's people, whose answer is a person's own. That build keeps the parked calls and the claim through its relaunch, as keys it does not know, so each names its job and is read as none under another; and its watch's answer by turn, reaching a run this build carries on, is spent unrecorded.
